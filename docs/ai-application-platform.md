# AI 应用平台远期能力地图

本文只保留远期视野，不是当前产品规格、课程顺序或验收清单。当前产品要求见根 [SPEC.md](../SPEC.md)。

## 为什么保留这张地图

需求评审助手应吸收成熟平台的边界意识，但不复制平台规模。远期能力用于帮助判断今天的接口是否留下合理扩展点，而不是授权预建空模块。

## 能力域

| 能力域 | 远期问题 | 当前项目边界 |
| --- | --- | --- |
| 模型与 Provider | 多供应商、路由、配额、能力目录 | 统一配置与真实错误即可 |
| 知识生产 | 文件、解析任务、版本、Chunk、索引、删除 | 先支持固定格式与来源链 |
| 检索 | 多路召回、Rerank、Graph、多跳 | 先用 FTS、pgvector、RRF 基线 |
| Agent 与 Tool | Agent Registry、权限、沙箱、连接器 | 先做一个受治理 Runtime |
| MCP 与 Skills | 能力发现、复用、版本和信任 | 先接一个真实能力和一个领域 Skill |
| Multi-Agent/A2A | 跨系统任务、身份、结果和错误 | 先证明本地责任拆分收益 |
| Workflow | 画布、调度、恢复、人工任务 | 只做必要状态与恢复机制 |
| Evaluation | 数据集、实验、Judge、回归、反馈 | 每层先保留最小质量证据 |
| Observability | Trace、Metrics、成本、告警 | 先关联 Run、事件和错误 |
| 安全治理 | 租户、RBAC、审计、数据边界 | 当前只做最小权限和人工确认 |
| 产品体验 | 证据、过程、等待、冲突、协作 | 当前工作台呈现真实运行事实 |
| 部署运维 | 多环境、灰度、弹性、容灾 | 当前只要求可部署和可诊断 |

## 从成熟产品吸收的边界

- 文件、业务文档、Chunk、索引和 Citation 是不同对象。
- 应用、知识、模型、Tool 和 Agent 是不同资源，不应散落在 Prompt 中。
- 简单固定链路应先成立，再增加 Agent 或编排。
- 解析、检索、Tool、状态、错误和来源必须可观察。
- 平台抽象只有在第二个真实消费者或明确变化点出现时才有价值。

## 准入规则

远期能力进入当前产品前必须同时回答：

1. 解决哪个已复现的真实问题？
2. 为什么现有最简单结构不足？
3. 输入、输出、状态、权限和错误是什么？
4. 收益怎样在固定样例或运行记录中证明？
5. 引入后由哪个 package 或产品模块负责？

未满足时只保留认知，不创建 package、demo、配置、数据库表或 UI 占位。

## 明确不直接搬入

- 完整多租户、企业权限中台和组织体系。
- 通用连接器市场、工具市场和 Agent 市场。
- 低代码 Workflow 画布和通用应用生成平台。
- 大规模知识库运营、计费、配额与模型网关。
- Kubernetes、灰度、跨区域容灾和企业告警平台。

这些能力可以影响边界设计，但不能变成两个阶段的隐藏验收项。
