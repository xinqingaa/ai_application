# AI 应用课程学习与工程指南

本文是课程组织、文档职责、代码关系和学习验收的规范真源。长期目标见 [strategy.md](strategy.md)，产品要求见 [SPEC.md](../SPEC.md)，工程实现边界见 [PLAN.md](../PLAN.md)。

## 1. 学习方式

课程设计从需求评审助手的产品目标反推知识，学习者按认知前置正向学习：

```text
项目愿景与阶段目标
→ 概念建立局部心智模型
→ 机制解释数据或状态变化
→ 实验运行真实代码并观察
→ 项目篇组合能力
→ 测试、评估和需求修改
```

产品反推决定“学什么”，认知前置决定“先学什么”。课程只有第一阶段、第二阶段和一套连续编号；`course/learning-path.md` 是阅读顺序和课程序号的唯一真源。目录、知识地图、正文页尾、文件名和工程计划都不能形成第二套课表。

### 学习者视角

课程不是知识目录的扩写。每个学习单元按下面的认知顺序组织：

1. 从学习者此刻真实遇到的问题开始，不从术语定义或完整架构开始。
2. 先用自然语言、前端或跨端开发经验建立局部直觉。
3. 当数据流或状态流确实需要一个新对象时，再引入术语并立即解释。
4. 沿一条主要链路说明输入怎样变成输出，以及约束在哪一层生效。
5. 再把机制放回需求评审助手，说明它解决什么、不解决什么。
6. 通过实验观察、失败定位和修改任务把理解落到真实代码。

学习完整性不以读完多少名词判断，而以学习者能否解释问题、追踪数据或状态、观察结果、定位失败并判断自然边界。

## 2. 四类课程文档

四类文档共同服务于同一学习单元，但各自只承担一种主要职责。正文都要从学习者当前遇到的问题出发，说明已有输入、本文交付和非目标；新术语首次出现时先用自然语言解释，并沿一条主要数据、状态、证据或异常链路组织内容。标题保持简洁，优先使用学习者已经接触过的术语，表达核心对象、关系或边界；尚未解释的本地 package、类名和目录名先在介绍或正文中建立含义，不用标题代替解释。

### 概念篇

回答“是什么、为什么需要、与相近概念有什么区别、边界在哪里”。它可以引导一个阶段、学习单元或独立概念。

概念篇至少建立：真实问题、最小心智模型、输入输出、相近概念、典型误区、适用与不适用边界，以及它在完整产品中的位置。涉及框架时，概念篇解释 Provider、框架运行时、本地通用封装和产品领域组装的层次与选型边界，不展开 API、版本和安装。默认不讲实现代码、运行命令和项目任务。学习单元完成后可以增加“学完后回看”，但不能倒灌全部机制细节形成总复习文档。

完成标准：学习者能用自己的话区分相近概念，并能判断一个新问题是否属于本文范围。

### 机制篇

回答“为什么有效、数据或状态怎样变化、关键约束是什么、边界在哪里”。机制篇是课程核心正文。

机制篇围绕一个大问题中的一个局部问题，至少讲清：它要解决什么问题、当前已有输入、一条主要数据流或状态流、关键对象与不变量、简单方案的不足、正常边界、异常边界和向后交付。机制可以由原生实现、成熟框架或二者组合承载；选用哪种手段不改变机制篇作为核心正文的地位。

当课程以框架能力解决当前问题时，机制篇直接解释框架的公开能力、核心抽象、运行流程和扩展位置，说明框架怎样完成该能力、应用怎样提供配置与业务约束，以及两者如何组合成完整结果。框架术语、必要的接口形状、状态图、数据流、伪代码和少量关键代码都可以用于解释机制；最小原生实现只在有助于看清框架隐藏的责任时作为对照，不是机制篇的前提。

机制篇不承担文件树、命令、安装、完整可运行项目、完整日志、逐步调试和按版本罗列的 SDK 调用，也不逐行导览框架或本地源码。这些操作性内容进入实验篇；实验篇运行和验证机制，不能替代机制篇对框架能力与实现逻辑的解释。

新术语第一次出现时必须先用自然语言解释，不能用另一个尚未解释的术语替代定义。框架的公开概念和理解机制所需的关键接口可以进入机制篇；项目文件路径、完整调用代码和调试顺序进入实验篇。

完成标准：学习者能从输入解释到输出，指出关键约束在哪里生效，并区分机制边界、配置问题和外部依赖失败。

### 实验篇

回答“代码怎样准备和运行、改变什么、观察什么、失败时怎样定位”。正文位于 `course/labs/`，真实代码位于 `source/demos/` 或阶段产品。

实验篇至少承担：

- 对应机制、观察问题和本实验不能证明的内容。
- 环境、真实依赖、凭证、数据和运行前检查。
- 唯一主入口、精确命令、参数、默认值和退出状态。
- 运行前预测、固定输入和一个主要变量。
- 正常输出、关键日志字段和结果解读。
- 自然 bad case、真实依赖失败和确定性契约失败的区别。
- 从表现到原因再到验证方式的排查顺序。
- 从 demo 入口进入公共能力和测试的读码路径，并说明每一站的责任。
- 一个修改任务、预期变化、不应变化的契约和验证命令。
- 使用框架或协议时固定实际 SDK、Provider 和协议版本，运行官方或成熟入口，观察公开状态、事件、错误和 Trace；升级差异与迁移操作也在实验篇验证。

实验篇引用机制篇，不重复完整原理。框架主线先直接运行成熟实现；最小原生实现只用于对照框架隐藏的控制流、责任和失败边界，不能逐步扩成另一套教学框架。主线机制通常配有实验，但文档、demo 和课程序号不强制一一对应。学习者应能只依赖当前课程、产品运行文档和明确前置，从干净环境完成实验；不能依赖已经删除的旧 README 或隐藏操作。

完成标准：学习者能独立准备、运行、读日志、定位失败、改变一个变量并用测试或对照验证。

### 项目篇

回答“怎样把已学能力组合成可验收产品结果”。项目篇位于 `course/project/`，引用根 [SPEC.md](../SPEC.md) 的产品要求，负责学习目标、设计题、集成检查点、需求变更、bad case 和阶段验收。

项目篇至少讲清：阶段问题、已有能力、数据/状态/异常流、设计选择、真实代码入口、集成检查点、自然 bad case、需求变更、验收证据和非目标。涉及框架时还要验收框架运行时、本地通用层与领域组装的职责分界，新能力是否进入正确层次，以及相对更简单实现的收益；不能用“框架能够运行”代替产品验收。项目篇不能复制产品规格或运行手册；产品安装、API、运行和部署由 `source/apps/review_assistant/README.md` 维护。

完成标准：学习者能把能力组合进唯一产品，解释为什么这样分层，完成一个业务变更，并用真实运行、测试或评估证明结果。

## 3. 一节课的粒度

一个编号只承载一个核心学习问题，可以同时链接一篇机制正文和一篇配套实验。

课程标题与标题下方的介绍共同表达学习问题。标题负责让学习者快速识别主题，不必写成完整问句，也不把全部子步骤塞进标题；介绍负责补充当前问题、学习交付和非目标。官方概念或框架能力已经足够明确时可以直接进入标题，本地内部名称则应在学习者理解其职责后再使用。

出现以下情况时优先拆分：

- 同时存在两个独立生命周期。
- 同时改变两个主要数据或状态对象。
- 需要两套不同的实验变量或失败模型。
- 协议概念、协议生命周期、真实接入和项目职责被放进同一正文。
- 标题列出多个并列主题，但无法用一条数据流连接。
- 同一节既要回答“是否应该使用”，又要完整解释“运行时怎样执行”。

概览型概念篇可以展示多个对象，但只负责建立关系，不在一节中讲完每个对象的机制。正文不写死“上一节、下一节”，只说明知识输入、本文交付和复用方向。

学习路径中的每个编号必须有简短介绍，至少说明当前问题和本文交付；不能只留下标题、状态或实验链接。知识地图中的每个知识节点必须有核心问题与边界说明。

## 4. 学习定位与产品准入

文档类型、学习定位和产品准入是三件不同的事：

| 维度 | 回答的问题 |
| --- | --- |
| 文档类型 | 应该用概念、机制、实验还是项目篇解释 |
| 学习定位 | 它是必备基础、主线、扩展还是未来认知 |
| 产品关系 | 当前产品必须接入、条件接入、只做受控实验，还是不实现 |

准入顺序是：

1. 它解决 SPEC 中哪个真实问题。
2. 普通程序、专用 Tool 或已有能力是否已经足够。
3. 它是否改变产品输入输出、权限、状态、副作用或验收。
4. 课程需要理解机制，是否等于产品必须启用。
5. 产品接入后怎样用真实运行、测试或评估证明收益。

学习主线不自动等于产品默认接入；受控实验也不自动授权产品能力。相反，产品必接能力必须在 SPEC 中有职责，并在项目篇和验收中可追踪。

## 5. 三个课程真源

- `course/learning-path.md`：现在读什么，以及唯一编号。
- `course/knowledge-map.md`：有哪些能力、前置、定位、核心边界和学习入口，不安排顺序。
- `course/project/`：怎样把知识组合成阶段综合实践，不复制产品 Spec。

知识地图不维护课程序号，不要求知识项与正文一一对应。一个知识节点可以由概念、机制和实验共同承担；一篇正文也可以覆盖同一问题下的多个紧密知识点。

### 当前基线与课程演进

三个课程真源维护的是当前有效基线，不是永久冻结的课表。长期方向、两个阶段、唯一项目、连续编号和文档职责保持稳定；总节数、未编写课程的拆分与顺序、知识节点，以及 MCP、Agent、Agent Skills、A2A 等演进领域的具体内容，可以根据认知前置、真实项目反馈和官方规范更新而调整。

调整只进入唯一学习路径和真正受影响的知识节点，不另建版本课表。全局编号必须连续；已经形成学习依赖的课程不因普通排课优化反复改号，但事实错误、失效边界和必要前置仍应修正。

协议和快速演进框架的课程分开维护三层内容：跨版本稳定的问题、角色与机制；当前规范的版本特性；实验使用的协议修订、SDK 和真实服务。学习路径与知识地图不穷举 API，机制篇标明所依据的官方规范修订，实验篇固定 SDK 与协议版本，并区分核心、可选扩展、实验能力和已弃用内容。

仅 SDK 调用变化时更新实验、README、锁文件和测试；协议数据模型或生命周期变化时更新机制、实验和知识地图，必要时调整学习路径；产品是否使用某项能力变化时先更新 SPEC。文档冲突按 [AI 协作指南](ai-collaboration.md) 的真源顺序裁决，协议事实以对应官方规范为准。

## 6. 代码与文档关系

```text
course/concepts/               概念
course/mechanisms/             机制
course/labs/                   实验教材
course/project/                综合实践教材
source/packages/               通用能力唯一实现
source/demos/                  实验代码
source/apps/review_assistant/  唯一产品
```

每个能力域只维护一个 package。demo 只调用公共能力观察机制，不复制核心算法；产品通过 import 组合 package。没有新的观察维度、通用能力或产品任务时，不为文档创建代码。

README 分工：package README 维护模块职责和公共 API；demo README 维护代码入口、测试和实验篇链接；product README 维护安装、配置、启动、测试、API 和部署；course 文档负责学习解释、实验指导和项目判断。

外部框架不改变代码所有权规则。第二阶段的本地 `agent_core` 随 Agent 框架接入建立，并在课程推进中逐步扩展通用运行、治理和适配能力；产品通过这一层组合框架能力，Prompt、领域 Schema、权限策略、记忆策略和角色组装仍留在产品。实验可以直接调用框架观察公开行为，产品主路径不复制框架运行时，也不预建尚未学习的空实现。

## 7. 产品与 SDD

- `SPEC.md` 是产品“做什么”的唯一稳定规格。
- `PLAN.md` 是 `source/` 怎样实现 Spec 的稳定工程分解，不记录实时进度。
- 项目篇引用 Spec 开展学习、设计和验收。
- 产品代码、Schema、OpenAPI、状态模型和测试是精确执行真源。
- 学习路径只规定认知顺序，不承担工程进度管理。

规格变化先判断是否改变产品输入输出、责任边界、状态、安全或验收；只有真正改变时才更新 SPEC。临时实现步骤、迁移清单和实时结果不写入长期规范。

## 8. 真实调用与证据

LLM、RAG、Agent 和 Eval 主路径使用真实模型或真实外部服务。缺少 Key、鉴权失败、限流、超时和能力不支持必须清晰暴露，不静默返回 Mock、假向量、内存检索或静态成功结果。

Mock 只用于单元测试、离线排查、稳定复现确定性失败或明确对照，并说明它不能证明真实质量。

不同证据证明不同事实：

| 证据 | 能证明 | 不能单独证明 |
| --- | --- | --- |
| 自然 bad case | 真实输入下的能力边界 | 所有输入的总体质量 |
| 真实依赖失败 | Provider、数据库、协议或权限边界 | 内部状态机的全部分支 |
| 确定性契约测试 | Schema、排序、错误转换和不变量 | 真实模型或检索质量 |
| 探索实验 | 候选策略和可能问题 | 产品验收已经通过 |
| 冻结验收集 | 固定范围内的质量、成本和延迟 | 未覆盖场景的表现 |

支撑准入或验收的实验在运行前固定：实验身份、数据集版本、模型、Prompt、Schema、Retriever、Tool 或 Workflow 版本、协议修订、SDK 版本、对照组、唯一主要变量、参数、指标、通过条件、成本与延迟预算、外部依赖和结果位置。

看到结果后不得删除失败样例、回改阈值、改变 split 或覆盖原记录制造通过。需要改变配置时建立新实验并保留旧结果。探索结果可以指导下一次实验，但不能被改名为验收证据。

## 9. 旧内容重构与迁移（按需）

新写课程、普通改写和质量审查不需要执行内容迁移流程。只有移动、合并或删除已有内容时，才先确认原内容的目标归属和学习职责，在目标位置形成可用内容后再删除旧内容，并检查链接、代码注释、README、命令和测试入口。详细操作由课程写作 Skill 的按需迁移流程维护。

## 10. Agent、Tool、MCP、Workflow 与 Multi-Agent

先选择最简单结构：固定步骤使用普通程序或固定 Pipeline；模型需要动态选择下一步时使用 Agent；需要显式状态、恢复或人工节点时使用 Workflow；只有存在独立责任、上下文、工具或可验证协作收益时才使用 Multi-Agent。

第二阶段采用“成熟框架承载主路径，关键机制沿真实运行深化”的方式。LangChain 承担高层 Agent 与 Tool 组合，LangGraph 承担显式状态、持久化、恢复和人工介入；本地 `agent_core` 承载通用 Agent 运行、治理和框架适配，并随课程能力逐步扩展，产品 `agent/` 负责领域 Prompt、Schema、证据、权限、记忆和角色组装。稳定依赖方向是“产品领域组装 → `agent_core` 契约与适配 → LangChain / LangGraph”，框架已有的运行时、图执行器和持久化引擎不在本地重复实现。

无论框架提供多少默认能力，模型都只能理解任务、提出工具和生成参数草案；应用仍负责 Schema 校验、权限、执行、副作用、状态、预算、停止、错误和人工确认。Agent 必须显式表达运行状态和停止原因；Conversation、Run State、短期记忆、长期偏好与可引用业务知识不能混用。Tool Result 和 Agent 推断经过来源与支持性检查后才能成为业务 Citation。

每个 Tool 必须有单一职责、输入输出契约、结构化错误、超时取消、权限、审计和副作用说明。读取与写入分开；通用 Code Tool 只有在专用 Tool 或普通程序不足时才准入，并受沙箱和资源限制。MCP 只标准化连接、能力发现和结果交换，不替代内部 Tool Runtime 的治理。

Agent Skills 封装可发现的说明、资源和脚本，不冒充 Prompt、Tool 或 MCP，也不能绕过 Runtime。A2A 是独立 Agent 间的互操作协议，不等于框架内 Handoff 或本地 Delegation。框架可以提供适配器和协作原语，但不会自动补齐 MCP、Skills、A2A 或 Multi-Agent 的权限、安全、生命周期和产品语义。

Multi-Agent 必须保留单 Agent 基线，比较质量、成本、延迟、证据一致性和失败定位。Workflow 进入产品时必须明确状态、节点输入输出、分支循环、Checkpoint、恢复、人工介入和副作用幂等，不建设无业务需求的低代码画布。

## 11. 学习完成

学习者应能够：

- 用自己的话解释概念、相近概念和不适用边界。
- 画出机制的数据流、状态流、证据流或异常流。
- 独立运行实验、阅读日志、定位失败并完成单变量修改。
- 从实验入口找到公共契约、关键实现和测试。
- 将能力组合进唯一产品并完成一个真实需求变更。
- 使用测试、评估或 Trace 证明结果，而不是只展示一次成功输出。
- 判断何时保持普通程序，何时增加 RAG、Agent、Multi-Agent 或 Workflow。

更完整的代码所有权标准见 [ai-coding-mastery.md](ai-coding-mastery.md)。

## 12. 维护边界

- 长期目标只写入 `strategy.md`。
- 产品要求只写入 `SPEC.md`。
- 工程实现边界只写入 `PLAN.md`。
- 学习与文档规则只写入本文。
- 写作执行流程只写入 `skills/course-writing/SKILL.md`。
- 产品运行事实只写入 `source/apps/review_assistant/README.md`。
- 不在长期文档记录迁移过程、实时进度或临时讨论。
- 不依赖 `archive/` 作为当前主线。
