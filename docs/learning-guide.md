# AI 应用课程学习与工程指南

这份文档是本仓库学习方式、课程组织、文档规范、代码组织和运行规则的唯一真源。

长期目标与项目阶段以 [strategy.md](strategy.md) 为准；AI Coding 掌握标准以 [ai-coding-mastery.md](ai-coding-mastery.md) 为准。

## 1. 核心学习方式

课程设计由需求评审助手的项目版本反推需要学习的知识，但学习者不从完整项目规格倒着学习。

必须区分两个方向：

- **设计者倒推**：先明确项目版本结果，再选择真正需要的概念、机制、实验和代码。
- **学习者正学**：先看通俗项目愿景和当前项目篇中的业务契约，再按认知前置学习概念、机制和小实验，最后回到同一项目篇完成综合交付。

基本链路是：

```text
通俗项目愿景建立方向
→ 读取当前版本的业务契约与非目标
→ 概念篇建立心智模型
→ 机制篇解释内部变化并完成小实验
→ 按当前问题穿插下一个概念和机制
→ 通过实验观察内部过程
→ 回到同一项目篇组合已有能力
→ 调用真实模型和真实外部服务
→ 观察真实 bad case 或正常策略边界并定位
→ 用评估证明改动
→ 完成版本验收
```

“项目驱动”不等于“项目篇先读”。项目目标决定学什么；认知前置决定先读什么。

下面这条认知链仍然适用于整个课程：

```text
真实问题
→ 基础原理
→ 最小实现
→ 主流框架实现
→ 失败分析与能力边界
```

但它是一种思考顺序，不是每篇文档必须照抄的固定标题模板。不同类型文档承担不同职责。

## 2. 学习组织：两个阶段、一个版本轴、三类文档

### 两个阶段

- 阶段一：可信 RAG + 单 Agent 需求评审助手。
- 阶段二：Workflow + 多 Agent 评审系统。

### 版本顺序与阅读顺序

V0–V6 是唯一项目里程碑顺序，版本定义以 [strategy.md](strategy.md) 为准。每个版本内部如何从概念、机制和实验进入项目，由 `course/learning-path.md` 唯一定义。

不再建立这些平行顺序：

- 不维护 M0–M6。
- 不把 LLM、RAG、Agent、Eval 当作必须依次毕业的课程。
- 不为“概念单元”再维护一套与标准学习路径竞争的编号课表。
- 不根据文件名编号推断全局学习顺序。

### 三类文档

课程正文只分为：

1. 概念篇。
2. 机制篇。
3. 项目篇。

三分的是职责，不是篇幅。概念篇和机制篇可以很长、很厚，但必须围绕自己的核心问题展开。

### 知识与功能的分级准入

新增知识、技术或产品需求时，先判断它是否服务当前业务闭环，再决定进入概念篇、机制篇还是项目篇。实现难度是成本因素，不是首要分级依据。

| 层级 | 进入条件 | 必须交付 |
| --- | --- | --- |
| 项目篇 | 缺少它会使当前版本的业务输入、输出、可信性、可用性或验收契约不成立 | 真实产品集成、真实调用或外部服务、测试、失败路径、运行入口和版本验收 |
| 机制篇 | 不一定进入当前产品，但机制具有迁移价值，并且能用边界清楚的小实验观察输入、输出、内部变化和自然边界 | 最小真实实验、对照变量、诊断字段、真实 bad case 或正常策略边界，以及框架或外部服务边界 |
| 概念篇 | 需要建立选型和边界判断，但当前收益未证明、与产品关系较弱、实现成本过高，或者无法形成稳定且有解释力的小实验 | 定义、数据流、相近方案、适用条件、反例、成本和明确非目标 |
| 未来认知 | 与当前项目关系低，当前只需保留视野 | 进入知识地图；没有真实阅读需求时不创建正文或代码 |

文档类型、学习定位和产品关系是三个不同维度：

- **文档类型**回答用概念篇、机制篇还是项目篇承担学习。
- **主线学习**表示当前版本必须理解、实验或作出设计判断，不等于能力必然进入产品默认链路。
- **支撑学习**表示遇到对应真实问题时进入，不阻塞版本验收。
- **产品必需**由对应项目篇的业务契约定义，必须完成真实产品集成和验收。
- **条件准入**可以属于主线学习，但只有预先登记的质量、成本、延迟或可维护性收益超过新增复杂度后才进入产品；Reranker 是典型例子。
- **未来认知**只保留边界视野，不进入当前产品。

`course/knowledge-map.md` 的“定位”只记录学习定位；产品必需项以项目篇为真源，条件准入项必须在知识地图的代码入口或说明中明确标注，不能把“主线”误读为“默认接入产品”。

按下面顺序判断：

1. 当前或近期版本没有它，产品闭环是否仍然成立？若不成立，进入项目篇；不能因为实现困难而降级。
2. 它能否解释当前已出现或即将验证的失败？能否通过受控小实验观察？若能，进入机制篇。
3. 它是否主要用于建立技术选型、能力边界或远期视野？若是，进入概念篇。
4. 它是否只增加技术栈数量，没有新的业务问题、观察维度或可验证收益？若是，保留为未来认知或不进入课程。

机制实验不是进入产品的自动许可。候选能力应先用固定样例和指标证明质量、成本、延迟或可维护性收益；收益大于新增复杂度后，才进入对应项目版本。框架、数据库和供应商只是实现选择，不能代替要学习的机制。

### 评估、验收与实验前约定

课程采用三层契约，避免把所有指标写成永久规则，也避免看到结果后再定义成功：

| 层级 | 真源 | 负责内容 |
| --- | --- | --- |
| 长期规则 | 本文 | 每个版本怎样建立证据、何时冻结实验、怎样修改标准 |
| 版本契约 | 对应 `course/project/` 项目篇 | 当前版本的业务门槛、基线、指标类别、真实 bad case / 边界题、范围和完成标准 |
| 实验约定 | 对应产品或 demo 的 eval 配置、数据集与运行记录 | 本轮数据集版本、模型和策略版本、具体参数、数值阈值、预算与结果 |

每个项目版本必须提前确定：

- 业务目标、输入输出、非目标和最小可用产品入口。
- 硬门槛：缺少任一项就不能通过版本验收的确定性条件。
- 对照基线、固定数据集和需要观察的质量、成本、延迟与失败指标。
- 至少一个来自真实输入、真实依赖或正常策略取舍的 bad case / 边界现象，一个需求变更和对应回归方式。
- 哪些结论由确定性测试、集成测试、质量评估或人工判断支持；不同证据不能互相替代。

凡是要支撑产品准入、版本比较或主线质量结论的实验，必须在首次运行前登记并冻结：

- `experiment_id`、数据集版本和样例范围。
- 模型、Prompt、Schema、Retriever、Tool 或 Workflow 版本。
- 对照组、实验组和唯一变化变量。
- 具体参数、指标、通过条件、成本和延迟预算。
- 真实服务依赖、失败处理和结果保存位置。

实验运行后不能为了让结果通过而回改本轮阈值、删除失败样例或更换对照组。若发现标准不合理，应保留原记录，说明原因，并创建新的实验版本重新约定。探索性实验可以采用更轻量的记录，但必须明确标注为探索，不能作为版本完成证据。

`course/learning-path.md` 只维护必需阅读顺序，不记录具体数值阈值、每次运行结果或实时待办。新知识只有在改变当前版本契约，或解释已经出现且无法由现有内容处理的失败时，才能进入主路径；否则合并进已有概念或机制、进入知识地图，或保留为未来认知。项目版本进入实现后，主路径默认冻结，不能因发现一个新框架或技术名继续扩张。

## 3. 课程入口和唯一阅读路径

`course/README.md` 是学习者首页，`course/learning-path.md` 是阅读顺序的唯一真源。

标准阅读路径：

```text
course/README.md
→ course/learning-path.md
→ 当前版本的标准正向路线
→ 先读取当前项目篇的业务场景、输入输出、Definition of Ready 和非目标
→ 概念篇建立判断
→ 机制篇 + 小实验建立实现能力
→ 回到同一项目篇完成综合实现和验收
→ 对应 package README
→ 运行真实代码入口
→ 观察输入、输出、证据、状态和错误
→ 完成 bad case、修改题与版本验收
```

阅读内容围绕项目问题选择，但按认知前置正向展开，不跟能力目录机械通关：

- 项目篇可以在版本开始时提供固定业务契约，但学习者此时不提前进入实现任务和验收结论；完整综合实践仍位于必要概念、机制和小实验之后。
- 不要求先读完 `concepts/`。
- 不要求先读完某个能力域下的全部机制。
- 不要求学完所有 LLM 内容才进入 RAG。
- `course/concepts/` 与 `course/mechanisms/` 均平铺正文，不按 LLM、RAG、Agent 等能力域分子目录；能力域分组只在 `course/knowledge-map.md` 维护。
- 与项目暂时关系不大的重要知识，可以作为概念或机制补充，但不进入当前项目验收。
- 不根据正文页尾、目录排列、文件名或 package 模块顺序推断下一篇。
- 概念篇、机制篇和项目篇不独立维护平行课表；正文读完后返回 `course/learning-path.md`。

## 4. 集中知识清单

`course/knowledge-map.md` 是课程知识清单的唯一真源，用来回答“有哪些能力、重要到什么程度、在哪里学习”，不负责规定项目阅读顺序。

每个知识项至少记录：

| 字段 | 含义 |
| --- | --- |
| 能力名称 | 需要掌握或认知的知识 |
| 能力域 | LLM、RAG、Agent、Workflow、Eval、AI Native、工程基础等 |
| 文档类型 | 概念、机制或项目 |
| 项目阶段 | 阶段一、阶段二或未来认知 |
| 学习定位 | 主线、支撑或未来认知 |
| 前置知识 | 理解它之前真正需要什么，使用完整知识名称 |
| 文档入口 | 对应概念篇、机制篇或项目篇 |
| 代码入口 | package、demo、app、产品路径或条件准入说明 |
| 正文状态 | 待编写、可学习、需修订等；不表示产品已经接入 |

知识项与文档不一一对应：

- 一篇文档可以讲清多个紧密相关的知识项。
- 一个知识项可以在概念篇、机制篇和项目篇中从不同角度出现。
- 一个项目版本可以同时使用 LLM、RAG、Agent 和 Eval 能力。
- 不为了让知识清单“整齐”而创建空文档、空目录或空代码。

各能力域可以保留标签和分组价值，但不各自维护与知识地图或标准学习路径竞争的课程规划。

### 集中查看知识

`course/knowledge-map.md` 只按 LLM、RAG、Agent、Workflow、Eval、AI Native 和工程基础组织完整知识书架。

- 不在知识地图中维护 V0–V6 阅读路线。
- 不向学习者暴露内部知识编号或编号范围。
- 知识项、前置和项目位置都使用完整名称表达。
- 文档路径或标题锚点已经足够定位知识，不再另建稳定 ID。
- 尚未进入当前项目的知识仍可保留，但必须标明主线、支撑或未来认知。

因此：

- 想知道“现在读什么、下一步是什么”，看 `course/learning-path.md`。
- 想重新理解课程目标和各入口职责，看 `course/README.md`。
- 想集中检查“Agent、RAG 或 Eval 有哪些知识、是否遗漏”，看 `course/knowledge-map.md`。
- 想把已经学过的能力组合成当前版本，进入 `course/project/` 对应项目篇。
- 想理解知识本身，进入对应概念篇和机制篇。

## 5. 概念篇规范

概念篇回答：

> 这个概念是什么，为什么需要它，边界在哪里？

### 必须讲清

- 它解决什么问题。
- 一句话定义。
- 输入、处理和输出。
- 最小心智模型或数据流。
- 与相近概念的区别。
- 一个能够暴露误解的反例。
- 能解决什么、不能解决什么。
- 在需求评审助手中的位置。
- 当前属于主线、支撑还是未来认知。

### 可以采用

- 真实场景叙事。
- 数据流图。
- 对比表。
- 小型示例。
- 常见误区。
- 判断题或自检题。

### 不应承担

- 大段 package 文件树。
- 完整运行参数手册。
- 项目版本的详细任务清单。
- 为了“有代码”而新增实现。
- 在概念尚未建立前直接从框架 API 开始。

概念篇通常可以没有代码。若引用代码或运行结果，必须指向真实入口并说明它只是用于观察什么。

### 完成标准

读者能够用自己的话解释概念、区分相近概念、判断适用边界，并说明它是否是当前项目真正需要的能力。

## 6. 机制篇规范

机制篇回答：

> 这个机制为什么有效，数据在内部如何变化，失败时如何定位？

### 必须讲清

- 现有简单方案的问题。
- 新机制解决了什么。
- 输入输出发生了什么变化。
- 内部数据流、关键约束和不变量。
- 从简单方案到工程方案的递进。
- 可以观察机制的最小实验。
- 至少一个来自真实输入、真实依赖或正常策略取舍的 bad case / 边界现象及定位顺序。
- 不要求把失败写成独立或主要章节，不为了覆盖课程条目凭空制造异常输入、损坏实现或无业务意义的报错演示。
- 主流框架封装了什么、没有解决什么。
- 对应 package、demo 或外部服务的边界。

### 可以对应代码

机制篇可以：

- 扩展已有 package。
- 复用已有 demo。
- 建立必要的新实验。
- 只解释已有真实代码。
- 在没有必要实现时只做机制认知。

机制篇不强制每篇都增加 package，也不要求每个机制单独建立 demo。

### 已有真实实现时的代码桥梁

机制篇不以代码数量判断质量。尚无必要实现时，可以只完成机制认知；已经存在真实 package、demo、产品代码或外部服务入口时，正文必须帮助学习者从机制进入实现，不能只给目录链接、文件树或抽象数据流，把实现解释全部留给 README。

机制篇的解释顺序由领域问题、判断过程和数据变化决定，不能直接照搬 package 文件顺序或函数调用顺序。应先让读者建立“为什么要分这些步骤”的心智模型，再把每一步映射到真实代码责任；源码调用链是机制证据，不是正文天然目录。

正文应按当前问题选择少量真实入口和关键代码，至少讲清：

- 公共入口接收什么，返回什么。
- 核心调用链怎样推进，数据在每一步如何变化。
- 哪些关键约束和不变量由应用代码执行，而不是依赖模型、框架或调用者自觉。
- 正常结果和诊断怎样组装，失败在哪一层转为可观察错误。
- 简单方案为什么不足，工程方案增加的每一层分别解决什么问题。

代码片段只在有助于解释机制时使用，必须来自真实文件并标明路径。正文不需要逐行解释完整实现，也不复制大段源码；但读者只看正文时，应能定位公共入口、复述主调用链，并把关键机制映射到真实代码责任。

存在可运行实验时，正文应在实验结论出现之前明确说明真实代码入口、实验入口和观察问题。具体命令、参数组合、完整输出字段和常见运行故障仍由 demo README 或产品 README 维护，正文只保留完成当前学习动作所需的最小入口。

### 框架使用原则

- 先解释原生机制，再解释框架抽象。
- 使用 LangChain、LangGraph 等框架时，要说明为什么当前问题值得引入。
- 框架实现不能代替基础原理。
- 框架没有解决的错误、状态、权限和评估问题必须显式说明。
- 项目暂时不需要时，不为了覆盖“主流框架”强行增加依赖。

### 完成标准

读者能够画出数据流，预测关键输入变化的影响，运行或解释最小实验，并根据失败现象找到优先排查的位置。

若已有真实实现，读者还应能够：

- 找到公共入口并解释其输入输出。
- 说明核心调用链和关键数据转换。
- 将至少一个不变量和一个真实 bad case 或自然边界对应到真实代码。
- 修改一个实验输入或策略，并在运行前预测结果变化。

## 7. 项目篇规范

项目篇回答：

> 当前版本为什么要增加这项能力，怎样组合已有知识完成一个可验收的业务结果？

### 必须讲清

- 当前版本的业务目标。
- 已有能力和本次新增能力。
- 真实输入、输出和业务契约。
- 需要学习者做出的设计选择。
- 进入项目前应具备的概念和机制，并链接回正向学习路线。
- 对应 package 和产品代码入口。
- 真实运行方式和需要观察的结果。
- 至少一个来自正常业务输入、真实依赖或正常策略取舍的 bad case / 边界现象；不为验收故意损坏实现。
- 至少一个需求变更或修改题。
- 数据流、状态流和异常流。
- 验收标准和本版本明确不做的内容。

### 不应承担

- 再讲一遍完整基础原理。
- 复制 package README。
- 复制产品安装、配置和部署手册。
- 将设计草图写成已经实现的功能。
- 为了版本看起来完整而提前建设平台能力。

### 项目版本交付链

项目篇是版本业务契约和综合验收的唯一真源。学习者可以在版本开始时先读取其中的业务场景、输入输出、Definition of Ready 和非目标，为机制实验取得固定契约；完整实现、真实 bad case / 边界题、变更题和验收仍位于一轮核心概念和机制之后：

```text
course/learning-path 定义当前标准学习路线
→ 项目篇先提供固定业务契约
→ 概念篇与机制篇建立理解并完成小实验
→ 回到同一项目篇完成组合任务和版本验收
→ source/packages 实现或扩展通用能力
→ review_assistant 组合为真实产品链路
→ tests / fixtures / eval 固化可重复验证
→ workbench 呈现输入、证据、状态、失败和人工操作
→ 运行真实模型与外部服务
→ 完成 bad case、需求变更和回归
→ 版本验收
```

每个版本必须沿用一组稳定的核心业务材料和评估样例。新增材料用于覆盖新问题，不能通过频繁更换案例掩盖回归或让前后版本失去可比较性。

项目篇定义综合实现与验收；真实 Schema、API、状态和实现以产品代码为准；通用算法以 package 为准。

### 完成标准

项目版本不仅要“跑通”，还要满足：

- 使用真实模型或真实外部服务。
- 能解释架构和数据契约选择。
- 能修改一个业务需求。
- 能制造并定位一个失败。
- 有最小评估证据。
- 能说明为什么没有使用更复杂方案。

## 8. `course/project/` 与 `review_assistant/` 的职责

这两个目录都围绕需求评审助手，但不是两份相同项目。

```text
course/project/       项目篇教材：组合任务、设计选择、真实 bad case / 边界题和版本验收
review_assistant/     产品代码真源：真正安装、运行、测试和部署的需求评审助手
```

### `course/project/` 负责

- 按阶段和 V0–V6 组织项目篇。
- 说明业务目标、学习目标和版本边界。
- 链接需要阅读的概念篇与机制篇。
- 提出设计题、修改题、真实 bad case / 边界题和验收标准。
- 指向 `source/packages/` 和 `review_assistant/` 的真实入口。

它不保存产品代码，不重复维护完整安装、配置、API 和部署说明。

### `review_assistant/` 负责

- 产品组合代码。
- FastAPI、工作台、Workflow Runtime 等真实入口。
- 产品级数据契约和 API。
- 产品测试、固定业务材料和评估数据。
- 数据库、存储、Docker 和部署配置。
- 安装、配置、运行、测试和部署 README。

它不承担概念教学，不重复项目篇中的学习目标、设计题和自检题。

### 信息真源

| 内容 | 唯一真源 |
| --- | --- |
| 为什么做、学什么、设计题、真实 bad case / 边界题、版本验收 | `course/project/` |
| 概念与机制原理 | `course/concepts/`、`course/mechanisms/` |
| 通用能力实现 | `source/packages/` |
| 机制实验和对照 | `source/demos/` |
| 学习期组合实验 | `source/apps/` |
| 产品组合代码 | `review_assistant/` |
| 产品安装、配置、运行、测试和部署 | `review_assistant/README.md` |
| 产品 API 与 Schema | 产品代码及其生成文档 |

项目篇可以引用产品 README 和代码入口，但不复制其内容。产品 README 可以标明当前实现对应的版本，但不重复课程讲解。

## 9. 文档与代码节奏

代码交付由项目版本或有必要的机制实验驱动，而不是由文档数量驱动。

### 机制正文与代码材料的分工

| 材料 | 负责回答 | 不应退化为 |
| --- | --- | --- |
| 机制正文 | 为什么这样实现、数据怎样变化、核心调用链、关键代码、不变量和失败定位 | 只有架构图和链接，或完整运行手册 |
| package README | 模块职责、完整代码阅读顺序、公共 API 和扩展边界 | 重复课程原理 |
| demo README | 运行命令、实验变量、输出解读、demo 调用路径、修改实验的方法和常见运行失败 | 第二篇机制正文 |
| 测试 | 固化不变量、格式契约、失败路径和回归证据 | 用测试通过替代机制解释 |

这些材料共同服务同一学习问题，但信息各有真源。正文可以引用 package、demo 和测试；不能因 README 已经说明“怎样运行”，就省略正文中“怎样实现、为什么这样实现”的解释。

允许：

- 概念篇没有代码。
- 多篇概念与机制共同服务一个项目版本。
- 一个机制实验被多个项目版本复用。
- 一个项目版本组合多个已有 package。
- 暂时不进入项目的知识只保留概念或机制认知。

仍然要求：

- 文档先定义问题、边界、输入输出和验收。
- 文档引用代码时必须指向真实文件。
- 不用伪代码替代应该存在的真实项目入口。
- 不批量生成大量无法运行和验证的项目正文。
- 代码完成后同步更新对应 README 和运行说明。

## 10. 代码目录与职责

```text
source/
├── packages/       # 通用能力的唯一实现
├── demos/          # 机制实验、对照和稳定失败复现
├── apps/           # 学习期能力组合与临时应用壳
└── python_base/    # 已完成的 Python 基础练习

review_assistant/   # 从阶段一开始演进的产品真源
```

### `source/packages/`

- 每个能力域全仓库只有一个 package 实例。
- 例如 `llm_core`、后续按需建立的 `rag_core`、`agent_core`、`eval_core`。
- 所有 demo、app 和产品都通过 import 复用。
- 不按课程编号或文档类型复制 package。
- package 内职责增多时按能力子目录组织，不在根目录持续堆文件。

### `source/demos/`

- 只用于观察机制、做对照实验或稳定复现失败。
- 核心算法必须进入 package。
- 相近观察复用已有 lab，不为每篇文档新建 demo。
- demo 输出要区分输入、应用诊断、模型结果和结论。

### `source/apps/`

- 用于学习期组合多个能力。
- 可以验证 SSE、简单 API 或阶段性集成。
- 不作为最终产品的平行实现。
- 能力成熟并进入产品后，由 `review_assistant/` 作为产品真源。

### `review_assistant/`

- 从阶段一开始逐步形成，不等待某个“项目课程”结束后再创建。
- import `source/packages/`，不复制核心能力。
- 只在真实版本需要时创建目录和基础设施。
- 不预建空 app、workbench、infra 或占位文件。

## 11. 真实模型与 Mock 硬规则

LLM、RAG、Agent 和 Eval 的学习主路径必须调用真实模型或真实外部服务。

### 默认行为

- 默认配置走真实调用。
- 缺少 API key 应清晰报错。
- 供应商限流、超时、鉴权失败和模型不支持应真实暴露。
- 不允许在真实调用失败后静默返回 fake 结果。
- 成本、额度、延迟和供应商差异是需要学习的工程事实。

### Mock 允许范围

fake、mock、simulation 仅允许用于：

- 单元测试。
- 离线排查。
- 稳定复现失败路径。
- 明确标注的对照实验。

使用时必须标注：

- 这是模拟结果。
- 它验证的是哪项确定性逻辑。
- 它不能代表真实模型质量。
- 如何运行对应的真实调用路径。

Mock 结果不能作为项目版本效果、模型能力或 RAG 质量的主要验收证据。

## 12. 项目运行与观察

每个真实入口都应有一条清晰主命令，并说明：

- 前置服务。
- 必需环境变量。
- 输入样例。
- 输出位置。
- 关键观察字段。
- 常见真实失败。

终端或 UI 至少能区分：

- 用户输入。
- 检索候选和最终上下文。
- 模型输出。
- Sources 与 Citation。
- Agent 或 Workflow 状态。
- 错误类型和失败节点。
- Token、成本和延迟等必要诊断。

项目默认不把运行结果写入用户目录或项目外路径。需要导出时使用显式开关，并写入被 `.gitignore` 忽略的本地输出目录。

## 13. Agent、Workflow 与 Multi-Agent 工程规则

这些规则用于保证课程最终能够落地为可控 Agent 系统，而不是只停留在概念和框架 API。

### 13.1 先选择最简单的执行结构

Workflow 与 Agent 解决不同问题，不构成固定的复杂度先后。先判断哪些部分可以由普通程序或固定 Pipeline 完成，再按运行时问题选择：

```text
规则和步骤是否固定？
├── 是：普通确定性程序或固定 Chain / RAG Pipeline
└── 否或部分不固定
    ├── 需要显式状态、分支、循环、恢复或人工节点：Workflow
    ├── 需要模型动态选择下一步、知识源或工具：单 Agent
    └── 两类问题同时存在：Workflow 管理状态与恢复，Agent 节点负责受控动态决策

只有存在不同责任、上下文、工具或可验证的并行协作收益时，才进入 Multi-Agent。
```

本项目先在 V3 使用单 Agent 解决查询改写、知识源选择和补检索，再在 V4 增加 Checkpoint、人工介入和恢复，不代表所有系统都必须先 Agent 后 Workflow。结构选择由真实问题决定，V0–V6 只描述本项目的演进顺序。

### 13.2 模型决策与应用控制分离

模型可以负责：

- 理解意图。
- 选择候选工具或知识源。
- 生成工具参数草案。
- 判断是否需要补检索、追问或继续推理。
- 生成受 Schema 约束的业务结果。

应用必须负责：

- 校验输入、Tool Schema 和业务 Schema。
- 检查权限、风险等级和人工确认条件。
- 执行工具和外部副作用。
- 保存状态、运行记录和版本信息。
- 强制最大步数、超时、预算和停止条件。
- 将工具错误转换为可判断的结构化结果。
- 决定失败如何暴露、重试、转人工或终止。

模型提出行动，不直接绕过应用控制面执行高风险操作。

### 13.3 Tool 必须是可治理契约

每个 Tool 至少定义：

- 清晰名称和单一职责。
- 输入 Schema 与字段语义。
- 输出 Schema 与错误结构。
- 参数校验。
- 超时、重试和取消边界。
- 是否存在副作用。
- 幂等键或重复执行策略。
- 权限和人工确认条件。
- 执行日志和来源追踪。

Retriever as Tool 也遵守同样规则，必须能看到查询、知识源、过滤条件、候选结果和失败原因。

### 13.4 Agent Loop 必须显式终止

Agent 运行状态至少能表达：

- 原始任务和当前目标。
- 当前上下文与证据。
- 已调用工具及结果。
- 当前步骤和累计成本。
- 待补充信息。
- 当前状态和最终停止原因。

停止原因不能只表现为“没有继续生成”，应区分：

- 正常完成。
- 需要用户补充。
- 等待人工确认。
- 达到步数、时间或预算上限。
- 工具或模型失败。
- 安全策略阻止。

#### Memory 与业务知识必须分开

- Run State 保存当前运行步骤、工具结果和停止原因。
- Conversation 保存当前会话消息。
- 短期记忆负责当前会话窗口、摘要和预算。
- 长期记忆只保存用户明确确认且跨会话仍有效的偏好或约束，必须记录作用域、来源，并支持更新、删除和关闭。
- PRD、接口规则、客户端规则和历史评审等业务事实进入可引用知识系统，不能由长期记忆替代。
- 模型未经用户确认的推断和 Agent 中间结论不能自动成为长期记忆，也不能冒充 Citation。

### 13.5 Workflow 必须可恢复

Workflow 进入项目时必须明确：

- State Schema。
- 每个节点的输入和输出。
- 分支条件和循环上限。
- Checkpoint 时机。
- 中断前保存什么。
- 恢复时从哪里继续。
- 有副作用节点如何保证幂等。
- 节点失败是重试、跳过、回退还是转人工。

不能只画节点图而没有运行状态和恢复语义。

### 13.6 Multi-Agent 必须建立在基线上

每个 Agent 必须具有可说明的独立责任、上下文、工具或输出契约。

系统必须明确：

- 共享状态和私有上下文分别是什么。
- 任务如何分配和调度。
- 证据如何合并。
- 意见冲突如何表达和裁决。
- 最终结果由谁负责。
- 单个 Agent 失败如何隔离和恢复。

进入 Multi-Agent 前保留单 Agent 基线，至少比较质量、成本、延迟、证据一致性和失败定位难度。

### 13.7 Agent 运行必须可观察和可评估

每次关键运行至少关联：

- `run_id` / `trace_id`。
- 模型、Prompt、Retriever、Tool 和 Workflow 版本。
- 输入、关键状态变化和停止原因。
- 检索结果、Tool Call 和节点轨迹。
- Token、成本、延迟和错误。
- 最终业务结果和人工反馈。

评估不仅检查最终文本，还要按阶段检查：

- 查询改写和知识源选择。
- 检索质量和证据覆盖。
- Tool 参数与执行结果。
- Agent 轨迹和停止判断。
- Workflow 路径和人工节点。
- Multi-Agent 分工、汇总和冲突处理。

### 13.8 安全与人工确认

- 工具默认最小权限。
- 读取和写入能力分开授权。
- 高风险、副作用或不可逆操作进入人工确认。
- Prompt 内容不能绕过 Tool Runtime 权限。
- 敏感输入、工具结果和日志按需要脱敏。
- 失败和拒绝必须对用户可见，不能伪装成功。

## 14. Python 与依赖管理

全仓库使用根目录一个 uv 环境和一个依赖真源：

- `pyproject.toml`：依赖和 editable package 配置。
- `uv.lock`：精确版本锁定。
- `.venv/`：由 `uv sync` 生成，不提交。

常用命令：

```bash
uv sync
uv add package-name
uv add --dev package-name
uv remove package-name
uv run ...
```

要求：

- 不在每个 package、demo、app 或产品目录维护独立 Python 依赖文件。
- API key、模型配置和数据库连接使用 `.env` / `.env.example`。
- 不手写 `PYTHONPATH` 维持平行包。
- 可选依赖等真实能力落地时再加入。

## 15. 学习完成与代码所有权

一个项目版本完成后，学习者至少应能够：

- 解释真实问题和设计选择。
- 画出数据流、状态流和异常流。
- 指出模型、检索、上下文、工具和 UI 的边界。
- 修改一个字段、策略、工具、节点或业务规则。
- 主动构造一个失败并定位。
- 使用评估或测试证明修改没有破坏主链路。
- 判断下一步应该保持简单还是增加复杂度。

更完整的 AI Coding 掌握标准见 [ai-coding-mastery.md](ai-coding-mastery.md)。

## 16. 禁止行为

- 建立 V0–V6 之外的第二套项目编号。
- 把能力目录重新变成必须线性学完的课程。
- 将知识项与文档、demo 强制一一对应。
- 为每篇文档创建一次 package 增量。
- 为文档类型建立平行代码实现。
- 用 Mock 结果冒充真实模型表现。
- 在调用失败时静默降级。
- 提前建设通用 Agent 平台、知识平台或低代码画布。
- 让远期平台能力成为当前版本验收项。
- 长期保留旧路径和新路径两个真源。
- 在长期文档记录迁移过程和实时学习进度。
- 主动依赖或扩展 `archive/`。
- 无真实需求时预建空目录、空 package、空 demo 或 `.gitkeep`。

## 17. 文档维护原则

- 长期目标只写入 `strategy.md`。
- 学习与工程规范只写入本文。
- 代码掌握标准只写入 `ai-coding-mastery.md`。

当多个文档出现重复规则时，应保留唯一真源，其他位置改为链接。
