# AI 应用课程学习与工程指南

这份文档是本仓库学习方式、课程组织、文档规范、代码组织和运行规则的唯一真源。

长期目标与项目阶段以 [strategy.md](strategy.md) 为准；AI Coding 掌握标准以 [ai-coding-mastery.md](ai-coding-mastery.md) 为准。

## 1. 核心学习方式

课程不再以“先学完一门能力课，再开始做项目”为主路径，而是由需求评审助手的项目版本反推需要学习的知识。

基本链路是：

```text
项目版本提出真实问题
→ 判断缺少哪些概念和机制
→ 阅读必要的概念篇与机制篇
→ 通过实验观察内部过程
→ 将能力组合进项目
→ 调用真实模型和真实外部服务
→ 主动制造失败并定位
→ 用评估证明改动
→ 完成版本验收
```

下面这条认知链仍然适用于整个课程：

```text
真实问题
→ 基础原理
→ 最小实现
→ 主流框架实现
→ 失败分析与能力边界
```

但它是一种思考顺序，不是每篇文档必须照抄的固定标题模板。不同类型文档承担不同职责。

## 2. 学习组织：两个阶段、一个版本轴、三类文档

### 两个阶段

- 阶段一：可信 RAG + 单 Agent 需求评审助手。
- 阶段二：Workflow + 多 Agent 评审系统。

### 唯一强顺序

V0–V6 是唯一项目里程碑和唯一强学习顺序。版本定义以 [strategy.md](strategy.md) 为准。

不再建立这些平行顺序：

- 不维护 M0–M6。
- 不把 LLM、RAG、Agent、Eval 当作必须依次毕业的课程。
- 不为“概念单元”再维护一套编号课表。
- 不根据文件名编号推断全局学习顺序。

### 三类文档

课程正文只分为：

1. 概念篇。
2. 机制篇。
3. 项目篇。

三分的是职责，不是篇幅。概念篇和机制篇可以很长、很厚，但必须围绕自己的核心问题展开。

## 3. 唯一阅读入口和阅读路径

重构后的课程以 `course/README.md` 为唯一阅读入口。

标准阅读路径：

```text
course/README.md
→ 当前项目版本的项目篇
→ 项目篇列出的概念篇和机制篇
→ 对应 package README
→ 运行真实代码入口
→ 观察输入、输出、证据、状态和错误
→ 完成 bad case、修改题与版本验收
```

阅读顺序跟项目走，不跟目录走：

- 不要求先读完 `concepts/`。
- 不要求先读完某个能力域下的全部机制。
- 不要求学完所有 LLM 内容才进入 RAG。
- 与项目暂时关系不大的重要知识，可以作为概念或机制补充，但不进入当前项目验收。

## 4. 集中知识清单

`course/knowledge-map.md` 是课程知识清单的唯一真源，用来回答“有哪些能力、重要到什么程度、在哪里学习”，不负责规定项目阅读顺序。

每个知识项至少记录：

| 字段 | 含义 |
| --- | --- |
| 能力名称 | 需要掌握或认知的知识 |
| 能力域 | LLM、RAG、Agent、Workflow、Eval、AI Native、工程基础等 |
| 文档类型 | 概念、机制或项目 |
| 项目阶段 | 阶段一、阶段二或未来认知 |
| 优先级 | 主线、支撑或未来认知 |
| 前置知识 | 理解它之前真正需要什么 |
| 文档入口 | 对应概念篇、机制篇或项目篇 |
| 代码入口 | package、demo、app 或产品路径 |
| 状态 | 未规划、已规划、已落地、需修订等 |

知识项与文档不一一对应：

- 一篇文档可以讲清多个紧密相关的知识项。
- 一个知识项可以在概念篇、机制篇和项目篇中从不同角度出现。
- 一个项目版本可以同时使用 LLM、RAG、Agent 和 Eval 能力。
- 不为了让知识清单“整齐”而创建空文档、空目录或空代码。

各能力域可以保留标签和分组价值，但不再各自维护分散的 outline 真源。

## 5. 概念篇规范

概念篇回答：

> 这个概念是什么，为什么需要它，边界在哪里？

### 必须讲清

- 它解决什么问题。
- 一句话定义。
- 输入、处理和输出。
- 最小心智模型或数据流。
- 与相近概念的区别。
- 一个能够暴露误解的反例。
- 能解决什么、不能解决什么。
- 在需求评审助手中的位置。
- 当前属于主线、支撑还是未来认知。

### 可以采用

- 真实场景叙事。
- 数据流图。
- 对比表。
- 小型示例。
- 常见误区。
- 判断题或自检题。

### 不应承担

- 大段 package 文件树。
- 完整运行参数手册。
- 项目版本的详细任务清单。
- 为了“有代码”而新增实现。
- 在概念尚未建立前直接从框架 API 开始。

概念篇通常可以没有代码。若引用代码或运行结果，必须指向真实入口并说明它只是用于观察什么。

### 完成标准

读者能够用自己的话解释概念、区分相近概念、判断适用边界，并说明它是否是当前项目真正需要的能力。

## 6. 机制篇规范

机制篇回答：

> 这个机制为什么有效，数据在内部如何变化，失败时如何定位？

### 必须讲清

- 现有简单方案的问题。
- 新机制解决了什么。
- 输入输出发生了什么变化。
- 内部数据流、关键约束和不变量。
- 从简单方案到工程方案的递进。
- 可以观察机制的最小实验。
- 至少一个失败案例及定位顺序。
- 主流框架封装了什么、没有解决什么。
- 对应 package、demo 或外部服务的边界。

### 可以对应代码

机制篇可以：

- 扩展已有 package。
- 复用已有 demo。
- 建立必要的新实验。
- 只解释已有真实代码。
- 在没有必要实现时只做机制认知。

机制篇不强制每篇都增加 package，也不要求每个机制单独建立 demo。

### 框架使用原则

- 先解释原生机制，再解释框架抽象。
- 使用 LangChain、LangGraph 等框架时，要说明为什么当前问题值得引入。
- 框架实现不能代替基础原理。
- 框架没有解决的错误、状态、权限和评估问题必须显式说明。
- 项目暂时不需要时，不为了覆盖“主流框架”强行增加依赖。

### 完成标准

读者能够画出数据流，预测关键输入变化的影响，运行或解释最小实验，并根据失败现象找到优先排查的位置。

## 7. 项目篇规范

项目篇回答：

> 当前版本为什么要增加这项能力，怎样组合已有知识完成一个可验收的业务结果？

### 必须讲清

- 当前版本的业务目标。
- 已有能力和本次新增能力。
- 真实输入、输出和业务契约。
- 需要学习者做出的设计选择。
- 必须阅读的概念篇和机制篇。
- 对应 package 和产品代码入口。
- 真实运行方式和需要观察的结果。
- 至少一个需要主动制造的失败。
- 至少一个需求变更或修改题。
- 数据流、状态流和异常流。
- 验收标准和本版本明确不做的内容。

### 不应承担

- 再讲一遍完整基础原理。
- 复制 package README。
- 复制产品安装、配置和部署手册。
- 将设计草图写成已经实现的功能。
- 为了版本看起来完整而提前建设平台能力。

### 完成标准

项目版本不仅要“跑通”，还要满足：

- 使用真实模型或真实外部服务。
- 能解释架构和数据契约选择。
- 能修改一个业务需求。
- 能制造并定位一个失败。
- 有最小评估证据。
- 能说明为什么没有使用更复杂方案。

## 8. `course/project/` 与 `review_assistant/` 的职责

这两个目录都围绕需求评审助手，但不是两份相同项目。

```text
course/project/       项目篇教材：教为什么做、学什么、怎样判断和验收
review_assistant/     产品代码真源：真正安装、运行、测试和部署的需求评审助手
```

### `course/project/` 负责

- 按阶段和 V0–V6 组织项目篇。
- 说明业务目标、学习目标和版本边界。
- 链接需要阅读的概念篇与机制篇。
- 提出设计题、修改题、失败题和验收标准。
- 指向 `source/packages/` 和 `review_assistant/` 的真实入口。

它不保存产品代码，不重复维护完整安装、配置、API 和部署说明。

### `review_assistant/` 负责

- 产品组合代码。
- FastAPI、工作台、Workflow Runtime 等真实入口。
- 产品级数据契约和 API。
- 产品测试、固定业务材料和评估数据。
- 数据库、存储、Docker 和部署配置。
- 安装、配置、运行、测试和部署 README。

它不承担概念教学，不重复项目篇中的学习目标、设计题和自检题。

### 信息真源

| 内容 | 唯一真源 |
| --- | --- |
| 为什么做、学什么、设计题、失败题、版本验收 | `course/project/` |
| 概念与机制原理 | `course/concepts/`、`course/mechanisms/` |
| 通用能力实现 | `source/packages/` |
| 机制实验和对照 | `source/demos/` |
| 学习期组合实验 | `source/apps/` |
| 产品组合代码 | `review_assistant/` |
| 产品安装、配置、运行、测试和部署 | `review_assistant/README.md` |
| 产品 API 与 Schema | 产品代码及其生成文档 |

项目篇可以引用产品 README 和代码入口，但不复制其内容。产品 README 可以标明当前实现对应的版本，但不重复课程讲解。

## 9. 文档与代码节奏

代码交付由项目版本或有必要的机制实验驱动，而不是由文档数量驱动。

允许：

- 概念篇没有代码。
- 多篇概念与机制共同服务一个项目版本。
- 一个机制实验被多个项目版本复用。
- 一个项目版本组合多个已有 package。
- 暂时不进入项目的知识只保留概念或机制认知。

仍然要求：

- 文档先定义问题、边界、输入输出和验收。
- 文档引用代码时必须指向真实文件。
- 不用伪代码替代应该存在的真实项目入口。
- 不批量生成大量无法运行和验证的项目正文。
- 代码完成后同步更新对应 README 和运行说明。

## 10. 代码目录与职责

```text
source/
├── packages/       # 通用能力的唯一实现
├── demos/          # 机制实验、对照和稳定失败复现
├── apps/           # 学习期能力组合与临时应用壳
└── python_base/    # 已完成的 Python 基础练习

review_assistant/   # 从阶段一开始演进的产品真源
```

### `source/packages/`

- 每个能力域全仓库只有一个 package 实例。
- 例如 `llm_core`、后续按需建立的 `rag_core`、`agent_core`、`eval_core`。
- 所有 demo、app 和产品都通过 import 复用。
- 不按课程编号或文档类型复制 package。
- package 内职责增多时按能力子目录组织，不在根目录持续堆文件。

### `source/demos/`

- 只用于观察机制、做对照实验或稳定复现失败。
- 核心算法必须进入 package。
- 相近观察复用已有 lab，不为每篇文档新建 demo。
- demo 输出要区分输入、应用诊断、模型结果和结论。

### `source/apps/`

- 用于学习期组合多个能力。
- 可以验证 SSE、简单 API 或阶段性集成。
- 不作为最终产品的平行实现。
- 能力成熟并进入产品后，由 `review_assistant/` 作为产品真源。

### `review_assistant/`

- 从阶段一开始逐步形成，不等待某个“项目课程”结束后再创建。
- import `source/packages/`，不复制核心能力。
- 只在真实版本需要时创建目录和基础设施。
- 不预建空 app、workbench、infra 或占位文件。

## 11. 真实模型与 Mock 硬规则

LLM、RAG、Agent 和 Eval 的学习主路径必须调用真实模型或真实外部服务。

### 默认行为

- 默认配置走真实调用。
- 缺少 API key 应清晰报错。
- 供应商限流、超时、鉴权失败和模型不支持应真实暴露。
- 不允许在真实调用失败后静默返回 fake 结果。
- 成本、额度、延迟和供应商差异是需要学习的工程事实。

### Mock 允许范围

fake、mock、simulation 仅允许用于：

- 单元测试。
- 离线排查。
- 稳定复现失败路径。
- 明确标注的对照实验。

使用时必须标注：

- 这是模拟结果。
- 它验证的是哪项确定性逻辑。
- 它不能代表真实模型质量。
- 如何运行对应的真实调用路径。

Mock 结果不能作为项目版本效果、模型能力或 RAG 质量的主要验收证据。

## 12. 项目运行与观察

每个真实入口都应有一条清晰主命令，并说明：

- 前置服务。
- 必需环境变量。
- 输入样例。
- 输出位置。
- 关键观察字段。
- 常见真实失败。

终端或 UI 至少能区分：

- 用户输入。
- 检索候选和最终上下文。
- 模型输出。
- Sources 与 Citation。
- Agent 或 Workflow 状态。
- 错误类型和失败节点。
- Token、成本和延迟等必要诊断。

项目默认不把运行结果写入用户目录或项目外路径。需要导出时使用显式开关，并写入被 `.gitignore` 忽略的本地输出目录。

## 13. Python 与依赖管理

全仓库使用根目录一个 uv 环境和一个依赖真源：

- `pyproject.toml`：依赖和 editable package 配置。
- `uv.lock`：精确版本锁定。
- `.venv/`：由 `uv sync` 生成，不提交。

常用命令：

```bash
uv sync
uv add package-name
uv add --dev package-name
uv remove package-name
uv run ...
```

要求：

- 不在每个 package、demo、app 或产品目录维护独立 Python 依赖文件。
- API key、模型配置和数据库连接使用 `.env` / `.env.example`。
- 不手写 `PYTHONPATH` 维持平行包。
- 可选依赖等真实能力落地时再加入。

## 14. 学习完成与代码所有权

一个项目版本完成后，学习者至少应能够：

- 解释真实问题和设计选择。
- 画出数据流、状态流和异常流。
- 指出模型、检索、上下文、工具和 UI 的边界。
- 修改一个字段、策略、工具、节点或业务规则。
- 主动构造一个失败并定位。
- 使用评估或测试证明修改没有破坏主链路。
- 判断下一步应该保持简单还是增加复杂度。

更完整的 AI Coding 掌握标准见 [ai-coding-mastery.md](ai-coding-mastery.md)。

## 15. 禁止行为

- 建立 V0–V6 之外的第二套项目编号。
- 把能力目录重新变成必须线性学完的课程。
- 将知识项与文档、demo 强制一一对应。
- 为每篇文档创建一次 package 增量。
- 为文档类型建立平行代码实现。
- 用 Mock 结果冒充真实模型表现。
- 在调用失败时静默降级。
- 提前建设通用 Agent 平台、知识平台或低代码画布。
- 让远期平台能力成为当前版本验收项。
- 长期保留旧路径和新路径两个真源。
- 在长期文档记录迁移过程和实时学习进度。
- 主动依赖或扩展 `archive/`。
- 无真实需求时预建空目录、空 package、空 demo 或 `.gitkeep`。

## 16. 文档维护原则

- 长期目标只写入 `strategy.md`。
- 学习与工程规范只写入本文。
- 代码掌握标准只写入 `ai-coding-mastery.md`。
- 企业平台远期能力只写入 `ai-application-platform.md`。
- AI Agent 执行路由只写入 `agent-skill.md`。
- 课程正文、知识清单和项目版本任务留在 `course/`。
- 产品运行与部署说明留在 `review_assistant/`。

当多个文档出现重复规则时，应保留唯一真源，其他位置改为链接。
