# AI 应用课程学习与工程指南

本文是课程组织、文档职责、代码关系和学习验收的规范真源。长期目标见 [strategy.md](strategy.md)，产品要求见 [SPEC.md](../SPEC.md)，工程实现边界见 [PLAN.md](../PLAN.md)。

## 1. 学习方式

课程设计从需求评审助手的产品目标反推知识，学习者按认知前置正向学习：

```text
项目愿景与阶段目标
→ 概念建立局部心智模型
→ 机制解释数据或状态变化
→ 实验运行真实代码并观察
→ 项目篇组合能力
→ 测试、评估和需求修改
```

产品反推决定“学什么”，学习前置决定“先学什么”。课程只有第一阶段、第二阶段和一套连续编号；阶段内部只使用无编号的学习单元。

`course/learning-path.md` 是阅读顺序和课程序号的唯一真源。目录、知识地图、正文页尾、文件名和工程计划都不能形成第二套课表。

## 2. 四类课程文档

### 概念篇

回答“是什么、为什么需要、与相近概念有什么区别、边界在哪里”。它可以引导一个阶段、学习单元或独立概念。

概念篇重点建立问题、最小心智模型、输入输出、相近概念和适用边界，默认不讲实现代码。学习单元完成后可以修订概念篇或增加“学完后回看”，但不能把后续全部机制和项目细节倒灌为总复习文档。

### 机制篇

回答“为什么有效、数据或状态怎样变化、关键约束是什么、边界在哪里”。机制篇是课程核心正文。

机制篇应围绕一个大问题中的一个局部问题，讲清当前输入、主要变化、一个关键约束、简单方案的不足和正常边界。机制篇不承担源代码、文件树、命令、安装、完整日志字段、源码调用链和代码修改步骤。公式、数据流、状态图、输入输出样例和帮助理解机制的最小抽象结构不视为源码讲解；只有不可替代时才保留极少量关键语法片段，并立即回到机制解释。新术语在第一次需要时仍必须用自然语言解释。

### 实验篇

回答“代码怎样准备和运行、改变什么、观察什么、失败时怎样定位”。正文位于 `course/labs/`，真实代码位于 `source/demos/` 或阶段产品。

实验篇负责环境与真实依赖、入口与命令、运行前预测、单一主要变量、日志与诊断、失败区分、调试顺序、读码入口、修改题和测试。实验篇引用机制篇，不重复完整原理。主线机制通常配有实验，但不强制文档与 demo 一一对应。

### 项目篇

回答“怎样把已学能力组合成可验收产品结果”。项目篇位于 `course/project/`，引用根 [SPEC.md](../SPEC.md) 的产品要求，负责学习目标、设计题、集成检查点、需求变更、bad case 和阶段验收。

项目篇不是产品规格或运行手册。产品安装、API、运行和部署由 `source/apps/review_assistant/README.md` 维护。

## 3. 一节课的粒度

一个编号只承载一个核心学习问题，可以同时链接一篇机制正文和一篇配套实验。

出现以下情况时优先拆分：

- 同时存在两个独立生命周期。
- 同时改变两个主要数据或状态对象。
- 需要两套不同的实验变量或失败模型。
- 协议原理、真实接入和项目职责被放进同一正文。
- 标题列出多个并列主题，但无法用一条数据流连接。

概览型概念篇可以展示多个对象，但只负责建立关系，不在一节中讲完每个对象的机制。正文不写死“上一节、下一节”，只说明知识输入、本文交付和复用方向。

## 4. 三个课程真源

- `course/learning-path.md`：现在读什么，以及唯一编号。
- `course/knowledge-map.md`：有哪些能力、前置、定位和学习入口，不安排顺序。
- `course/project/`：怎样把知识组合成阶段综合实践，不复制产品 Spec。

知识地图不维护课程序号，不要求知识项与正文一一对应。产品必需能力由 `SPEC.md` 定义；学习主线不自动等于产品默认接入。

## 5. 代码与文档关系

```text
course/concepts/               概念
course/mechanisms/             机制
course/labs/                   实验教材
course/project/                综合实践教材
source/packages/               通用能力唯一实现
source/demos/                  实验代码
source/apps/review_assistant/  唯一产品
```

每个能力域只维护一个 package。demo 不复制核心算法，产品通过 import 组合 package。没有新的观察维度、通用能力或产品任务时，不为文档创建代码。

README 分工：package README 维护模块职责和公共 API；demo README 维护代码入口、测试和实验篇链接；product README 维护安装、配置、启动、测试、API 和部署；course 文档负责学习解释、实验指导和项目判断。

## 6. 产品与 SDD

- `SPEC.md` 是产品“做什么”的唯一稳定规格。
- `PLAN.md` 是 `source/` 怎样实现 Spec 的稳定工程分解，不记录实时进度。
- 项目篇引用 Spec 开展学习和验收。
- 产品代码、Schema、OpenAPI、状态模型和测试是精确执行真源。
- 学习路径只规定认知顺序，不承担工程进度管理。

规格变化先判断是否改变产品输入输出、责任边界、状态、安全或验收；只有真正改变时才更新 SPEC。临时实现步骤不写入长期规范。

## 7. 真实调用与实验

LLM、RAG、Agent 和 Eval 主路径使用真实模型或真实外部服务。缺少 Key、鉴权失败、限流、超时和能力不支持必须清晰暴露，不静默返回 Mock、假向量、内存检索或静态成功结果。

Mock 只用于单元测试、离线排查、稳定复现确定性失败或明确对照，并说明它不能证明真实质量。

实验遵守：先预测再运行；一次只改变一个主要变量；复用稳定业务材料；区分探索与验收；支撑准入或验收时预先固定样例、配置、对照、指标和预算；运行后不通过删除失败样例或回改阈值制造通过。

## 8. Agent、Tool、Workflow 与 Multi-Agent 边界

先选择最简单结构：固定步骤使用普通程序或固定 Pipeline；模型需要动态选择下一步时使用 Agent；需要显式状态、恢复或人工节点时使用 Workflow；只有存在独立责任、上下文、工具或可验证协作收益时才使用 Multi-Agent。

模型可以理解任务、提出工具和生成参数草案；应用必须负责 Schema 校验、权限、执行、副作用、状态、预算、停止、错误和人工确认。

每个 Tool 必须有单一职责、输入输出契约、结构化错误、超时取消、权限和审计。MCP 只标准化连接与能力交换，不替代 Tool Runtime。Agent Skills 封装说明、资源和脚本，不冒充具有副作用的 Tool。

Agent 必须显式表达状态和停止原因。Conversation、短期记忆、长期偏好与可引用业务知识不能混用。Multi-Agent 必须保留单 Agent 基线并比较质量、成本、延迟、证据一致性和失败定位。

Workflow 进入产品时必须明确状态、节点输入输出、分支循环、Checkpoint、恢复、人工介入和副作用幂等，不建设无业务需求的低代码画布。

## 9. 学习完成

学习者应能够解释概念和边界，画出机制的数据或状态流，独立运行实验、阅读日志、定位失败并修改一个变量，将能力组合进产品并修改一个业务需求，使用测试、评估或 trace 证明结果，并判断何时保持简单或增加复杂度。

更完整的代码所有权标准见 [ai-coding-mastery.md](ai-coding-mastery.md)。

## 10. 维护边界

- 长期目标只写入 `strategy.md`。
- 产品要求只写入 `SPEC.md`。
- 工程实现边界只写入 `PLAN.md`。
- 学习与文档规则只写入本文。
- 写作执行流程只写入 `skills/course-writing/SKILL.md`。
- 产品运行事实只写入 `source/apps/review_assistant/README.md`。
- 不在长期文档记录迁移过程、实时进度或临时讨论。
- 不依赖 `archive/` 作为当前主线。
