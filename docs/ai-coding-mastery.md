# AI Coding 学习、掌握与代码所有权

这份文档是本仓库在 AI Coding 参与下判断“是否真正掌握”的唯一真源。

学习方式、文档类型和代码组织以 [learning-guide.md](learning-guide.md) 为准。本文不判断代码由谁敲出，只判断谁能够对系统负责。

## 1. 核心判断

AI 生成代码不等于没有学习，也不等于已经掌握。

真正的分界线是：

> 谁能对系统目标、结构、数据、状态、失败、评估、取舍和后续修改负责。

如果代码主要由 AI 生成，但学习者能解释、验证、修改、调试和迁移，仍然是真正掌握。

如果只知道“项目跑起来了”，却不知道为什么这样设计、为什么会错、需求变化后改哪里，就还没有建立代码所有权。

## 2. 为什么需要单独定义掌握标准

AI Coding 能显著加快项目闭环，但也会带来几种掌握幻觉：

- 接受 AI 给出的第一个架构，没有比较更简单的方案。
- 代码运行成功，却没有检查真实输出质量。
- 只会继续让 AI 修错，不会自己缩小问题范围。
- 能解释类名和函数名，不能解释数据为什么这样流动。
- 使用 Mock 跑通测试，却没有处理真实模型的不确定性。
- 项目需求变化后，不知道应该改 Prompt、Retriever、Agent 还是 UI。
- Multi-Agent 看起来复杂，却说不清每个 Agent 为什么存在。

因此，本仓库以机制实验、项目版本和重要能力变更作为掌握验收单位，不以文档数量、代码行数或提交次数判断学习进度。

## 3. 三层掌握标准

### 3.1 概念掌握

能够：

- 用自己的话解释概念。
- 说明输入、处理和输出。
- 区分相近概念。
- 给出一个反例或不适用场景。
- 判断它是当前项目主线、支撑能力还是未来认知。
- 说明为什么当前版本需要或不需要它。

概念掌握不要求一定有代码。

### 3.2 机制掌握

能够：

- 画出机制的数据流。
- 说明关键约束和不变量。
- 预测关键输入或配置变化会带来什么结果。
- 解释框架封装了什么。
- 运行或解释最小实验。
- 主动制造一个失败。
- 根据现象确定优先排查位置。
- 判断失败来自应用逻辑、外部服务还是模型不确定性。

### 3.3 项目掌握

能够：

- 解释当前版本的业务目标和非目标。
- 说明架构与数据契约选择。
- 解释数据流、状态流和异常流。
- 修改一个真实业务需求。
- 判断应该修改数据、Prompt、Schema、Retriever、Tool、Agent、Workflow 还是 UI。
- 使用测试、评估或 trace 证明修改结果。
- 说明为什么没有继续增加复杂度。
- 将相同方法迁移到另一个业务场景。

## 4. 六项代码所有权能力

### 能解释

- 模块解决什么真实问题。
- 输入和输出是什么。
- 核心状态由谁维护。
- 确定性逻辑和模型判断分别在哪里。
- 为什么使用当前方案。

### 能验证

- 真实模型是否被调用。
- 关键输入输出是否符合契约。
- RAG 是否命中正确来源。
- Citation 是否真的能回到证据。
- Agent 是否选择了正确工具或知识源。
- Workflow 是否走过预期节点。
- 修改前后质量是否有证据支持。

### 能修改

- 增加或删除一个业务字段。
- 调整 Prompt 或结构化 Schema。
- 替换 Retriever 或检索策略。
- 增加工具、节点、状态或人工审核点。
- 修改前端对事件和状态的呈现。
- 同步更新必要的测试和评估样本。

### 能调试

能够区分问题来自：

- 文档解析、Chunk 或 Metadata。
- Embedding、关键词检索、向量检索或 Rerank。
- Context Construction。
- Prompt、模型或 Structured Output。
- Tool Schema、Tool Runtime 或权限。
- Agent 决策或 Workflow State。
- SSE、API 或前端状态同步。
- 供应商鉴权、限流、超时和模型能力差异。

### 能迁移

能将问题判断、系统分层、评估方法和调试路径迁移到：

- 客服知识助手。
- 合同审查。
- 内部知识库。
- 测试用例生成。
- 研发提效工具。

迁移不是复制代码，而是重新判断场景需要 LLM、RAG、Workflow、单 Agent 还是多 Agent。

### 能取舍

能够判断：

- 什么时候普通程序更合适。
- 什么时候直接 LLM 足够。
- 什么时候固定 RAG 足够。
- 什么时候需要单 Agent。
- 什么时候必须使用 Workflow。
- 什么时候 Multi-Agent 的收益大于成本。
- 什么时候需要 Human-in-the-loop。
- 什么时候平台化过早。

## 5. AI Coding 下的推荐工作流

```text
先理解业务问题
→ 明确输入、输出和完成标准
→ 设计最小结构
→ 让 AI 辅助实现
→ 审查关键数据和状态
→ 运行真实链路
→ 主动制造失败
→ 定位和修复
→ 修改一个需求
→ 用评估或测试回归
→ 用自己的话解释取舍
```

AI 可以加速：

- 代码生成。
- 测试样例。
- 重构和静态检查。
- 文档草稿。
- 日志分析。
- 多方案比较。

AI 不能替代学习者承担：

- 业务目标。
- 项目范围。
- 架构取舍。
- 数据和权限边界。
- 验收结论。
- 是否值得增加复杂度。

## 6. 真实模型环境下的掌握

本仓库的主路径使用真实模型和真实外部服务。掌握真实 AI 应用还要求能够：

- 区分代码错误和供应商错误。
- 识别鉴权、限流、超时、网络和模型能力问题。
- 理解同一输入可能得到不同输出。
- 使用 Schema、校验、Refusal 和评估约束不确定性。
- 记录模型、Prompt、Context、Token、成本和延迟。
- 不用 Mock 结果证明模型质量。

Mock 只证明被模拟的确定性逻辑是否符合预期，不能证明真实模型效果、检索质量或 Agent 决策质量。

## 7. RAG 掌握检查

学习者应能够回答：

- 资料如何从文件变成可检索知识？
- Chunk、Metadata、Embedding 和索引分别解决什么问题？
- 为什么关键词检索和向量检索会命中不同内容？
- 如何区分召回失败和生成失败？
- Citation 如何与真实来源建立关系？
- 证据不足时为什么应该拒答或追问？
- 如何构造 Golden Set 和 bad case？
- 修改 Chunk、Retriever 或 Prompt 后如何证明变好？

## 8. Agent 与 Workflow 掌握检查

学习者应能够回答：

- 为什么这里需要 Agent，而不是固定 RAG？
- 模型负责决定什么，应用负责执行和校验什么？
- Tool Schema、Tool Runtime、Agent Loop 和 Workflow State 有何区别？
- Agent 什么时候继续、停止、追问或转人工？
- Workflow 为什么在这个节点中断？
- 中断后需要保存哪些状态才能恢复？
- 一次错误结果来自检索、工具、模型决策还是状态设计？

## 9. Multi-Agent 掌握检查

多 Agent 是第二阶段目标，但必须建立在单 Agent 基线上。

每个 Agent 都需要回答：

- 它拥有哪项独立责任？
- 它是否需要不同知识、上下文或工具？
- 输入和输出契约是什么？
- 与其他 Agent 如何共享状态和证据？
- 谁负责汇总和最终裁决？
- 意见冲突如何处理？
- 失败是否能定位到具体角色和步骤？

系统层还必须比较：

- 单 Agent 与多 Agent 的任务完成质量。
- Token 成本和总延迟。
- 调试和失败定位难度。
- 证据一致性。
- 是否真的获得可测量收益。

如果无法回答这些问题，多 Agent 很可能只是多个 Prompt 的包装。

## 10. 每个项目版本的所有权验收

版本完成后，至少选择一组问题进行现场验证：

- 不看 AI 解释，我能否画出主链路？
- 我能否指出三个最可能失败的位置？
- 我能否让系统稳定复现其中一个失败？
- 我能否增加一个字段、策略、工具、节点或人工审核点？
- 我能否说明需要补哪些测试或评估样本？
- 我能否解释真实模型失败时系统如何表现？
- 我能否证明修改后的质量没有退化？
- 我能否解释为什么当前版本没有采用更复杂架构？

只有项目能运行、结果可验证、失败可定位、需求可修改，才算真正建立代码所有权。

## 11. 面向真实工作的迁移

真实业务通常存在：

- 需求持续变化。
- 数据不完整或质量不稳定。
- 老系统和权限边界复杂。
- 模型输出不稳定。
- 成本、延迟和合规约束。
- 架构历史包袱。

课程最终训练的不是记住一个理想架构，而是：

- 判断问题类型。
- 设计可演进边界。
- 使用 AI 加速实现。
- 使用评估证明质量。
- 使用 trace 定位失败。
- 在约束下作出取舍。
- 在需求变化时知道应该改哪里。
