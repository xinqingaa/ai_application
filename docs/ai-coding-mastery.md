# AI Coding 掌握标准

本文定义“代码由 AI 生成或协助时，学习者怎样证明自己真正掌握”。它不规定课程顺序、文档模板或产品需求。

## 掌握不是逐行背诵

学习者不必手写所有样板代码，但必须能够：

- 说明输入、输出、状态、错误和外部依赖。
- 画出关键数据流或状态流。
- 找到业务边界和失败边界的所有者。
- 独立运行、观察、调试并修改一个真实需求。
- 用测试、实验、评估或 Trace 证明修改没有破坏契约。
- 判断 AI 建议何时过度设计、越权或静默掩盖失败。

## 四层掌握

### 概念

能够用自己的话解释“是什么、为什么需要、与相邻概念怎样区分、何时不该使用”。只会复述名词不算掌握。

### 机制

能够从输入沿数据或状态变化解释到输出，说明关键约束、简单方案的不足和正常失败边界。机制理解不要求逐行讲源码。

### 实验

能够独立准备真实依赖、运行入口、阅读日志、区分配置错误与机制边界、完成单变量对照，并从实验入口定位到关键实现和测试。

### 项目

能够把能力组合进唯一产品，解释为何属于 package 或 app，修改一个业务需求，处理 bad case，并用验收证据说明完成程度。

## 代码所有权检查

对自己声称掌握的模块，应能回答：

1. 谁调用它，它又调用谁？
2. 哪些对象是稳定契约，哪些只是实现细节？
3. 哪些配置或身份变化会让旧数据、缓存或结果失效？
4. 失败在哪一层产生，怎样向上暴露？
5. 哪些行为需要真实服务验证，哪些可由确定性测试守住？
6. 需求变化时最小修改面在哪里？
7. 怎样回滚或定位回归？

回答不了时先回到机制、实验和测试，不用继续堆新抽象。

## AI 协助的边界

AI 可以生成草稿、补测试、列风险和提出重构方案；学习者仍负责：

- 选择最简单且满足需求的结构。
- 核对依赖、权限、副作用和真实服务行为。
- 拒绝静默 Mock、假成功和不可解释 fallback。
- 保留用户已有改动，不用破坏性命令掩盖冲突。
- 审核测试是否验证业务不变量，而不只是覆盖代码行。

## 按能力类型验收

| 能力 | 至少能解释 | 至少能验证 |
| --- | --- | --- |
| LLM | Provider、配置身份、Prompt、Schema、错误 | 真实调用与结构化失败 |
| RAG | 文档到 Citation 的来源链和检索控制 | 固定数据、真实检索和 bad case |
| Agent/Tool | Harness、权限、循环、停止和结构化错误 | Tool 轨迹、达到上限、失败与取消 |
| Multi-Agent | 拆分责任、状态、证据归属和冲突 | 与单 Agent 的固定基线比较 |
| Workflow | 状态、恢复、人工节点和幂等 | 中断、重试、恢复与副作用边界 |
| AI Native UI | 业务结果、证据、事件、等待和错误 | 正常、空结果、失败、取消和重连状态 |

## 完成判断

一项能力只有在“能解释、能运行、能诊断、能修改、能验证”同时成立时才算掌握。若只能让 AI 生成代码并看到一次成功输出，仍处于试用而不是所有权阶段。
