# AI Coding 掌握标准

本文定义“代码由 AI 生成或协助时，学习者怎样证明自己真正掌握”。它不规定课程顺序、文档模板或产品需求。

## 1. AI Coding 最容易制造的假象

一次运行成功不等于掌握。常见假象包括：

- 能让 AI 生成代码，却说不清输入、输出和失败边界。
- 看到测试通过，却不知道测试验证了业务不变量还是只覆盖了实现。
- 能复制日志给 AI，却不能判断应该检查数据、配置、Provider、Tool 还是状态机。
- 能增加一个框架抽象，却不知道普通函数是否已经足够。
- 能修改当前样例，却无法迁移到新 Provider、新资料格式或新业务规则。
- 能展示 Agent 或 Multi-Agent，却没有相对简单基线的收益证据。

掌握的目标不是逐行背诵，而是取得代码所有权。

## 2. 四层掌握

### 概念

能够用自己的话解释“是什么、为什么需要、与相邻概念怎样区分、何时不该使用”。只会复述名词不算掌握。

### 机制

能够从输入沿数据、状态、证据或异常变化解释到输出，说明关键约束、简单方案的不足和正常失败边界。机制理解不要求逐行讲源码。

### 实验

能够独立准备真实依赖、运行入口、阅读日志、区分配置错误与机制边界、完成单变量对照，并从实验入口定位到公共契约、关键实现和测试。

### 项目

能够把能力组合进唯一产品，解释为何属于 package 或 app，修改一个业务需求，处理 bad case，并用验收证据说明完成程度。

## 3. 六种代码所有权

### 解释

能说明：

- 谁调用它，它又调用谁。
- 输入、输出、状态、错误和外部依赖是什么。
- 哪些对象是稳定契约，哪些只是实现细节。
- 模型、应用、数据库、Tool 和 UI 分别负责什么。

### 验证

能判断应该使用：

- 确定性单元测试。
- 数据库、Provider 或协议集成测试。
- 真实模型、检索或 Tool 实验。
- 固定数据集和回归。
- 人工评审或 Trace。

并能说明每种证据不能证明什么。

### 修改

能完成一个真实需求变化，预测最小修改面和不应变化的契约，更新代码、测试、数据或配置中真正受影响的部分，而不是全仓机械重写。

### 调试

能从表现建立候选层次，沿输入、配置、外部依赖、核心机制、结果转换和调用方逐层排查。能够区分真实空结果、配置错误、能力不支持、超时、Schema 失败和业务质量不足。

### 迁移

能说明替换 Provider、模型、Embedding 空间、数据库、Tool 连接或 UI 入口时：

- 哪些契约可以保持。
- 哪些身份和缓存必须失效。
- 哪些测试可以复用。
- 哪些行为必须重新用真实服务验证。

### 权衡

能比较普通程序、专用 Tool、通用 Tool、RAG、Agent、Multi-Agent 和 Workflow 的成本、复杂度、权限与收益；能拒绝没有真实职责的抽象，也能在固定流程不足时说明为什么需要升级结构。

## 4. 代码所有权问题

对自己声称掌握的模块，应能回答：

1. 谁调用它，它又调用谁？
2. 哪些对象是稳定契约，哪些只是实现细节？
3. 哪些配置或身份变化会让旧数据、缓存或结果失效？
4. 失败在哪一层产生，怎样向上暴露？
5. 哪些行为需要真实服务验证，哪些可由确定性测试守住？
6. 需求变化时最小修改面在哪里？
7. 怎样回滚、重放或定位回归？
8. 如果移除当前框架，哪些业务不变量仍然成立？
9. 这项能力为什么进入产品，而不只是课程实验？

回答不了时先回到机制、实验和测试，不继续堆新抽象。

## 5. 推荐的 AI 协作工作流

1. 先让 AI 帮助定位真源、已有实现、测试和边界。
2. 自己写出问题、输入输出、约束、失败和验收。
3. 要求 AI 给出最小方案和备选方案，说明取舍。
4. 审查依赖、权限、副作用、真实服务和数据身份。
5. 实现后先运行确定性测试，再运行真实实验。
6. 阅读日志和差异，完成一个小修改或故意失败。
7. 用自己的话解释结果，并保留可回归证据。

AI 可以生成草稿、补测试、列风险和提出重构方案；学习者仍负责选择结构、核对真实行为、保护已有改动和决定何时完成。

## 6. 真实调用掌握

主路径使用真实模型或真实外部服务时，学习者必须知道：

- 凭证、端点、模型、能力和配置身份来自哪里。
- 缺少 Key、鉴权、限流、超时和能力不支持怎样暴露。
- 哪些参数能够比较，哪些差异来自供应商或模型能力。
- Mock 只复现哪种确定性行为。
- 如何记录模型、Prompt、Schema、Retriever、Tool 和数据集版本。

不能用静态回复、假向量、内存检索或 Mock Tool 成功证明真实质量。

## 7. 按能力类型验收

### LLM 应用

至少能解释 Provider、配置身份、Prompt、Schema、Context、错误和使用量；能运行真实调用、制造结构化失败，并在不改变业务入口的情况下切换一个模型配置。

### RAG

至少能从文档身份追踪到 Chunk、Retriever、Context 和 Citation；能区分 lexical、dense、fusion、filter 和生成问题；能在固定数据上完成一个策略修改并保留 bad case。

### Agent 与 Tool

至少能解释 Harness、Tool Schema、Runtime、权限、循环、预算和停止；能展示正常调用、参数错误、权限拒绝、超时、取消和达到上限；能判断 File、Code 或 MCP 能力是否应进入产品。对 Agent Skills，至少能区分格式与客户端行为，解释发现、激活、渐进加载、脚本执行和权限边界，并能定位版本或兼容性失败。

### Deep Research

至少能解释启动条件、研究计划、证据账本、来源质量、冲突、综合和停止；能回查关键结论的来源，并说明继续搜索为什么有或没有价值。

### Multi-Agent 与 A2A

至少能解释拆分责任、上下文、工具、共享状态、证据归属、局部失败和冲突裁决；能用固定任务比较单 Agent 与 Multi-Agent 的质量、成本、延迟和失败定位。对 A2A，至少能解释 Agent Card、Message、Task、Part、Artifact、任务生命周期和协议绑定，区分 Agent Card 中的能力 Skill 与 Agent Skills，并完成一次固定规范和 SDK 版本下的真实互操作验证。

### Workflow

至少能解释状态、节点、Checkpoint、Interrupt、恢复、人工节点、副作用和幂等；能展示中断、拒绝、重试、恢复和重复请求不会重复执行副作用。

### AI Native UI

至少能解释业务结果、证据、事件、等待、错误和用户控制；能展示正常、空结果、失败、取消、重连和部分完成状态。

## 8. 现场验收

一项能力完成时，学习者应能在不让 AI 代答的情况下：

1. 画出主要数据或状态流。
2. 从产品入口定位到公共契约和关键实现。
3. 运行正常案例和一个失败案例。
4. 解释日志中三个关键字段。
5. 完成一个小需求变化。
6. 选择并运行合适的验证。
7. 说明当前方案的一个代价和一个不采用的备选方案。

## 9. 完成判断

一项能力只有在“能解释、能验证、能修改、能调试、能迁移、能权衡”同时达到与其复杂度相称的程度时才算掌握。若只能让 AI 生成代码并看到一次成功输出，仍处于试用而不是所有权阶段。
