# LLM 在 AI 应用中的位置与边界

> 概念篇：理解需求评审助手为什么需要模型，以及普通程序、LLM、RAG、Agent 和 Workflow 分别承担什么责任。
>
> 阅读顺序见[标准学习路径](../learning-path.md)。本文无知识前置，交付对普通程序、LLM、RAG、Agent 和 Workflow 的基本判断。

## 从一个需求评审问题开始

产品同学提交一段需求：

> 订单详情页增加“申请售后”入口，对接售后接口 v2。

传统程序可以检查一些确定规则：

- 字段是否为空。
- 接口路径是否符合格式。
- 订单状态是否属于一组已知枚举。

但它很难仅靠预先写好的 `if-else` 判断：

- 需求有没有遗漏异常流程。
- 客户端展示条件和接口约束是否矛盾。
- 哪些描述可能导致 Web、Flutter 和服务端理解不一致。
- 哪些内容缺少验收标准。

这些问题没有固定关键词和唯一表达，需要理解一段非结构化材料，再生成新的分析。LLM 适合参与这部分工作。

但如果只是把 PRD 复制到聊天网页并输入“帮我评审”，应用仍然不知道：

- 模型依据了哪些材料。
- 输出为什么这次和上次不同。
- 风险字段能否被前端和数据库接收。
- 模型是否编造了不存在的接口或规则。
- 调用失败发生在网络、供应商、上下文还是结果解析。

所以“模型能够回答”只是能力起点，不是 AI 应用已经成立。

## 一句话理解 LLM

LLM 是一个根据当前输入和训练中形成的语言模式，逐步生成后续 Token 的概率模型。

对应用开发者更有用的表达是：

```text
输入
  指令 + 用户问题 + 当前材料

处理
  模型根据输入生成后续内容

输出
  文本、结构化内容或工具调用意图
```

它擅长：

- 理解和归纳自然语言。
- 从文本中抽取、分类和改写信息。
- 根据多个条件生成分析、建议或草稿。
- 在明确上下文中完成开放式判断。

它不天然具备：

- 对企业内部最新资料的可靠访问。
- 对事实来源的自动校验。
- 与数据库和业务接口的直接连接。
- 对业务权限、幂等和审批规则的负责能力。
- 对结果正确性的确定性保证。

模型的“会说”不能替代应用的“会控制”。

## 模型在应用链路中的位置

需求评审助手不是“前端调用一个模型 API”，而是一条由多种责任共同组成的链路：

```text
用户提交 PRD
→ 普通程序校验输入和权限
→ 检索系统寻找相关业务资料
→ 应用选择本轮允许模型看到的上下文
→ LLM 生成摘要、风险或追问
→ 应用校验输出结构和来源
→ 前端展示结果、证据、状态和失败
→ 评估系统记录效果并回流 bad case
```

LLM 位于“根据输入产生分析”这一段。它不是整条链路。

### 普通程序负责确定性边界

普通程序适合负责：

- 参数类型和必填校验。
- 权限判断。
- 数据库读写。
- 状态转换。
- 金额、时间和枚举等确定规则。
- 输出 Schema 与业务规则校验。

这些事情不应该因为接入 LLM 就交给模型猜测。

### LLM 负责语言理解与生成

LLM 适合负责：

- 理解 PRD 的目标和范围。
- 从多个文本片段中提炼风险。
- 把技术问题改写成产品可读的说明。
- 根据已有证据提出补充问题。
- 生成结构化报告的内容。

应用必须明确模型本轮的任务、材料和结果边界。

### RAG 负责把外部知识送到当前调用

模型训练时不知道团队刚更新的订单状态规则，也不会自动读取仓库中的接口文档。

RAG 负责：

```text
用户问题
→ 从外部资料中检索候选证据
→ 把相关内容交给模型
→ 模型基于当前证据生成结果
```

RAG 不是另一个模型，也不是简单的“上传文件”。它解决的是模型本轮依据什么外部知识。

### Agent 负责在不确定步骤中选择行动

固定 RAG 的步骤通常是预先写好的：

```text
检索 → 构造上下文 → 生成
```

当应用需要根据中间结果决定“是否改写查询、换知识源、调用接口、继续检索或向用户追问”时，才开始出现 Agent 的价值。

Agent 不是更聪明的聊天名称，而是模型参与下一步行动选择的运行机制。

### Workflow 负责显式流程和可恢复状态

当业务已经知道要经过哪些阶段，例如：

```text
需求理解
→ 技术评审
→ 测试评审
→ 人工确认
→ 报告汇总
```

Workflow 用显式状态、节点、分支、循环和恢复管理过程。能写成确定流程的部分，不必全部交给 Agent 自由决策。

## 怎样判断应该使用哪一种能力

| 问题 | 优先选择 |
| --- | --- |
| 字段是否为空、用户是否有权限 | 普通程序 |
| 阅读一段 PRD 并归纳风险 | LLM |
| 根据内部接口文档回答问题 | RAG + LLM |
| 根据检索质量决定是否改写查询 | 单 Agent |
| 按固定节点执行并支持人工审核 | Workflow |
| 多个真实角色需要独立上下文、工具和结果契约 | Multi-Agent |

这些能力可以组合，但不能因为项目最终会进入多 Agent，就在第一个版本同时引入所有复杂度。

## 为什么应用必须约束模型

一次模型输出受多项因素共同影响：

```text
任务描述
+ 当前上下文
+ 模型和参数
+ 输出约束
→ 概率性结果
```

即使 `temperature=0`，也不能把模型当作确定性函数：

- 供应商可能更新模型。
- 长上下文可能让模型忽略中间材料。
- Prompt 中的约束可能冲突。
- 输出可能语法正确但业务含义错误。
- 模型可能使用常识补充材料里没有的内容。

应用侧因此必须建立：

- Prompt：本轮要完成什么。
- Context：本轮允许依据什么。
- Schema：程序接受什么结果形状。
- Validation：结果是否真的符合业务契约。
- Reliability：失败后重试、降级还是终止。
- Evaluation：修改后是否真的变好。

标准学习路径会继续用“模型输入输出契约”统一这些责任。

## 在需求评审助手中的位置

模型能力会贯穿整个项目，但在不同学习位置承担的责任不同：

| 学习位置 | 模型承担的主要任务 |
| --- | --- |
| 第一阶段固定 RAG | 根据检索证据生成结构化风险、来源、拒答和需要补充的问题，并接受最小固定对照 |
| 第二阶段单 Agent | 判断是否改写、换知识源、调用工具、补检索或追问 |
| MCP、Agent Skills 与 Deep Research | 在受治理的工具和研究边界内规划、执行并保留证据 |
| Multi-Agent 与必要 Workflow | 在明确角色、状态、工具、恢复和人工确认边界中参与协作决策 |

不变的是：模型只负责被授权的语言理解、生成和有限判断，应用继续负责证据、状态、权限、校验和最终控制。

## 常见误解

### “Prompt 写好就不会胡说”

Prompt 可以改善任务遵循，但不能创造不存在的业务资料，也不能自动验证 Citation。

### “换成更强的模型就不用 RAG”

强模型可能有更好的通用能力，但仍不知道团队私有、最新和有权限边界的资料。

### “RAG 就是让模型记住上传的文件”

RAG 每次根据问题检索候选材料，再把选中的内容送入当前调用。它不等于模型永久记忆。

### “Agent 可以替代所有业务流程”

确定步骤、权限、金额和审批应由普通程序或 Workflow 管理。Agent 只应参与确实需要动态判断的部分。

### “输出是 JSON 就可信”

JSON 只说明结果具有某种形状。字段内容是否正确、来源是否存在、风险是否完整仍需本地校验和评估。

## 本文边界

本文只建立模型在 AI 应用中的位置，不展开：

- 怎样配置 Provider 并发起真实请求。
- Prompt 如何版本化。
- Schema 如何约束和校验输出。
- RAG 怎样解析、切分和检索文档。
- Agent Loop 与 Workflow 如何运行。
- 前端怎样消费流式事件。

这些问题会在后续机制篇中通过真实代码和实验分别展开。

## 判断是否已经理解

读完后，应能回答：

1. 为什么需求评审助手不能只做“把 PRD 发给模型”？
2. 普通程序、LLM、RAG、Agent 和 Workflow 各负责什么？
3. 固定检索流程为什么不需要 Agent？
4. Structured Output 为什么不能证明内容正确？
5. 模型没有业务资料时，应该修改 Prompt、增加 RAG，还是直接换大模型？为什么？

如果这些问题仍然混淆，先不要进入 Provider 和框架 API。完成后回到 [标准学习路径](../learning-path.md)，由唯一课表决定后续内容。
