# RAG 与外部知识的边界

> 概念篇：理解模型为什么需要外部知识，以及搜索、数据库查询、长上下文、固定 RAG 和 Agentic RAG 分别解决什么问题。
>
> 课程位置：[标准学习路径](../learning-path.md) V0 第七步。必要前置是 [LLM 在 AI 应用中的位置与边界](llm-in-ai-applications.md)；本文交付 RAG 的完整心智模型、方案选择边界和失败分层，不展开文档解析、Chunk、Embedding 与检索算法。

## 模型会评审，不代表知道团队规则

产品同学提交一段需求：

> 订单详情页增加“申请售后”入口，对接售后接口 v2。

模型可以根据通用软件经验指出一些风险，例如异常状态、重复提交和接口失败。但团队真正采用的规则可能是：

- 只有 `paid` 和 `completed` 状态允许申请售后。
- 接口 v2 新增必填字段 `source_channel`。
- Flutter 客户端仍在使用旧的入口展示条件。
- 历史评审已经确认虚拟商品不进入售后流程。

这些信息来自团队当前资料，不是模型仅凭训练知识就能可靠知道的事实。即使模型碰巧说对，应用也无法确认它依据的是当前规则、过期印象还是语言概率。

把所有资料一次性复制到 Prompt 也不能长期解决问题。随着文档增加，应用会遇到新的选择：哪些资料与本次需求相关，哪些版本仍然有效，哪些内容应该进入本轮模型输入，哪些来源需要展示给用户。

RAG 从这里开始有价值：它让应用在每次模型调用前，从受控的外部知识中寻找本轮可能需要的证据。

## 一句话理解 RAG

RAG 是 Retrieval-Augmented Generation，中文通常称为检索增强生成：应用先根据当前问题检索外部知识，再把选中的内容交给模型生成结果。

```text
输入
  用户问题 + 受控知识资料

处理
  检索候选证据 → 选择本轮上下文 → 模型基于上下文生成

输出
  业务结果 + 来源候选 + 检索与生成诊断
```

“增强”不是修改模型参数，也不是让模型永久记住文件。外部知识只在当前运行中通过检索和上下文进入模型输入。

因此，RAG 是一条应用数据流，不是某个向量数据库、Embedding 模型或框架的别名。

## RAG 有离线和在线两条链路

只看“问题 → 向量搜索 → 回答”会漏掉一半系统。真实 RAG 至少包含知识生产和在线回答两条链路。

### 知识生产：先让资料成为可检索对象

```text
原始文件
→ 加载与解析
→ 清洗与来源保留
→ Chunk 与 Metadata
→ 建立 lexical / dense 索引
→ 可检索知识
```

这条链路决定资料是否完整进入系统、来源位置是否保留、更新后能否区分版本。文件上传成功不等于知识已经可用；解析为空、切分破坏语义或来源丢失，都会让后面的检索失去基础。

### 在线回答：再为当前任务寻找证据

```text
待评审需求与问题
→ Retriever 查询受控知识
→ 返回候选 Chunk 和检索诊断
→ Context Builder 选择本轮材料
→ LLM 生成结构化风险
→ 应用校验结果并展示来源候选
```

这条链路中有三个容易混淆的对象：

- **检索候选**：Retriever 判断可能相关的知识片段。
- **最终上下文**：应用在预算、去重和来源约束下，决定真正交给模型的材料。
- **模型结果**：模型根据任务和最终上下文生成的分析。

候选被检索到，不代表一定进入上下文；进入上下文，也不代表模型一定正确使用。把三者分开，失败时才知道应该检查 Retriever、Context Builder 还是生成链路。

## 外部知识不只有 RAG 一种接入方式

选择方案前，先看知识在哪里、是否需要语义理解、结果是否要求确定性。

### 模型已有知识

模型已有知识适合通用、稳定、无需组织内部来源的内容，例如解释 HTTP 状态码的通常含义。

它不适合承担团队私有规则、刚发布的接口版本或必须提供来源的结论。更换更大的模型可能改善理解能力，但不会自动获得当前企业资料。

### 直接放入长上下文

当材料很少、范围固定，并且每次都需要阅读全文时，可以直接把材料加入上下文。例如只比较一份短 PRD 和一页接口变更说明。

长上下文没有消除选择问题。材料增加后，它仍会带来 Token 成本、噪声干扰、关键内容被忽略和来源混淆。上下文窗口能装下，不等于模型能稳定使用全部内容。

### 搜索

搜索负责从开放或指定范围中发现信息，结果通常是网页、文档或链接。它适合外部、变化快、需要发现新来源的问题。

需求评审助手的核心资料是受控的内部文档，必须考虑版本、业务范围和可追溯位置。搜索可以成为某种知识入口，但“搜索到网页”本身还没有完成清洗、权限、上下文选择和证据约束。

### 数据库查询

数据库查询适合结构明确、条件确定、要求精确结果的数据。例如查询订单 `123` 的当前状态，应该使用业务数据库或受控 API，而不是把所有订单记录做成向量后让模型猜。

RAG 更适合自然语言资料中的相关内容发现，例如从 PRD、接口文档和历史评审中寻找与“售后入口”相关的约束。

### 固定 RAG

固定 RAG 的执行步骤由应用预先确定：

```text
检索 → 构造上下文 → 生成 → 校验
```

它适合知识范围和处理步骤已知的问题。每一步可以单独观察、测试和替换，成本与失败边界也更容易控制。

V0 的需求评审助手采用固定 RAG，因为无论输入哪份 PRD，都需要执行同一条基础链路。模型不需要决定是否跳过检索、换知识源或再运行一轮工具。

### Agentic RAG

Agentic RAG 让模型参与决定下一步行动，例如：

- 是否改写查询。
- 应该选择哪个知识源。
- 当前证据是否需要再次检索。
- 应该继续行动还是向用户追问。

它适合步骤无法在运行前完全确定的任务，但会增加状态、工具契约、停止条件、成本和评估难度。固定流程能解决问题时，增加 Agent 不会自动提高检索质量。

本项目保留 V0 固定 RAG 基线，到 V3 再用已经出现的真实失败判断哪些步骤值得交给单 Agent 动态选择。

## 用问题性质选择方案

| 真实问题 | 优先方案 | 原因 |
| --- | --- | --- |
| 解释通用的软件概念 | 模型已有知识 | 不依赖内部最新事实 |
| 阅读一份很短且固定的材料 | 直接上下文 | 无需建立检索系统 |
| 查询某订单当前状态 | 数据库或业务 API | 字段和条件明确，要求确定结果 |
| 查找公开发布的最新政策 | 受控搜索 | 需要发现外部新来源 |
| 从内部 PRD、接口文档和历史评审中寻找相关规则 | 固定 RAG | 自然语言资料多，步骤固定且需要来源 |
| 根据中间证据决定改写、换源或补检索 | Agentic RAG | 下一步需要运行时动态判断 |

这些方案可以组合。例如，应用可以先用数据库查询当前订单状态，再用 RAG 查找该状态对应的售后规则，最后让模型解释两者是否冲突。组合不等于把所有信息都交给同一个 Retriever。

## 一个不该使用 RAG 的反例

假设用户问：

> 订单 `123` 现在是否为已支付状态？

如果状态存储在业务数据库中，这个问题有确定字段、确定记录和实时结果。正确链路是校验权限后查询数据库。

把历史订单说明、日志或数据库导出文本做成 RAG，再让模型根据相似片段回答，会引入不必要风险：

- 检索到的可能是旧状态。
- 相似记录可能属于另一笔订单。
- 模型可能把描述性文本当成实时事实。
- 结果难以满足确定性和一致性要求。

RAG 不是“只要有数据就使用”的默认方案。它主要解决非结构化知识的相关内容发现与生成依据问题，不能替代确定性查询和业务规则。

## RAG 能解决什么，不能解决什么

RAG 能够改善：

- 模型接触团队私有、最新或特定领域资料的能力。
- 从大量自然语言材料中筛选本轮相关内容的效率。
- 将来源候选和生成结果一起交给应用观察的可能性。
- 在不重新训练模型的情况下更新外部知识。

RAG 不能自动保证：

- 原始资料正确、完整且没有过期。
- Loader 没有遗漏文本，Chunk 没有切断关键条件。
- Retriever 一定召回正确证据。
- Context Builder 一定保留最重要的候选。
- 模型只依据证据生成，不补充材料外结论。
- 模型声明的 Citation 真的存在并支持结论。
- 证据不足时一定拒答。

这些边界说明为什么 RAG 项目不能只看最终回答。知识生产、检索、上下文和生成都需要独立诊断与评估。

## 从结果反查四层失败

当评审结果遗漏“虚拟商品不支持售后”时，不要立即修改 Prompt。先判断事实在哪一层丢失。

### 1. 知识生产失败

原始文档包含规则，但 PDF 没有文本层，或者解析、清洗、切分时丢失了对应段落。

此时 Retriever 根本没有机会命中。应该检查解析结果、Chunk 和来源位置。

### 2. 检索失败

规则已经成为可检索 Chunk，但当前查询没有召回，或被过滤、阈值和 Top-k 淘汰。

此时应该检查查询、知识范围、每路候选、排名和淘汰原因。

### 3. 上下文失败

Retriever 已返回正确 Chunk，但 Context Builder 因预算、去重或排序没有把它放入最终输入。

此时应该比较检索候选与最终上下文，而不是继续调整向量索引。

### 4. 生成失败

正确证据已经进入上下文，但模型忽略、误读或生成了材料外结论。

此时才重点检查 Prompt、模型、Structured Output、业务校验和证据约束。

这四层不是为了把错误分类得更复杂，而是为了让一次修改落在真正负责的模块上。

## 在需求评审助手中的位置

RAG 是阶段一的主线能力，但不同版本承担不同责任：

| 版本 | RAG 解决的重点 |
| --- | --- |
| V0 固定 RAG 基线 | 真实文档进入知识系统，建立可诊断的 lexical、dense 与 RRF 检索，并提供 Sources / Citation Candidate |
| V1 可信结构化评审 | 校验 Citation，判断证据充分性，在不足时拒答或追问 |
| V2 质量闭环 | 用固定数据评估检索、生成和引用，治理 bad case |
| V3 单 Agent RAG | 根据运行状态改写查询、选择知识源、补检索或追问 |

当前第 7 步只建立选择和边界判断。文档加载、Chunk、Embedding、PostgreSQL FTS、pgvector、RRF 与 Retrieval 诊断会由后续机制篇分别解释并通过真实实验观察。

## 常见误解

### “接入向量数据库就完成了 RAG”

向量数据库只承担索引和检索的一部分。没有可靠的知识生产、来源定位、上下文选择、生成约束和评估，系统仍然无法解释答案为什么错。

### “检索到相关文档，答案就有证据”

检索结果只是候选。必须继续确认候选是否进入上下文、模型结论是否由对应内容支持，以及来源是否通过应用校验。

### “所有资料都放进上下文，就不需要检索”

材料很少时可以这样做；当资料增长后，成本、噪声、版本和选择问题仍然存在。长上下文是容量能力，不是知识治理与相关性判断。

### “RAG 回答不好，就升级成 Agentic RAG”

如果问题来自文档解析错误、Chunk 破坏语义或 Retriever 参数不合理，Agent 只会在错误基础上执行更多步骤。先让固定 RAG 的每一层可观察，才能判断动态决策是否真的有收益。

### “Embedding 分数高就代表事实正确”

相似度只表达某种表示空间中的接近程度。相似文本可能属于旧版本、错误业务范围或相反条件，仍需 Metadata、来源和业务校验。

## 本文边界

本文不实现或展开：

- TXT、Markdown、DOCX 与文本型 PDF 的具体解析。
- Chunk 策略、父子块和 Metadata 设计。
- Embedding、向量相似度和 pgvector。
- PostgreSQL 全文检索与 RRF 融合。
- Citation 校验、Refusal 和证据充分性。
- Agent 的工具、状态和运行循环。

这些是后续机制或项目问题。本文的交付是先能判断为什么需要 RAG、应该选择哪种外部知识接入方式，以及错误最可能落在哪一层。

## 判断是否已经理解

读完后，应能回答：

1. 为什么模型能够分析 PRD，仍然不代表它知道团队当前接口规则？
2. RAG 的知识生产链和在线回答链分别包含什么？
3. 检索候选、最终上下文和模型结果为什么必须分开？
4. 查询实时订单状态为什么应该使用数据库，而不是 RAG？
5. 固定 RAG 与 Agentic RAG 的决定权有什么不同？
6. 一条正确规则没有出现在最终答案中，应该按什么顺序定位？
7. RAG 为什么不能自动证明 Citation 正确？
