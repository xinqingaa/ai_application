# RAG 与外部知识的边界

> 概念篇：理解模型为什么需要外部知识，以及搜索、数据库查询、长上下文、固定 RAG 和 Agentic RAG 分别解决什么问题。
>
> 课程位置：[标准学习路径](../learning-path.md)第一阶段第 7 节。必要前置是 [LLM 在 AI 应用中的位置与边界](llm-in-ai-applications.md)；本文交付 RAG 的心智模型、第一阶段固定 RAG 总图、方案选择边界和失败分层，不展开文档解析、Chunk、Embedding 与检索算法。

## 模型会评审，不代表知道团队规则

产品同学提交一段需求：

> 订单详情页增加“申请售后”入口，对接售后接口 v2。

模型可以根据通用软件经验指出一些风险，例如异常状态、重复提交和接口失败。但团队真正采用的规则可能是：

- 只有 `paid` 和 `completed` 状态允许申请售后。
- 接口 v2 新增必填字段 `source_channel`。
- Flutter 客户端仍在使用旧的入口展示条件。
- 历史评审已经确认虚拟商品不进入售后流程。

这些信息来自团队当前资料，不是模型仅凭训练知识就能可靠知道的事实。即使模型碰巧说对，应用也无法确认它依据的是当前规则、过期印象还是语言概率。

把所有资料一次性复制到 Prompt 也不能长期解决问题。随着文档增加，应用会遇到新的选择：哪些资料与本次需求相关，哪些版本仍然有效，哪些内容应该进入本轮模型输入，哪些来源需要展示给用户。

RAG 从这里开始有价值：它让应用在每次模型调用前，从受控的外部知识中寻找本轮可能需要的证据。

## 一句话理解 RAG

RAG 是 Retrieval-Augmented Generation，中文通常称为检索增强生成：应用先根据当前问题检索外部知识，再把选中的内容交给模型生成结果。

```text
输入
  用户问题 + 受控知识资料

处理
  检索候选证据 → 选择本轮上下文 → 模型基于上下文生成

输出
  业务结果 + 来源候选 + 检索与生成诊断
```

“增强”不是修改模型参数，也不是让模型永久记住文件。外部知识只在当前运行中通过检索和上下文进入模型输入。

因此，RAG 是一条应用数据流，不是某个向量数据库、Embedding 模型或框架的别名。上面三个框就是第一阶段固定 RAG 的地图；第 8–16 节把每个箭头做成可运行机制，对象始终是同一批售后资料。

## 第三段沿着一条链走完，不是十个专题

可以先把处理过程收成一句：

```text
入库 → 两路召回 → 融合截断 → 装配上下文 → 约束生成
```

用开头那几条规则想一遍转换：

```text
文件里的售后规则、接口字段、历史结论
→ 带来源位置的文档（还没有切片）
→ 带稳定身份的切片
→ 文本的向量表示（此时只比较已知句子，还没有从库里搜）
→ 按词找出候选（擅长 source_channel 这种原词）
→ 按向量找出候选（擅长「申请售后」和「逆向服务」意思接近）
→ 两路排名合成一份名单
→ 过滤、阈值、截断，并记下谁在哪一层被扔掉
→ 预算内真正交给模型的文字
→ 按候选生成；并检查模型声称的来源编号是否属于本轮候选
```

| 学习路径 | 这一步把什么变成什么 | 它在纠正哪种常见误判 | 它明确还不做 |
| --- | --- | --- | --- |
| 8 | 文件 → 可定位的文档 | 上传成功不等于知识可用 | 不切切片 |
| 9 | 文档 → 切片 | 切完不等于已经可以引用 | 不检索 |
| 10 | 文本 → 向量 | 两个句子接近不等于已经能搜整库 | 不入库、不召回 |
| 11 | 切片 → 词面候选 | 空结果不等于数据库坏了 | 不理解同义说法 |
| 12 | 切片 → 向量候选 | 距离近不等于事实正确 | 不把向量距离和词面分数直接相加 |
| 13 | 两路排名 → 一份名单 | 两路都跑通不等于已有最终候选 | 不定阈值，不装配上下文 |
| 14 | 名单 → 可诊断的检索结果 | 库里有不等于 Retriever 会返回 | 不写入模型输入 |
| 15 | 检索结果 → 本轮上下文 | 检索到不等于模型看见了 | 不生成风险结论 |
| 16 | 上下文 → 结构化结果 + 来源候选 | 模型写了编号不等于引用已校验 | 不判断内容是否真的支持结论 |

第 10 步和第 11 步之间有一次底座切换，后面读起来会突然变难，通常不是前面没读懂。第 10 步仍在比较事先选好的句子；第 11 步第一次问：同一批切片保存下来之后，怎样按用户问题从中找出候选。资料还是那些售后规则，只是对象从内存里的文本，变成库里可查询的记录。

本文先让你能画出这条链，并判断什么时候不该用 RAG。第 8–16 节再把每个箭头做成可观察的机制。读完第 16 节，完成的是固定 RAG 的核心机制入门：你知道资料怎样变成切片，两路检索怎样形成候选，候选怎样进入上下文，以及模型怎样基于候选生成。它还不是整个第一阶段产品掌握——第 17 节继续完成 Citation 支持性、证据充分性和 Refusal，后面再交付 API、工作台和四路对照。

步号顺序只由 [标准学习路径](../learning-path.md) 维护。下面出现的正式对象名，对应的就是这条链上的节点。

## 先给链上的节点起正式名字

进入 Loader、Chunk 或 Retriever 之前，先把业务对象和工程对象分开。它们都可能以文本出现，但承担的责任不同。先记住六个节点，就够把开篇那条链说圆：

| 对象 | 它是什么 | 它不是什么 |
| --- | --- | --- |
| File Artifact | 系统收到的 TXT、Markdown、DOCX 或 PDF 文件 | 已经可检索的知识 |
| Knowledge Document | 具有稳定业务身份、版本和来源角色的知识文档 | 文件名或数据库自增 ID |
| Chunk | 为检索建立的内容单元 | 天然正确的语义边界或已验证证据 |
| Retrieval Hit | Retriever 返回的候选 Chunk 和排名信息 | 最终进入模型的上下文 |
| Context Source | Context Builder 选入本轮模型输入的材料 | 已经支持模型结论的 Citation |
| Review Result | 模型生成并经过应用结构校验的评审结果 | 自动可信的事实结论 |

当前被评审的 PRD 叫 Target Requirement。它在最后才与外部知识汇合，第一阶段不把它无说明地放进通用知识候选池；否则系统可能检索到需求自己的说法，再把它当成证明需求正确的外部依据。现行规则是 Reference Knowledge，带历史属性的旧评审记录是 Historical Material，后者不能自动覆盖前者。第 8 节还会产出 Document Element：保留标题、段落、表格和来源位置，但它仍然不是 Chunk。

它们的关系不是“文件上传后直接问模型”，而是逐步转换：

```text
Reference Knowledge / Historical Material
→ File Artifact
→ Knowledge Document + Document Element
→ Chunk
→ Retrieval Hit
→ Context Source

Target Requirement + Context Source
→ Review Result
```

## 完整能力还有第四层，但第三段先不走

从原始文件到 Agent 按需行动，可以分成四层。第一阶段只把前三层做成固定 RAG；第四层在第二阶段进入 Agent Harness 和 Agentic RAG，不要当成当前这一段的学习路线。

```text
知识生产
1. 内容识别与解析路由
   文件容器 → 内容形态 → 文本抽取 / OCR / 视觉理解
2. 结构还原与统一表示
   原始片段 → 标题、段落、表格、阅读顺序和来源位置

固定 RAG
3. Chunk → Index → Retrieve → Context → Generate

动态控制
4. Tool Contract + Runtime
   → Agent 选择 Query / Source / Retrieve / Ask / Stop
```

前三层建立稳定、可测试的数据能力。第四层不是继续加工文档，而是运行时控制层：Agent 根据用户意图和当前证据决定调用哪些能力、是否补检索、追问或停止。Retriever、RRF 和满足准入条件的 Reranker 仍负责候选过滤、排序和诊断，不能让模型自由整理结果来替代检索契约。

这四层描述能力怎样依赖和演进。下面把前三层按离线、在线和生成再看一遍，对应开篇那条链，而不是另起一套步骤。

## 把开篇那条链按离线、在线和生成再看一遍

只看“问题 → 向量搜索 → 回答”会漏掉入库之前和生成之前的责任。开篇那句「入库 → 两路召回 → 融合截断 → 装配上下文 → 约束生成」可以展开成三条流。

### 知识生产：先让资料成为可检索对象

```text
原始文件
→ 识别内容形态并选择解析路线
→ 恢复标题、段落、表格、阅读顺序与来源位置
→ 清洗并形成统一文档元素
→ Chunk 与 Metadata
→ 建立 lexical / dense 索引
→ 可检索知识
```

这条链路先完成两层知识生产：第一层判断原生文本、扫描件或图文混排等内容形态并选择文本抽取、OCR 或视觉理解路线；第二层把解析结果恢复为带结构和来源的统一元素。之后才是 Chunk、索引和检索。文件上传成功不等于知识已经可用；解析路线选错、结构还原错误、切分破坏语义或来源丢失，都会让后面的检索失去基础。

第 8 步处理文件到文档元素，第 9 步切成 Chunk。词面索引和向量索引要等到切片具备稳定身份之后，分别在第 11、12 步进入真实数据库。

### 在线检索：为当前任务寻找候选

```text
待评审需求 + 评审问题 + knowledge scope
→ Retriever 查询受控知识
→ 返回候选 Chunk 和检索诊断
```

Retriever 的职责是寻找可能相关的候选。表示、匹配、排名、过滤和多路融合都发生在“找候选”这件事里，但它们不是同一个动作：

```text
内容表示
→ 查询与候选匹配
→ 每路候选排名
→ 范围过滤与阈值淘汰
→ 多路排名融合
→ 最终候选集
```

第 10 步只处理「内容表示」：观察文本怎样变成向量，还不从库中搜索。第 11、12 步才分别按词和按向量做匹配与每路排名；第 13 步融合两路排名，第 14 步做范围过滤、阈值淘汰并留下诊断。分数方向、全文检索和向量索引的内部细节由对应机制篇观察，这里只要求能指出它们落在这条链的哪一段。

### 证据进入生成：决定模型真正看到什么

```text
Target Requirement + Retrieval Hit
→ Context Builder 按角色、预算和去重规则选择材料
→ Context Source + Context Build Report
→ LLM 生成结构化风险
→ 应用校验结果并展示来源候选
```

这条链路中有三个容易混淆的对象：

- **检索候选**：Retriever 判断可能相关的知识片段。
- **最终上下文**：应用在预算、去重和来源约束下，决定真正交给模型的材料。
- **模型结果**：模型根据任务和最终上下文生成的分析。

候选被检索到，不代表一定进入上下文；进入上下文，也不代表模型一定正确使用。把三者分开，失败时才知道应该检查 Retriever、Context Builder 还是生成链路。第 15 步装配上下文，第 16 步约束生成，并检查模型声称的来源编号是否属于本轮候选；编号合法仍不等于内容支持结论。

## RAG 质量不是一个准确率

从文件进入系统到风险结论出现，至少有五个逐层收紧的问题：

| 质量判断 | 要回答的问题 | 典型失败 |
| --- | --- | --- |
| 可解析 | 文件内容是否完整、按合理顺序进入系统 | PDF 没有文本层、表格或否定条件丢失 |
| 可检索 | 内容是否成为带稳定身份和范围的候选单元 | Chunk 缺少来源、索引未更新 |
| 相关 | Retriever 是否把正确候选排进可用范围 | 同义改写召回失败、旧规则排名过高 |
| 可进入上下文 | 正确候选是否在预算和角色约束下进入模型输入 | top-k、去重或预算丢掉关键规则 |
| 能支撑结论 | 上下文内容是否真的足以支持当前风险结论 | 只有相似措辞，没有对应事实或条件 |

前一层成功只是后一层的必要条件，不是充分条件。文件解析成功不能证明检索正确；相似度高不能证明材料支持结论；模型输出了来源编号也不能证明 Citation 有效。因此，第一阶段必须保留分层诊断，并在第 17 节继续完成 Citation 支持性和证据充分性校验。

## 外部知识不只有 RAG 一种接入方式

选择方案前，先看知识在哪里、是否需要语义理解、结果是否要求确定性。

### 模型已有知识

模型已有知识适合通用、稳定、无需组织内部来源的内容，例如解释 HTTP 状态码的通常含义。

它不适合承担团队私有规则、刚发布的接口版本或必须提供来源的结论。更换更大的模型可能改善理解能力，但不会自动获得当前企业资料。

### 直接放入长上下文

当材料很少、范围固定，并且每次都需要阅读全文时，可以直接把材料加入上下文。例如只比较一份短 PRD 和一页接口变更说明。

长上下文没有消除选择问题。材料增加后，它仍会带来 Token 成本、噪声干扰、关键内容被忽略和来源混淆。上下文窗口能装下，不等于模型能稳定使用全部内容。

### 搜索

搜索负责从开放或指定范围中发现信息，结果通常是网页、文档或链接。它适合外部、变化快、需要发现新来源的问题。

需求评审助手的核心资料是受控的内部文档，必须考虑版本、业务范围和可追溯位置。搜索可以成为某种知识入口，但“搜索到网页”本身还没有完成清洗、权限、上下文选择和证据约束。

### 数据库查询

数据库查询适合结构明确、条件确定、要求精确结果的数据。例如查询订单 `123` 的当前状态，应该使用业务数据库或受控 API，而不是把所有订单记录做成向量后让模型猜。

RAG 更适合自然语言资料中的相关内容发现，例如从 PRD、接口文档和历史评审中寻找与“售后入口”相关的约束。

这里的「数据库查询」是业务库里的确定性查找，例如按订单号取当前状态。它和第 11 步把切片存进 PostgreSQL、再按词检索，不是同一件事：后者仍是自然语言相关内容发现，只是检索发生在数据库里。

### 固定 RAG

固定 RAG 的执行步骤由应用预先确定：

```text
检索 → 构造上下文 → 生成 → 校验
```

它适合知识范围和处理步骤已知的问题。每一步可以单独观察、测试和替换，成本与失败边界也更容易控制。

第一阶段的需求评审助手采用固定 RAG，因为无论输入哪份 PRD，都需要执行同一条基础链路。模型不需要决定是否跳过检索、换知识源或再运行一轮工具。

### Agentic RAG

Agentic RAG 让模型参与决定下一步行动，例如：

- 是否改写查询。
- 应该选择哪个知识源。
- 当前证据是否需要再次检索。
- 应该继续行动还是向用户追问。

它适合步骤无法在运行前完全确定的任务，但会增加状态、工具契约、停止条件、成本和评估难度。固定流程能解决问题时，增加 Agent 不会自动提高检索质量。

Agentic RAG 也不会替代知识解析、Chunk、索引和 Retriever。可以把它理解为运行时控制层：Agent 根据用户意图选择查询、知识源和工具，判断是否补检索、追问或停止；Retriever、RRF 或后续经过准入的 Reranker 仍负责产生和排列可诊断候选。让模型自由“整理搜索结果”不能替代检索排序契约。

本项目在第一阶段保留固定 RAG 基线，到第二阶段再用已经出现的真实边界判断哪些步骤值得交给单 Agent 动态选择。

## 用问题性质选择方案

| 真实问题 | 优先方案 | 原因 |
| --- | --- | --- |
| 解释通用的软件概念 | 模型已有知识 | 不依赖内部最新事实 |
| 阅读一份很短且固定的材料 | 直接上下文 | 无需建立检索系统 |
| 查询某订单当前状态 | 数据库或业务 API | 字段和条件明确，要求确定结果 |
| 查找公开发布的最新政策 | 受控搜索 | 需要发现外部新来源 |
| 从内部 PRD、接口文档和历史评审中寻找相关规则 | 固定 RAG | 自然语言资料多，步骤固定且需要来源 |
| 根据中间证据决定改写、换源或补检索 | Agentic RAG | 下一步需要运行时动态判断 |

这些方案可以组合。例如，应用可以先用数据库查询当前订单状态，再用 RAG 查找该状态对应的售后规则，最后让模型解释两者是否冲突。组合不等于把所有信息都交给同一个 Retriever。

## 一个不该使用 RAG 的反例

假设用户问：

> 订单 `123` 现在是否为已支付状态？

如果状态存储在业务数据库中，这个问题有确定字段、确定记录和实时结果。正确链路是校验权限后查询数据库。

把历史订单说明、日志或数据库导出文本做成 RAG，再让模型根据相似片段回答，会引入不必要风险：

- 检索到的可能是旧状态。
- 相似记录可能属于另一笔订单。
- 模型可能把描述性文本当成实时事实。
- 结果难以满足确定性和一致性要求。

RAG 不是“只要有数据就使用”的默认方案。它主要解决非结构化知识的相关内容发现与生成依据问题，不能替代确定性查询和业务规则。

## RAG 能解决什么，不能解决什么

RAG 能够改善：

- 模型接触团队私有、最新或特定领域资料的能力。
- 从大量自然语言材料中筛选本轮相关内容的效率。
- 将来源候选和生成结果一起交给应用观察的可能性。
- 在不重新训练模型的情况下更新外部知识。

RAG 不能自动保证：

- 原始资料正确、完整且没有过期。
- Loader 没有遗漏文本，Chunk 没有切断关键条件。
- Retriever 一定召回正确证据。
- Context Builder 一定保留最重要的候选。
- 模型只依据证据生成，不补充材料外结论。
- 模型声明的 Citation 真的存在并支持结论。
- 证据不足时一定拒答。

这些边界说明为什么 RAG 项目不能只看最终回答。知识生产、检索、上下文和生成都需要独立诊断与评估。

## 从结果反查四层失败

当评审结果遗漏“虚拟商品不支持售后”时，不要立即修改 Prompt。先判断事实在哪一层丢失。

### 1. 知识生产失败

原始文档包含规则，但 PDF 没有文本层，或者解析、清洗、切分时丢失了对应段落。

此时 Retriever 根本没有机会命中。应该检查解析结果、Chunk 和来源位置。

### 2. 检索失败

规则已经成为可检索 Chunk，但当前查询没有召回，或被过滤、阈值和 Top-k 淘汰。

此时应该检查查询、知识范围、每路候选、排名和淘汰原因。

### 3. 上下文失败

Retriever 已返回正确 Chunk，但 Context Builder 因预算、去重或排序没有把它放入最终输入。

此时应该比较检索候选与最终上下文，而不是继续调整向量索引。

### 4. 生成失败

正确证据已经进入上下文，但模型忽略、误读或生成了材料外结论。

此时才重点检查 Prompt、模型、Structured Output、业务校验和证据约束。

这四层不是为了把错误分类得更复杂，而是为了让一次修改落在真正负责的模块上。对照开篇的链：第 8–9 步主要对应知识生产，第 10–14 步对应检索（其中第 10 步还只是表示，第 11 步起才真正找候选），第 15 步对应上下文，第 16 步对应生成约束。

## 在需求评审助手中的位置

RAG 是第一阶段的主线能力，但不同学习位置承担不同责任：

| 版本 | RAG 解决的重点 |
| --- | --- |
| 第一阶段固定 RAG | 真实文档进入知识系统，建立可诊断的 lexical、dense 与 RRF 检索，完成 Sources、Citation、证据充分性、Refusal 和最小固定对照 |
| 第二阶段 Agent 系统 | 根据运行状态改写查询、选择知识源、调用 Tool、补检索或追问，再进入 Deep Research、Multi-Agent、A2A 和必要 Workflow |

当前第 7 步建立总图、方案选择和失败分层。第 8–16 步把开篇那条链逐段做成可观察机制；阅读顺序只由 [标准学习路径](../learning-path.md) 维护。

## 常见误解

### “接入向量数据库就完成了 RAG”

向量数据库只承担索引和检索的一部分。没有可靠的知识生产、来源定位、上下文选择、生成约束和评估，系统仍然无法解释答案为什么错。

### “检索到相关文档，答案就有证据”

检索结果只是候选。必须继续确认候选是否进入上下文、模型结论是否由对应内容支持，以及来源是否通过应用校验。

### “所有资料都放进上下文，就不需要检索”

材料很少时可以这样做；当资料增长后，成本、噪声、版本和选择问题仍然存在。长上下文是容量能力，不是知识治理与相关性判断。

### “RAG 回答不好，就升级成 Agentic RAG”

如果问题来自文档解析错误、Chunk 破坏语义或 Retriever 参数不合理，Agent 只会在错误基础上执行更多步骤。先让固定 RAG 的每一层可观察，才能判断动态决策是否真的有收益。

### “Embedding 分数高就代表事实正确”

相似度只表达某种表示空间中的接近程度。相似文本可能属于旧版本、错误业务范围或相反条件，仍需 Metadata、来源和业务校验。

### “第 10 步已经会算向量，就是已经会检索”

比较事先选好的句子，只说明表示空间里谁离谁近。从一批已保存的切片里按用户问题找出候选，是第 11 步起才开始的另一件事。

## 本文边界

本文不实现或展开：

- TXT、Markdown、DOCX 与文本型 PDF 的具体解析。
- Chunk 策略、父子块和 Metadata 设计。
- Embedding、向量相似度和 pgvector。
- PostgreSQL 全文检索与 RRF 融合。
- Citation 校验、Refusal 和证据充分性。
- Agent 的工具、状态和运行循环。

这些是后续机制或项目问题。本文的交付是：能画出第三段从文件到生成的链，判断为什么需要 RAG、应该选择哪种外部知识接入方式，以及错误最可能落在哪一层。

## 判断是否已经理解

读完后，应能回答：

1. 为什么模型能够分析 PRD，仍然不代表它知道团队当前接口规则？
2. 为什么第 10 步比较句子向量，还不能称为「从知识库检索」？
3. RAG 的知识生产链和在线回答链分别包含什么？
4. 检索候选、最终上下文和模型结果为什么必须分开？模型写了来源编号，为什么仍不等于引用已校验？
5. 查询实时订单状态为什么应该使用数据库，而不是 RAG？这和第 11 步把切片存进 PostgreSQL 有什么不同？
6. 固定 RAG 与 Agentic RAG 的决定权有什么不同？
7. 一条正确规则没有出现在最终答案中，应该按什么顺序定位？
8. RAG 为什么不能自动证明 Citation 正确？
9. 可解析、相关和能支撑结论为什么是三种不同的质量判断？
