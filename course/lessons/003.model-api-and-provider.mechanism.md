# Model API、调用生命周期与 Provider 抽象

> 机制篇：解释一次模型调用怎样穿过配置、Provider 和统一结果边界，以及供应商差异应该在哪里被吸收。
>
> 课程位置见[标准学习路径](../learning-path.md)。必要前置是[模型输入输出契约](002.model-input-output-contracts.concept.md)；运行、配置、日志和读码见[配套实验](003.model-api-and-provider.lab.md)。

## 为什么业务不能直接绑定模型 SDK

需求评审助手关心的是“识别哪些风险、依据是什么、结果能否进入后续流程”，而不是某个供应商的客户端怎样初始化。若每个业务模块都直接依赖 SDK，请求参数、异常类型、模型名和响应形状会散落在各处。

这种耦合会产生三个问题：

1. 换模型或供应商时，业务代码跟着变化。
2. 不同入口记录的模型、用量和耗时不一致，结果无法公平比较。
3. 供应商错误直接泄漏到业务层，同一种失败会得到不同处理。

因此应用需要一个稳定调用边界：业务声明“需要哪类模型能力”，调用层负责选择真实配置、适配供应商并返回统一结果。

如果你来自前端或 Flutter，可以把这层理解成数据源适配层。页面不应该因为数据从 REST 换成 GraphQL 就重写业务组件；同样，风险评审也不应该因为模型供应商变化就重写任务逻辑。业务需要的是稳定结果，适配层负责吸收连接方式和响应形状的变化。

这层边界的价值不只是“代码更整齐”。它决定系统能否回答：本次究竟用了哪个模型、为什么比上次慢、失败发生在哪一层，以及切换供应商后哪些变化属于预期。没有这些事实，后续 Prompt 对照、RAG 生成和 Agent 运行都很难公平比较。

## 从“能调用”到“可复用”的机制递进

一次 SDK 直调只能证明网络、密钥和某个模型当前可用。要让它成为应用能力，还要依次解决秘密配置、用途配置、供应商适配和统一结果。

```text
业务任务
  → 稳定的模型用途引用
  → 解析当前环境的真实配置
  → Provider 转换为供应商请求
  → 模型服务
  → Provider 转换响应或错误
  → 统一调用结果
```

这条递进不是为了把一次 HTTP 请求包装得越来越复杂，而是每增加一层都吸收一个已经出现的变化点。

### 第一层：SDK 直调只证明“现在能通”

最小调用直接传入密钥、端点、模型名、消息和参数，再从供应商对象中取出文本。它适合验证账号、网络和最小请求，但业务会同时接触秘密配置、供应商对象和返回细节。

一旦第二个模块也要调用模型，复制就开始出现：两个入口可能使用不同默认参数，记录不同字段，也可能用不同方式解释同一个远端错误。

### 第二层：秘密配置解决泄露，不解决用途漂移

把密钥移出业务代码是必要边界，但这只解决“秘密从哪里来”。模型名、端点、默认参数和能力假设如果仍散落在调用方，切换开发环境或展示环境时仍要到处修改。

### 第三层：集中模型配置形成可比较事实

集中配置把实际模型、端点、默认参数和能力声明放在同一位置。它让一次运行可以留下完整配置身份，但业务如果仍引用具体模型名，业务用途和供应商事实依然绑在一起。

### 第四层：用途引用把业务语义与供应商事实分开

业务真正想表达的通常不是“调用某个具体型号”，而是“执行日常评审”“生成结构化结果”或“生成 Embedding”。稳定用途引用表达前者，模型配置决定后者。

这和前端路由名相似：业务依赖稳定路由语义，构建和运行环境决定它最终指向哪个实现。用途引用不应按供应商命名，否则供应商变化仍会泄漏到业务。

### 第五层：统一响应和错误让调用可被系统消费

即使请求入口稳定，若上层仍直接读取不同 SDK 的响应对象和异常类型，比较、日志和错误处理仍会分叉。最后一层因此需要把成功和失败都还原为应用自己的语言。

这条链上的对象承担不同责任：

| 对象 | 回答的问题 | 不应承担 |
| --- | --- | --- |
| 模型用途引用 | 业务需要聊天、结构化生成还是 Embedding | 具体供应商 SDK 细节 |
| 模型配置 | 当前环境使用哪个模型、端点和默认参数 | 业务判断 |
| Provider | 怎样与某类供应商协议交互 | 决定产品任务 |
| 统一结果 | 本次实际用了什么、返回什么、消耗多少、是否失败 | 隐藏原始失败 |

用途引用的关键价值是稳定。业务可以表达“日常评审模型”或“结构化生成模型”，而不把某个供应商型号写成业务语义。底层模型变化时，任务身份不随之漂移。

## 一个完整场景：开发、展示和结构化任务

需求评审助手在开发阶段可能优先使用成本较低的模型，作品展示时可能选择效果更强的模型，结构化风险生成又可能需要明确支持 Schema 的模型。

如果业务直接保存具体模型名，这三种需要会演变成全局搜索和手工替换。漏改通常不会产生语法错误，而会表现为难以解释的质量漂移：同一个评审入口突然更慢、字段更不稳定，或只有某条路径继续使用旧模型。

稳定用途引用让业务入口保持不变，配置层决定当前环境中每种用途对应的真实模型。它并不保证模型行为一致，但能保证变化位置明确，运行记录也能说明本次实际发生了什么。

## 一次调用的完整生命周期

### 1. 业务形成请求意图

业务先确定消息、模型用途和本轮确实需要覆盖的参数。模型选择不应由页面、RAG 节点或 Agent 各自决定，否则同一任务会出现不可解释的配置漂移。

消息通常包含三种角色：

| 角色 | 主要来源 | 责任 |
| --- | --- | --- |
| system | 应用 | 任务身份和最高层边界 |
| user | 用户或应用 | 本轮问题与业务材料 |
| assistant | 历史模型结果 | 多轮上下文中的既有回复 |

本课程当前使用的无状态模型调用不会替应用保存完整会话。多轮调用需要应用明确选择哪些历史消息再次进入请求；长期状态、摘要和记忆属于后续 Conversation 与 Memory 机制。

这里要避免把 `messages` 当成普通字符串数组。不同角色表达不同控制来源：应用规则、用户问题和历史回复不能互相冒充。尤其进入 Agent 以后，网页、文件和 Tool Result 即使出现在消息里，也仍是不可信内容，不能自动升级为系统规则。

### 2. 配置层解析真实调用事实

稳定用途引用需要解析为实际模型、端点、能力标签、默认参数和秘密配置来源。秘密值与普通配置必须分离：前者不进入仓库，后者可以版本化和比较。

配置层还要守住模型角色。Chat、Embedding 和 Rerank 的输入输出不同，不能因为它们来自同一供应商就混用。错误的角色应在请求发出前暴露，而不是等待远端返回难以理解的协议错误。

### 3. Provider 吸收供应商差异

Provider 将统一请求转换为供应商协议，并把响应、用量和异常转换回应用契约。它吸收的是连接差异，不是业务差异。

所谓 OpenAI-compatible，只表示某些请求和响应形状相近，不代表所有平台都支持相同的结构化输出、Tool Calling、流式事件、上下文长度或错误码。普通 Chat 可用，不能推出其他能力也可用。

### 4. 统一结果保留调用身份

业务不能只取得文本。一次可比较的结果至少应保留：

- 生成内容；
- 实际模型与稳定用途引用；
- token 用量或供应商可提供的等价数据；
- 总耗时；
- 完成原因；
- 结构化错误；
- 必要的调用追踪身份。

如果结果不保存配置身份，之后看到质量、成本或延迟变化时，就无法判断究竟改变了模型、Prompt、参数还是供应商。

阅读一次结果时，学习者最容易只看生成内容。这样会把模型调用误解为“聊天成功了”。应用视角还要同时读取三类事实：

- **业务结果**：模型生成了什么。
- **调用身份**：任务请求了哪种用途，实际命中了哪个模型和供应商。
- **运行事实**：消耗、耗时、完成原因和错误是什么。

后续任何对照都建立在这三类事实同时存在的基础上。文本更好看，但模型身份或输入预算已经变化，就不能把差异全部归因于 Prompt。

## 参数应该由哪一层控制

模型名、端点和通用默认值属于配置；业务只覆盖本轮有明确原因的参数。

| 参数或事实 | 主要所有者 | 原因 |
| --- | --- | --- |
| 模型与端点 | 模型配置 | 环境和供应商可变化 |
| 默认采样参数 | 模型配置或任务配置 | 需要稳定复现 |
| 本轮最大输出 | 业务任务 | 与本轮结果预算有关 |
| 消息与材料 | 业务任务 | 表达真实输入 |
| 密钥 | 秘密配置 | 不进入日志和版本库 |

参数覆盖也应进入调用记录。否则“同一个模型同一个 Prompt”仍可能因为温度或输出上限不同而不可比较。

## 需求评审助手中的真实作用

同一产品会逐步增加风险识别、结构化输出、RAG 生成、Agent 决策和评估回放。它们可以使用不同模型用途，但都必须经过同一调用边界。

这样做使前端和运行记录能够稳定回答：

- 当前任务正在调用哪类模型能力；
- 本次实际命中了哪个模型配置；
- 花费了多少 token 和时间；
- 失败发生在鉴权、限流、超时、能力匹配还是响应处理；
- 切换供应商后，业务结果契约是否仍保持不变。

这不是为了预建“大模型平台”，而是为了让后续能力共享一个最小、可观察、可替换的基础。

从 AI Native 界面看，这一层还决定前端能否显示真实状态。若后端只返回最终文本，界面只能展示一个无法解释的转圈；若调用结果保留阶段和身份，界面才能区分正在调用、供应商限流、能力不支持和输出不可用。

## 失败应按调用阶段定位

| 表现 | 更可能的阶段 | 判断重点 |
| --- | --- | --- |
| 请求前就提示缺少密钥 | 配置或鉴权准备 | 秘密来源是否与当前配置匹配 |
| 调用返回 401 / 403 | 远端鉴权 | Key、端点和权限是否属于同一服务 |
| 偶发 429 | 限流 | 配额、并发和发生时段；不能当成内容错误 |
| Chat 配置被用于 Embedding | 能力匹配 | 模型角色是否在本地提前校验 |
| 普通 Chat 成功、Schema 模式失败 | 供应商能力 | 兼容接口不等于能力完整 |
| 有内容但缺少用量或调用身份 | 结果归一化 | 是否绕过统一调用边界 |

鉴权失败通常不应自动重试；限流和暂时性网络错误可能适合有限重试；能力不支持需要换配置或调整策略。完整重试、降级和失败报告由可靠调用机制继续展开。

这张表不是要求本节完成全部恢复策略，而是训练按阶段定位：请求是否形成、是否到达远端、远端是否接受、响应是否能转换。若一看到失败就先修改 Prompt，或者一看到 429 就判断业务输入有问题，定位链已经错位。

## 为什么当前只做最小调用层

统一调用层可以继续加入重试、缓存、成本统计、流式、Tool Calling 和 Harness，但本节不一次装入这些能力。此时真正需要看清的是三个不变量：配置如何集中、供应商差异如何被隔离、结果如何被观察。

过早建设“大而全 LLM Service”会让学习者看到很多模块，却不知道每个模块是被什么问题逼出来的。后续能力应该在真实问题出现时加厚同一个边界，而不是提前预建所有设施。

反过来，一次性连通脚本也不一定需要完整抽象。如果目标只是验证某个模型今天能否回答一个问题，SDK 直调已经足够。只有当调用会被多个业务入口复用、需要切换配置或需要比较运行事实时，这层抽象才产生明确收益。

## Provider 抽象的自然边界

Provider 可以统一调用形状和错误语言，但不能让不同模型变得等价。切换模型后，质量、成本、延迟、上下文限制和能力支持仍可能变化，需要真实对照。

它也不负责：

- 设计 Prompt；
- 判断结构化内容是否符合业务；
- 检索知识或校验 Citation；
- 决定 Agent 是否调用 Tool；
- 保存完整会话；
- 用假结果掩盖真实服务失败。

一次性连通性脚本可以直接使用 SDK；当同一产品有多个调用入口、需要切换模型或需要统一观察时，稳定边界才值得存在。

常见误区包括：

| 误区 | 为什么不成立 |
| --- | --- |
| 有相同 API 形状就等于相同模型能力 | 结构化输出、Tool、流式、限额和错误行为仍可能不同 |
| 有了统一客户端就不需要记录实际模型 | 抽象不能抹掉真实运行差异 |
| 用途引用可以随意命名 | 名称承担业务语义，按供应商命名会重新形成耦合 |
| 多轮 API 会自动记住历史 | 历史选择和持久化仍由应用负责 |
| 统一调用层应该处理所有 LLM 问题 | Prompt、检索、业务校验和 Agent 控制属于其他边界 |

## 用实验验证什么

配套实验使用相同输入切换真实配置。重点不是比较哪段回答更漂亮，而是验证：业务调用意图是否不变、实际配置身份是否被记录、统一结果字段是否稳定、真实错误是否清晰暴露。安装、运行、日志、读码和修改任务全部放在[实验篇](003.model-api-and-provider.lab.md)。

## 掌握标准

完成本节后，应能：

1. 画出业务请求经过配置、Provider、模型服务和统一结果的链路。
2. 解释用途引用、真实模型配置和 Provider 为什么不能合并成一个概念。
3. 说明 OpenAI-compatible 为什么不等于能力完全一致。
4. 根据错误发生阶段判断应检查配置、供应商能力还是结果归一化。
5. 判断哪些变化应被调用层吸收，哪些仍需业务和评估处理。

本节交付的是后续 Prompt、Structured Output、RAG 和 Agent 共用的模型调用边界，不是完整的可靠性、会话或质量平台。完成实验后回到[标准学习路径](../learning-path.md)。
