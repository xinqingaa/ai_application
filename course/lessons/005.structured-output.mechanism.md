# Structured Output 与应用侧校验

> 机制篇：解释模型文本怎样经过格式、Schema 和业务校验，成为应用敢于消费的结构化结果。
>
> 课程位置见[标准学习路径](../learning-path.md)。前置是 Prompt 的任务与输出描述；模式切换、失败复现、日志和读码见[配套实验](005.structured-output.lab.md)。

## 为什么“请输出 JSON”不是数据契约

人能看懂的回答不一定能被程序使用；能解析的 JSON 也不一定符合业务字段。模型可能返回 Markdown 围栏、裸数组、中文字段名、错误枚举、缺失字段或额外解释。

需求评审结果还要进入前端卡片、数据库、评估和后续运行节点。若任何一层把“看起来像 JSON”当成“已经可信”，失败就会在离模型更远的位置出现，更难定位。

Structured Output 真正要回答：

1. 字段契约由谁定义；
2. 生成阶段能施加多强的约束；
3. 应用收到结果后怎样校验；
4. 失败发生在 API、JSON、Schema 还是业务内容层。

例如模型返回：

```text
以下是评审结果：
[
  {"category": "api", "severity": "严重", "description": "……"}
]
```

人可以理解，程序却至少遇到四个问题：前缀导致整体不是 JSON，根形态可能不是产品约定的对象，`severity` 不一定是有效枚举，内容也没有证明来自本轮证据。这个例子说明“结构化”不是外观，而是逐层取得应用信任。

本节也不是要求所有 AI 应用照搬同一份风险 Schema。需要保留的是方法：先定义下游真正能消费的业务对象，再让模型尽量按该对象生成，最后由应用校验并保留失败阶段。

## 从自由文本到应用契约

结构化结果要经过多层边界：

```text
Prompt 描述输出意图
  → 模型 API 可选的格式或 Schema 约束
  → 模型原始响应
  → JSON 解析
  → 应用 Schema 校验
  → 业务规则校验
  → 下游消费
```

每层解决不同问题：

| 层 | 能保证什么 | 不能保证什么 |
| --- | --- | --- |
| Prompt | 模型知道期望字段和表达 | 一定返回合法 JSON |
| JSON Mode | 返回合法 JSON 对象 | 字段、类型和枚举正确 |
| JSON Schema 生成约束 | 平台支持时减少字段漂移 | 内容事实正确；所有平台都支持 |
| 应用 Schema | 字段、类型、枚举和根形态满足契约 | 引用真实、结论合理 |
| 业务校验 | 领域规则和来源关系成立 | 所有质量维度都优秀 |

越靠前的约束能减少无效输出，越靠后的校验越接近应用信任边界。生成约束不能代替本地校验，因为供应商能力可能变化，模型仍可能失败，业务规则也超出通用 Schema。

## 六层递进为什么不能跳步

### 第一层：自由文本只适合人读

自由文本允许模型自然表达，但程序无法稳定提取风险标题、等级和来源。前端若依赖 Markdown 结构猜字段，模型只要改变标题或列表格式就会破坏消费端。

### 第二层：Prompt 中描述 JSON 是软约束

明确字段名和枚举能提高结构稳定性，却不能阻止模型添加解释、改用中文字段、返回裸数组或输出近义枚举。Prompt 告诉模型希望怎样说话，但没有建立应用拒绝不合格结果的能力。

### 第三层：JSON Mode 只守语法边界

JSON Mode 通常能减少围栏和多余说明，但一个完全合法的 JSON 对象仍可能使用错误字段和错误类型。它解决“是不是 JSON”，不解决“是不是这份业务对象”。

### 第四层：JSON Schema 把字段约束前移

供应商支持时，可以在生成阶段限制根形态、字段、类型和枚举。这样做减少无效输出，却新增了能力依赖：同样的 Schema 在不同模型或兼容平台上可能被拒绝或只得到部分支持。

### 第五层：应用 Schema 是最终结构信任边界

无论生成阶段使用多强约束，应用仍要用自己的 Schema 校验返回结果。原因很简单：业务最终承担结果，下游不能把信任外包给一个可能变化的远端能力。

### 第六层：业务规则决定“结构正确后能否使用”

字段和枚举全部合法，Citation 仍可能不存在，风险理由也可能与证据无关。结构校验通过只表示对象能够进入下一层，不表示它已经成为可信结论。

```text
自由文本
→ Prompt 软约束
→ JSON 语法约束
→ 可选生成 Schema
→ 应用 Schema
→ 业务与证据校验
```

这条链的重点不是永远选择最强模式，而是无论供应商提供什么能力，应用都保留自己的接受边界。

## 三种生成约束强度

### Prompt-only

只在任务协议中描述 JSON 字段。它跨平台、接入简单，但属于软约束。模型可能夹带解释、改变根形态或使用近义字段。

它适合作为最低能力基线，也能帮助判断 Prompt 对输出形状有多大影响；它不适合作为业务信任依据。

### JSON Mode

API 要求返回合法 JSON 对象。它减少语法失败，却不理解产品里的风险类别、必填字段和枚举。合法 JSON 仍可能无法进入业务。

因此从 Prompt-only 切换到 JSON Mode 后，最合理的预期是 JSON 解析错误减少，而不是所有 Schema 错误都消失。

### JSON Schema

将字段 Schema 前移到生成阶段。平台支持时，字段形状通常更稳定；不支持时可能在请求阶段直接失败。此时应判断供应商能力，而不是误以为本地解析器出错。

JSON Schema 也不是“质量模式”。它能限制 `level` 必须来自枚举，却不能判断模型选择 `high` 是否合理，也不能判断引用片段是否支持风险结论。

应用可以根据真实能力选择生成约束，但无论采用哪种模式，都要经过同一份本地 Schema。

## 一份最小风险结果契约

需求评审助手当前以根对象承载风险列表，便于未来在同级增加摘要、缺口或运行信息：

```json
{
  "risks": [
    {
      "title": "售后入口条件可能与订单状态机不一致",
      "category": "state_flow",
      "level": "medium",
      "rationale": "入口条件与允许发起售后的状态范围尚未形成同一契约。",
      "citations": [
        {"source_id": "order-state-rule", "excerpt": "仅满足指定状态的订单允许发起售后"}
      ]
    }
  ]
}
```

这份样例的学习重点不是具体字段数量，而是四个契约选择：

- 根形态稳定，不能一会儿对象、一会儿裸数组；
- 字段名和必填性稳定；
- 类别和等级使用有限枚举；
- Citation 仍只是模型声明，必须由后续 RAG 机制验证。

字段还体现了下游真实用途：

| 字段 | 为什么进入契约 | 仍需后续判断 |
| --- | --- | --- |
| `title` | 前端需要稳定卡片标题 | 标题是否准确、是否重复 |
| `category` | 支持分类、筛选和评估 | 分类是否符合业务语义 |
| `level` | 支持排序和人工关注 | 严重度是否判断合理 |
| `rationale` | 解释为什么形成风险 | 是否真正依据本轮材料 |
| `citations` | 保存模型声明的来源 | 来源是否存在并支持结论 |

Schema 不应把“希望生成三条风险”写成永恒的数组长度规则，因为条数属于任务策略，不是所有业务场景的结构事实。稳定形状进入 Schema，随任务变化的目标留在 Prompt 或业务配置。

根对象而不是裸数组也是一个有意取舍。它让结果以后可以增加摘要、证据状态或补充问题，同时不改变风险列表本身的责任。但“以后可能需要”不能成为无限扩字段的理由；只有真实消费者出现时才加厚契约。

## 单一契约怎样避免漂移

Prompt 输出说明、模型 API 的生成约束、本地 Schema 和前端消费必须描述同一份业务对象。若四处各写一版字段，改名或增加枚举时必然漂移。

“单一契约”不表示所有层都读取同一个文件，而是表示：有一个权威业务 Schema，其他表示由它生成或接受一致性检查。更改字段时，需要同时验证生成约束、解析、业务消费和固定失败样例。

最危险的漂移通常不是语法错误，而是两层都能运行却理解不同。例如 Prompt 仍要求 `severity`，应用 Schema 已改为 `level`；模型会稳定生成旧字段，本地也会稳定拒绝，团队却可能误以为模型能力下降。

## Prompt 与 Structured Output 为什么缺一不可

Prompt 让模型理解“为什么生成这些字段、依据什么生成”；Structured Output 让应用只接受符合契约的结果。

只有 Prompt 时，大多数输出可能看起来正确，但少数漂移会在前端或数据库暴露。只有 Schema 时，模型虽然知道字段形状，却不理解风险任务、证据边界和字段语义，内容失败会显著增加。

可以把它们看成前后两道门：Prompt 在生成前对齐任务意图，Schema 在生成后执行接受规则。任何一道门都不能承担另一道门的责任。

## 四类失败必须分开

### 1. API 层失败

请求在模型返回内容前就失败，例如供应商不支持 JSON Schema、参数格式不兼容、鉴权或限流。此时不存在可解析的模型正文，处理方向是模型能力与调用可靠性。

这种失败最容易被误诊为本地 Schema 写错。判断顺序应先确认是否取得了模型响应；没有响应时，JSON parser 和业务校验都还没有开始工作。

### 2. JSON 层失败

已经取得文本，但 JSON 语法不合法，例如混入 Markdown、额外解释、内容截断或根类型错误。应保留原始响应和解析错误，不能用空对象伪装成功。

自动截取第一对花括号有时能“救回”输出，却可能吞掉模型的拒答、警告或多段内容，因此不能默认把修复后的对象当作原始成功。

### 3. Schema 层失败

JSON 合法，但字段、类型、枚举或必填项不符合契约。此时要检查 Prompt 输出描述是否与 Schema 一致，以及示例是否诱导了旧字段。

若相同字段每次都失败，盲目重试通常不会改变结果；应先检查契约是否漂移。若只是偶发截断或格式噪声，才可能在严格预算内考虑重试。

### 4. 契约通过但内容质量差

所有字段都合法，结论仍可能空泛，Citation 也可能指向不存在或不支持结论的来源。Schema 只证明形状可消费，不证明事实可信。这个问题要交给 RAG、Citation 校验、评估和人工判断。

这四类失败的处理方式不同：能力不支持不能靠改枚举修复，字段错误不应盲目重试，引用错误也不能靠增加 JSON 约束解决。

## 解析结果为什么要保留失败阶段

应用侧解析不应只返回“对象或空值”。一个可诊断结果至少要表达：

- 是否成功；
- 失败发生在 JSON 还是 Schema；
- 校验后的业务对象；
- 原始响应或安全摘要；
- 可定位的错误信息；
- 本次使用的生成约束模式。

下游只消费校验成功的对象，原始文本保留给调试和审计。这样前端不会误把解析失败显示成“没有风险”，评估也能区分模型遗漏和系统解析故障。

“没有风险”和“没有形成有效风险对象”必须是不同状态。前者是业务判断，后者是系统执行失败；如果都表示为空列表，用户、日志和评估都会得到错误事实。

## 与 Prompt、RAG 和可靠性的边界

| 机制 | 负责 | 不负责 |
| --- | --- | --- |
| Prompt | 描述任务和输出意图 | 强制字段合法 |
| Structured Output | 生成约束、解析和 Schema 校验 | 判断证据是否支持结论 |
| RAG / Citation | 提供并验证来源 | 修复 JSON 语法 |
| Reliability | 控制调用失败、重试和降级 | 把无效结构伪装成成功 |

结构化失败是否重试还要看原因。偶发截断可能适合有限重试；稳定的枚举漂移更可能需要修复 Prompt 或 Schema；供应商不支持某种模式应切换明确配置或约束策略，并把降级记录下来。

## 设计 Schema 时常见的两个极端

Schema 太松时，字段看似存在但下游仍要猜含义；Schema 太重时，模型被迫一次生成复杂嵌套对象，任何小错误都让整份结果失败。

初始契约应围绕产品当前真实消费建立：风险标题、类别、等级、理由和来源声明已经足够观察完整链路。只有产品确实需要新字段，并且生成、校验、界面和评估都能承接时，才继续扩展。

常见误区包括：

| 误区 | 正确边界 |
| --- | --- |
| 使用 JSON Mode 后可以省略本地 Schema | JSON 合法不代表业务字段合法 |
| API 拒绝 JSON Schema 就说明解析器有问题 | 请求阶段失败尚未进入解析 |
| Schema 失败多重试几次就会好 | 稳定契约漂移需要修契约或 Prompt |
| Schema 通过说明 Citation 可信 | Schema 只能验证 Citation 的形状 |
| 字段越多，结构化能力越完整 | 复杂契约会增加生成失败和维护成本 |

## 用实验验证什么

配套实验固定 Prompt、样例、模型和采样参数，只切换生成约束强度，并稳定复现 JSON 与 Schema 失败。重点是判断失败层，而不是证明某个模式永远最好。运行、日志、读码和修改任务全部放在[实验篇](005.structured-output.lab.md)。

## 掌握标准

完成本节后，应能：

1. 解释合法 JSON、Schema 通过和业务可信之间的差别。
2. 画出 Prompt、生成约束、本地校验和业务消费的完整链路。
3. 根据现象区分 API、JSON、Schema 和内容质量失败。
4. 说明为什么供应商的 JSON Schema 支持不能替代应用校验。
5. 判断某条规则应进入 Schema、Prompt 还是业务校验。
6. 设计失败结果，使前端、日志和评估不会把它误读为成功。

本节交付的是可进入业务的结果契约，不是事实正确性保证。完成实验后回到[标准学习路径](../learning-path.md)。
