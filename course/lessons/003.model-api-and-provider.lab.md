# 真实模型调用与 Provider 实验

配套机制：[Model API、调用生命周期与 Provider 抽象](003.model-api-and-provider.mechanism.md)。本实验先运行 SDK 直调基线，再观察同一业务调用怎样通过 `config_ref` 进入 Provider，并验证供应商变化不应迫使业务代码改写。

本实验能证明调用契约、配置身份、真实响应和错误是否可观察，不能证明某个模型的需求评审质量更好。

## 1. 准备真实调用

在仓库根目录执行：

```bash
uv sync
cp .env.example .env
```

在 `.env` 中至少配置 `OPENAI_API_KEY`。使用 OpenAI-compatible 服务时，再按实际服务配置 `OPENAI_BASE_URL`、`OPENAI_MODEL` 和模型配置所需变量。不要把真实 Key 写入命令、课程文档或 Git。

模型配置真源位于 `source/packages/llm_core/config/models.yaml`。开始前确认：

- `chat.dev_chat` 和准备比较的其他 `config_ref` 存在。
- 配置引用的环境变量已经设置。
- 目标模型支持当前 Chat 能力。
- 网络、鉴权和额度允许一次真实请求。

## 2. 先跑 SDK 直调基线

```bash
uv run python source/demos/llm_invoke_lab/first_chat.py
uv run python source/demos/llm_invoke_lab/first_chat.py --temperature 0.7
uv run python source/demos/llm_invoke_lab/first_chat.py --sample S3
```

运行前预测：改变 `temperature` 可能改变文本内容，但不应改变输入样例身份；改变 `sample` 会改变业务输入。观察：

- `sample`、`model` 和 `temperature`。
- 返回模型身份。
- `prompt_tokens`、`completion_tokens` 和总 Token。
- `latency_ms`。
- 内容预览。

这条脚本直接使用 SDK，是用来观察业务代码会如何接触供应商对象的对照，不是项目推荐入口。

## 3. 再通过统一客户端调用

```bash
uv run python source/demos/llm_invoke_lab/provider_switching.py
uv run python source/demos/llm_invoke_lab/provider_switching.py --verbose
uv run python source/demos/llm_invoke_lab/provider_switching.py \
  --configs chat.dev_chat,chat.structured_chat
```

可用参数：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `--sample` | `S2` | 选择固定业务样例 |
| `--configs` | 两个 Chat 配置 | 逗号分隔需要比较的 `config_ref` |
| `--temperature` | 使用配置默认值 | 对所有配置覆盖同一个 temperature |
| `--verbose` | 关闭 | 展开 messages 和最终请求参数 |
| `--log-format json` | compact | 输出 JSON Lines，便于脚本处理 |

第一轮固定 `sample` 和 temperature，只改变 `config_ref`。记录：

- 业务入口是否仍然是一次 `client.chat(...)`。
- 每个结果返回的 `config_ref`、provider 和 model 是否与预期一致。
- usage 与 latency 是否可读。
- Provider 错误是否转换为统一错误，而不是泄露无法处理的 SDK 对象。

## 4. 怎样读输出

| 区域或字段 | 回答的问题 |
| --- | --- |
| experiment header | 本轮样例、配置和主要变量是什么 |
| messages / params | 实际发出了什么；只在 verbose 展开 |
| provider / model / config_ref | 请求最终进入哪个配置和服务 |
| usage / latency | 本次调用消耗和耗时是多少 |
| API error | 供应商调用在哪类错误上失败 |

两个模型文本不同不等于 Provider 抽象失败；业务调用入口、统一响应和错误边界保持稳定才是本实验观察重点。

## 5. 失败时按层排查

| 表现 | 优先检查 | 验证方式 |
| --- | --- | --- |
| 未配置 Key | 根 `.env` 和模型配置引用 | 确认变量存在但不要打印值 |
| `config_ref` 不存在 | `models.yaml` 中的 section 与 name | 使用脚本默认配置重新运行 |
| 鉴权失败 | Key、Base URL 和服务账号 | 保留真实错误，不切 Mock |
| 模型不存在或能力不支持 | 配置中的模型名和服务能力 | 使用服务实际支持的模型配置 |
| 超时或限流 | 网络、额度、服务状态 | 记录错误类型和本轮配置，不无限重试 |
| 两个配置结果无法比较 | 同时改变了 sample 或 temperature | 恢复固定输入，只改变 `config_ref` |

## 6. 读码顺序

1. `source/demos/llm_invoke_lab/first_chat.py`：直调 SDK 时调用者必须自己处理什么。
2. `source/demos/llm_invoke_lab/provider_switching.py`：业务调用者传入什么、读取什么。
3. `source/packages/llm_core/client/service.py`：统一公共入口怎样选择配置和 Provider。
4. `source/packages/llm_core/config/`：配置身份怎样解析。
5. `source/packages/llm_core/providers/`：供应商请求、响应和错误怎样转换。
6. `source/packages/llm_core/tests/test_client_structured.py` 与 `test_client_embed.py`：结构化调用和模型角色边界怎样被确定性守住。

第一次阅读只追踪 `chat.dev_chat` 的正常调用，不同时展开所有 Provider。

## 7. 修改与验证

选择一个修改：

- 用 `--temperature` 覆盖一个参数。
- 在已有配置中选择另一个真实 `config_ref`。
- 切换 `sample` 后再恢复同一 sample 比较。

修改前写下：哪些请求字段、模型结果、usage 或 latency 可能变化；业务入口和统一响应字段为什么不应变化。

运行确定性测试：

```bash
uv run pytest source/packages/llm_core/tests/test_client_structured.py \
  source/packages/llm_core/tests/test_client_embed.py -q
```

测试证明客户端的结构化调用和模型角色契约，不证明真实 Provider 当前可用。普通 Chat 主路径的真实可用性仍以本实验请求为准。
