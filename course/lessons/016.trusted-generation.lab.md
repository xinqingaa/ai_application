# 来源声明集合检查实验

> 这是[模型写了来源编号，为什么还不能直接相信](016.trusted-generation.mechanism.md)的实验篇。固定 Retriever 已经找到售后规则，Context Builder 也已经交出模型本轮可见的文字和允许声明的来源。本实验继续调用真实结构化模型，观察模型声明的 `source_id` 怎样被应用逐条检查。

本文只回答一个实验问题：保持资料、检索、Requirement、Context Policy、Prompt、Schema 和模型配置不变，只改变 Evidence 内容时，本轮允许集合、模型声明和生成状态会怎样变化？

本实验能证明当前环境中的真实 `Retrieval → Context → Structured Generation → Citation Candidate membership` 链能够运行，也能用确定性测试证明未知 ID、空集合和结构化失败的状态契约。它不能证明合法 ID 的内容支持某条风险，不能证明 Evidence 已经充分，也不能证明空 Evidence 时模型一定会拒答。

## 1. 固定输入为什么分成 Query 和 Requirement

第 14、15 节一直使用：

```text
资料：order_rules.md
Retrieval Query：surface_match=申请售后
范围：after_sale + reference_knowledge + current_evidence
```

第 16 节需要生成完整评审，因此还需要一份真正被评审的 Requirement：

```text
requirement case：after_sale_entry_v2
title：订单详情页新增申请售后入口
```

两者属于同一售后主题，但责任不同：

| 输入 | 作用 | 能否成为 Citation |
| --- | --- | --- |
| `surface_match=申请售后` | 固定上游检索表达，让第 14、15 节的候选基线保持不变 | 不直接进入生成结果 |
| `after_sale_entry_v2.requirement_text` | 本轮被评审的 PRD 片段 | 不能；它是评审对象，不是外部依据 |
| `order_rules.md` 的当前 Evidence | 提供订单状态、接口和客户端规则 | 只有最终装入 Context 的 Chunk 才可以声明 |

当前 demo 不再使用整段 PRD 同时充当 Retrieval Query。否则从第 15 节进入第 16 节时，Query、向量、路线排名和 allowlist 会一起改变，学习者无法判断差异来自上游还是生成。

## 2. 运行前准备

本实验承接[固定 Retriever 控制与诊断实验](014.retriever-contract.lab.md)和[Context 实验](015.context-engineering.lab.md)。先确认它们的真实基线可以完成，不要在本实验里用 Mock、内存候选或假向量补齐失败的上游。

需要：

- `DATABASE_URL` 指向已执行 `0001`、`0002` migration 的 PostgreSQL Database；
- 真实 Embedding endpoint、model 和 key 可用；
- `chat.structured_chat` 指向真实 Chat Provider；
- Provider 支持本次选择的 Structured Output 模式；
- 当前课程数据库没有同一资料的旧 Chunk 身份混入售后候选。

产品级 PostgreSQL 安装、Role、Database 和 migration 由[需求评审助手 README](../../source/apps/review_assistant/README.md#postgresql-本地准备)维护。本实验只做运行前核对。

在仓库根目录执行：

```bash
uv sync
set -a && source .env && set +a

psql "$DATABASE_URL" -c "SELECT current_database(), current_user, version();"
psql "$DATABASE_URL" -c "\d+ review_assistant.rag_chunks"
psql "$DATABASE_URL" -c "\d+ review_assistant.rag_chunk_embeddings"
psql "$DATABASE_URL" -c "SELECT extname, extversion FROM pg_extension WHERE extname = 'vector';"
```

再核对当前业务文档的 Chunk：

```bash
psql "$DATABASE_URL" -P pager=off -c "
SELECT chunk_id, document_id, document_version, left(content, 70) AS content
FROM review_assistant.rag_chunks
WHERE document_id = 'KR-ORDER-STATE'
ORDER BY document_version, chunk_id;
"
```

当前 fixture 经 structure-aware Chunking 会形成两个真实身份：订单状态规则 Chunk，以及接口与客户端约束 Chunk。demo 会幂等写入当前 Chunk 和 Embedding；它不执行 migration，也不清空数据库。若最终候选出现非当前 fixture 身份，程序返回 `1`，不会把脏数据导致的 allowlist 变化解释成生成行为。

当前 `uv.lock` 锁定的关键客户端版本可以这样核对：

```bash
uv run python -c 'import openai, pydantic, psycopg; print(openai.__version__, pydantic.__version__, psycopg.__version__)'
```

当前锁文件对应 `openai 2.44.0`、`pydantic 2.13.4`、`psycopg 3.3.4`。Provider 与模型不是写死的实验答案：运行时以日志中的 `provider`、`model`、`config` 为准。SDK 或 Provider 升级后必须重新验证 `json_schema` 能力、错误映射和真实输出，不能只看到普通 Chat 成功就推断结构化模式兼容。

## 3. 唯一主入口、固定配置和退出状态

唯一主入口是：

```bash

```

上游固定为第 15 节基线：

| 控制 | 固定值 |
| --- | --- |
| Retrieval Query | `surface_match=申请售后` |
| lexical `candidate_k` | `5` |
| dense `candidate_k` | `5` |
| 两路 threshold | `None` |
| `rrf_k` | `60` |
| `final_top_k` | `3` |
| Context Policy | `full_context` |
| Context 总预算 | `2200` |
| Evidence 分区预算 | `1000` |
| Prompt | `review.risk_review@5.0.0` |

本节不提供 `candidate_k`、`final_top_k` 或 Evidence budget 参数。要观察检索名单变化回到第 14 节；要观察装入预算变化回到第 15 节。

主入口参数：

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `--variants` | 三种全跑 | 选择一个或多个 Evidence 变体 |
| `--structured-mode` | `json_schema` | 选择 Provider 侧结构约束模式 |
| `--config-ref` | `chat.structured_chat` | 选择真实 Chat 配置 |
| `--log-format` | `compact` | 可切换 `verbose`、`json` 或 `quiet` |
| `--verbose` | 关闭 | 展开 Context、原始结构化响应和逐条声明检查 |

查看实际入口：

```bash
uv run python source/demos/rag_retrieval_lab/inspect_trusted_generation.py --help
```

退出状态区分“实验是否完成”和“模型结果是否业务成功”：

| 状态 | 含义 |
| ---: | --- |
| `0` | 所有选定 variant 都完成真实调用，并形成结构化生成报告；其中某个 `GenerationStatus` 可以是非成功观察结果 |
| `1` | 输入、配置、数据库、Embedding、Retriever 清洁度、Chat Provider 或 Structured Output 使实验未完成 |

例如 `empty_evidence` 中模型编造一个 ID，业务状态应是 `unknown_citation_source`，但实验已经成功观察到该边界，所以进程可以返回 `0`。鉴权失败或 Provider 根本没有返回响应则返回 `1`。不能只看 shell 退出码判断评审结果是否可信。

## 4. 唯一主要变量：模型看到什么 Evidence

三组 Context 共用同一个 Requirement 和同一份 `full_context` Policy，只改变 Evidence：

| variant | Evidence | Citation Candidate 运行前预测 |
| --- | --- | --- |
| `rag_evidence` | 真实 Retriever 找到并由 Context Builder 装入的售后 Chunk | 当前两个稳定 `chunk_id` |
| `normal_noise` | 合法格式的营销活动入口规则 | 只有 `KR-CAMPAIGN-ENTRY-NOISE` |
| `empty_evidence` | 无 Evidence | 空集合 |

`normal_noise` 是生成层探针：它由 Context Builder 显式装入，不写入售后检索范围，也不是 Retriever 自然召回结果。它不能证明 Metadata Filter 失效。三组也不是质量验收集，只是观察生成边界的探索对照。

比较时不要同时切换模型或 Structured Mode。每次运行真实模型的具体风险可能不同，因此预测重点是 allowlist、声明资格和状态规则，不是风险数量或措辞。

## 5. 先运行真实 RAG Evidence

先只跑基线：

```bash
uv run python source/demos/rag_retrieval_lab/inspect_trusted_generation.py \
  --variants rag_evidence \
  --verbose
```

运行前写下预测：

```text
Retrieval Query 仍是 surface_match=申请售后
Requirement 是 after_sale_entry_v2 PRD
Retriever 配置与第 15 节相同
Context Policy 是 full_context
两个真实售后 Chunk 都进入 Evidence
allowlist 只包含这两个稳定 chunk_id
任何文档标题简称或新造 ID 都应成为 unknown_source
结构与全部已声明 ID 都通过时，状态才可能是 succeeded
```

不要预测“模型一定生成 N 条风险”或“一定引用两个 Chunk”。真实模型可以只指出 Requirement 自身缺失，这类风险可以没有 citation；本节需要观察它实际做了什么。

### 5.1 先核对运行身份

按顺序确认：

1. `dataset` 是 `rag-retrieval-exploration-1.0.0`；
2. `retrieval query` 是 `surface_match=申请售后`；
3. `requirement` 是 `after_sale_entry_v2`；
4. `retriever config` 在后续三组对照中不变；
5. `context policy` 是 `full_context`，Evidence budget 为 `1000`；
6. `prompt` 是 `review.risk_review@5.0.0`；
7. `provider`、`model`、`config` 与 `structured_mode` 符合本轮真实配置。

其中任一身份变化，都不能再把结果差异只归因于 Evidence。

### 5.2 再看模型真正拿到了什么

`--verbose` 下先找：

```text
included source ids
→ citation candidates
→ context tokens
→ model-visible Context block
```

两个集合通常相同，因为本轮只有当前 Evidence。若 Retrieval 有两个候选，但这里只剩一个，回到 `ContextBuildReport` 和第 15 节，而不是先改 Prompt。

### 5.3 最后看声明怎样被检查

继续按顺序读取：

```text
raw structured response
→ parsed risks
→ claims
→ claim 1.1: source_id → candidate / unknown_source
→ generation status
```

看到 `candidate` 只能解释为“这个原始 ID 属于本轮 allowlist”。不能改写为“这条引用正确”或“该风险已经获得支持”。

## 6. 再做 Evidence 单变量对照

分别运行噪声与空 Evidence：

```bash
uv run python source/demos/rag_retrieval_lab/inspect_trusted_generation.py \
  --variants normal_noise \
  --verbose

uv run python source/demos/rag_retrieval_lab/inspect_trusted_generation.py \
  --variants empty_evidence \
  --verbose
```

最后才一次并排运行三组：

```bash
uv run python source/demos/rag_retrieval_lab/inspect_trusted_generation.py \
  --variants rag_evidence,normal_noise,empty_evidence
```

### 6.1 `normal_noise` 应怎样读

运行前预测：

```text
Requirement 不变
allowlist = [KR-CAMPAIGN-ENTRY-NOISE]
若模型声明该 ID，membership 可以通过
即使通过，也不能说明营销活动规则支持售后接口结论
若模型生成真实售后 chunk_id，它反而应该是 unknown_source
```

这个变体专门打断一个错误推论：

```text
来源身份合法
≠
来源内容支持当前风险
```

是否错误使用噪声，需要阅读风险、rationale 和 Evidence 内容，或交给后续 Citation 支持性机制；单看 `candidate_claim_count` 无法自动判断。

### 6.2 `empty_evidence` 应怎样读

运行前预测：

```text
included Evidence = 0
allowlist = []
任何 claimed source_id 都是 unknown_source
模型可以指出 Requirement 自身明确缺失
没有 citation 的 succeeded 不等于模型学会了拒答
```

需要同时观察两种真实可能：

- 模型保持 citations 为空，结构合法，当前状态可能 `succeeded`；
- 模型仍编造 source ID，当前状态是 `unknown_citation_source`。

两种结果都不能单独证明证据充分性或 Refusal 策略已经完成。

## 7. 三种状态和 shell 退出码不要混用

每个 variant 都有自己的 `GenerationStatus`：

| 状态 | 已知事实 | 未知事实 |
| --- | --- | --- |
| `succeeded` | 结构合法，所有已声明 ID 都在 allowlist | 是否遗漏应有 citation、内容是否支持、证据是否充分 |
| `structured_output_invalid` | Provider 返回了内容，但 JSON 或 Schema 解析失败 | 如果重新生成是否会改善质量 |
| `unknown_citation_source` | 结构合法，至少一个声明 ID 越界 | 模型为什么改写或编造 ID |

Provider 调用之前或期间的鉴权、限流、超时、404、配置角色错误和能力不支持不属于这三种状态。它们以真实 `LLMError` 使实验退出 `1`。

## 8. Structured Mode 是另一条独立对照

Evidence 对照完成后，若 Provider 支持，可以只用 `rag_evidence` 比较本地解析仍然存在时，模型侧约束模式怎样变化：

```bash
uv run python source/demos/rag_retrieval_lab/inspect_trusted_generation.py \
  --variants rag_evidence \
  --structured-mode json_object \
  --verbose
```

这次唯一变量变成 Structured Mode，不再与三种 Evidence 结论合并。两种模式都要经过本地 `ReviewRiskList` 校验：

- `json_schema` 请求 Provider 使用严格 JSON Schema；
- `json_object` 只请求 JSON 对象，字段、类型和枚举仍由本地 Pydantic 检查。

Provider 不支持 `json_schema` 时保留真实能力错误。`json_object` 成功不能被写成“同一 Provider 的 `json_schema` 已通过”。

## 9. 保存 JSON Lines 记录

运行：

```bash
uv run python source/demos/rag_retrieval_lab/inspect_trusted_generation.py \
  --log-format json
```

按事件读取：

| 事件 | 关键字段 |
| --- | --- |
| `trusted_generation.started` | dataset、Retrieval Query、Requirement case、Retriever 配置、Context Policy、真实候选 IDs |
| `trusted_generation.variant_observed` | variant、Provider、model、Prompt、Structured Mode、included IDs、allowlist、parse、risks、candidate/unknown 数量、状态 |
| `trusted_generation.completed` | 每个 variant 的最终 `GenerationStatus` |

`--log-format json` 始终输出 JSON Lines；同时传 `--verbose` 不会切回终端表格。保存运行记录时不要删除失败 variant，也不要看到结果后更换模型、Prompt 或样例并覆盖旧记录。

## 10. 三类边界证据不能混用

### 10.1 自然模型行为

三种 variant 都调用真实模型。它们能展示当前 Provider、模型和固定输入下的自然行为，不能代表所有输入的总体质量。

### 10.2 真实依赖失败

| 表现 | 发生层次 | 正确处理 |
| --- | --- | --- |
| 缺少 `DATABASE_URL` | 实验配置 | 返回 `1`，不生成静态 Context |
| PostgreSQL 或 migration 失败 | Retrieval 准备 | 暴露真实错误，不切内存候选 |
| Embedding 鉴权、限流或超时 | Query 准备 | 没有可信 RetrievalResult，不使用假向量 |
| Retriever 部分路线失败 | 固定上游 | 返回 `1`，先回到第 14 节排查 |
| 出现旧 Chunk 身份 | 数据准备 | 返回 `1`，不把 allowlist 漂移归因于模型 |
| Chat 鉴权、限流、超时或 404 | Provider 调用 | 保留 `LLMError`，不返回空 risks |
| Structured Mode 不支持 | Provider 能力 | 保留能力错误，另建模式对照 |

### 10.3 确定性契约测试

运行：

```bash
uv run pytest source/packages/rag_core/tests/test_trusted_generation.py -q
```

测试使用可控响应验证：

- 已知 ID 进入 `candidate`；
- 未知 ID 使状态变成 `unknown_citation_source`；
- 空 allowlist 下任何声明都被拒绝；
- 无 citation 风险不会自动变成未知来源；
- JSON / Schema 失败保留错误阶段；
- 合法 ID 搭配不受支持的 excerpt 仍只能通过 membership 边界。

这里的 Fake client 只稳定复现模型已经返回某段内容后的确定性状态机。它不证明真实 Provider 可用，也不证明模型会产生正确引用。

## 11. 按“表现 → 层次 → 验证”排查

| 表现 | 可能层次 | 验证方式 |
| --- | --- | --- |
| Retrieval Query 变成长 PRD | 实验输入 | 核对 `surface_match=申请售后` |
| Requirement 只剩“申请售后” | 生成输入 | 核对 `after_sale_entry_v2` case |
| 出现非当前 Chunk | 数据准备 | 对照 fixture IDs 和数据库行 |
| Retrieval 最终少于两个当前 Chunk | Retriever | 回查路线状态、融合和最终截断 |
| Retrieval 有两条，allowlist 只有一条 | Context Builder | 查看 included/dropped 与 Evidence budget |
| Prompt 没列出 allowlist | Prompt 变量装配 | 查看渲染后的 messages 与报告 |
| 原始内容不是 JSON | Structured Output | 查看 `parse_error_stage=json` |
| JSON 字段或枚举错误 | Schema | 查看 `parse_error_stage=schema` |
| 模型把标题简称当 ID | Prompt 遵循 / 模型 | 保留原始 ID，确认 `unknown_source`，不自动匹配 |
| 合法 ID 支持了错误结论 | Citation 支持性尚未完成 | 对照 Evidence 原文，记录后续问题 |
| 空 Evidence 仍输出强外部事实 | 证据充分性尚未完成 | 不把 membership `succeeded` 当可信结论 |
| shell 返回 `0` 但某 variant 非成功 | 结果读取 | 查看各 variant 的 `GenerationStatus`；`0` 只表示实验完成 |

遇到未知声明时沿反向链排查：

```text
claim check
→ 本轮 allowlist
→ rendered messages
→ ContextBuildReport
→ RetrievalReport
```

不要因为模型写了一个听起来合理的文档名，就反向假设 Retriever 曾经返回过它。

## 13. 修改任务：空集合不能接受任何声明

在 [`test_trusted_generation.py`](../../source/packages/rag_core/tests/test_trusted_generation.py) 中找到空 Evidence 的测试。新增或重新实现下面的契约 Case：

```text
Context：没有 Evidence
allowlist：[]
模型结构化输出：声明 invented-source
```

写测试前预测：

- Provider 调用边界仍然被执行；
- `evidence_state` 是 `no_citation_candidates`；
- parse 仍然成功；
- `candidate_claim_count = 0`；
- `unknown_source_count = 1`；
- 最终状态是 `unknown_citation_source`；
- 不能按标题或内容把 `invented-source` 自动替换成真实 Chunk；
- `ReviewRiskList`、Prompt 版本和已知 ID 的行为都不应变化。

验证：

```bash
uv run pytest \
  source/packages/rag_core/tests/test_trusted_generation.py::test_empty_allowlist_rejects_every_claimed_source_id \
  -q
```

再运行真实 `empty_evidence`，比较真实模型是否自然产生声明。确定性测试证明集合不变量；真实实验证明当前模型在空 Evidence 下实际做了什么。两者都不能证明证据充分性策略。

## 14. 完成检查点
