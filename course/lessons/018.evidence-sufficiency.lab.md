# 证据充分性、Refusal 与补充问题实验

> 这是[证据充分性、Refusal 与补充问题](018.evidence-sufficiency.mechanism.md)的配套实验。第 17 节已经负责验证单条 Citation 的真实位置与支持关系；本实验把 Claim、覆盖要求和这些已验证 Citation 固定为上游输入，只改变 active `knowledge_scope`，观察真实模型怎样判断覆盖，并怎样把缺口变成补充问题。
>
> 本实验能证明当前 Provider 在固定输入下形成了怎样的充分性报告，不能证明第 17 节的支持性质量、Retriever 的召回质量，或模型在所有业务范围中的判断质量。

## 1. 运行前准备

本实验不访问 PostgreSQL、Embedding 或 Retriever。需要：

- 根环境已经通过 `uv sync` 安装；
- `chat.structured_chat` 对应的真实 Chat Provider、模型与 Key 可用；
- Provider 支持当前选择的 Structured Output 模式；
- 当前 Prompt 与 fixture 能从安装后的 package 中读取。

在仓库根目录执行：

```bash
uv sync
set -a && source .env && set +a

uv run python -c 'import openai, pydantic; print(openai.__version__, pydantic.__version__)'
```

当前 `uv.lock` 对应的客户端版本只说明实验环境，不能保证 endpoint、模型、额度或账户权限可用。运行后仍要以输出中的 Provider、模型、配置和 Structured Output 模式为准。

查看探针身份与唯一变量：

```bash
uv run python -c '
import json
from pathlib import Path
p = Path("source/apps/review_assistant/fixtures/rag/generation/evidence_sufficiency_probes.json")
d = json.loads(p.read_text())
print(d["fixture_kind"], d["version"])

'
```

## 2. 唯一主入口、参数和退出状态

唯一主入口是：

```bash
uv run python source/demos/rag_retrieval_lab/inspect_evidence_sufficiency.py
```

查看实际参数：

```bash
uv run python source/demos/rag_retrieval_lab/inspect_evidence_sufficiency.py --help
```

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `--variants` | 三组全跑 | 选择完整范围、移除错误契约或空范围探针 |
| `--structured-mode` | `json_schema` | 选择 Provider 侧结构约束方式 |
| `--config-ref` | `chat.structured_chat` | 选择真实 Chat 配置 |
| `--log-format` | `compact` | 可切换 `verbose`、`json` 或 `quiet` |
| `--verbose` | 关闭 | 展开原始结构化响应 |

退出状态区分“实验是否完成”与“资料能否回答”：

| 状态 | 含义 |
| ---: | --- |
| `0` | 已得到 `answerable`、`partial`、`refusal`，或已明确观察到结构化结果校验失败。 |
| `1` | fixture、配置、鉴权、额度、网络或 Provider 使实验没有形成充分性报告。 |

`partial` 与 `refusal` 都是成功观察到的业务结果，不能让 shell 返回 `1`。相反，额度耗尽或网络失败没有完成真实判断，不能临时改用 Fake 模型继续主实验。

## 3. 冻结输入与唯一主要变量

三个探针共用：

- 两条 Claim：接口 `source_channel` 规则，以及网络错误/业务拒绝的展示差异；
- 两个覆盖要求：分别需要“接口规则”和“错误契约”角色的已验证 Citation；
- 相同 Prompt、模型配置和固定上游 Citation 输入形状。

唯一变化是 active `knowledge_scope`：

| variant | active source | 运行前预测 |
| --- | --- | --- |
| `full_scope` | `API-V2` + `ERROR-UX` | 两项均可覆盖，预期 `answerable`。 |
| `missing_error_contract` | 只保留 `API-V2` | 接口结论可用；错误展示出现 gap，预期 `partial`。 |
| `empty_scope` | 无来源 | 两项均无合格 Citation，预期 `refusal`，且不调用模型。 |

这里“移除文档”同时使它不能再作为本轮 active scope 中的 Citation 来源。Claim、覆盖要求和其他来源不变，因此你观察的是少一类关键资料造成的边界变化，而不是靠换问题、换 Prompt 或换模型制造结果。

不要预测模型 `reason` 的逐字措辞。真实模型可能用不同语言解释相同覆盖关系；本实验关心的是它是否回到正确的覆盖要求、Claim 与来源角色。

## 4. 先观察完整范围

```bash
uv run python source/demos/rag_retrieval_lab/inspect_evidence_sufficiency.py \
  --variants full_scope \
  --verbose
```

运行前预测：

```text
active sources = API-V2, ERROR-UX
model calls = 1
两个 coverage requirement 都有来自预期角色的 Citation 候选
observed decision 倾向 answerable
```

按顺序观察：

1. `active sources` 是否为两份固定资料；
2. 两个 Coverage 行是否都有正确的 `requirement_id`；
3. `covered` 是否只关联它允许的 Claim，而没有借用另一来源角色；
4. `observed decision` 是否为 `answerable`；
5. usage、成本和延迟是否属于这一次真实调用。

一次 `answerable` 只说明当前模型在固定材料、Prompt 与配置下观察到了充分覆盖；它不是对所有未来资料的质量承诺。

## 5. 只移除错误契约

```bash
uv run python source/demos/rag_retrieval_lab/inspect_evidence_sufficiency.py \
  --variants missing_error_contract \
  --verbose
```

运行前预测：

```text
source-channel 仍保持可覆盖
error-contract 没有预期角色的已验证 Citation
observed decision 倾向 partial
follow-up 指向“错误契约”与展示差异
```

重点不是看到一条总提示，而是验证两个不变量：

- `API-V2` 与它支持的接口结论不应因为另一份资料被移除而消失；
- gap 必须指向 `error-contract`、受影响的 `error-presentation` Claim 和可回答的补充问题。

若模型把接口 Citation 用来覆盖错误展示，先看输出中的 `citation_claim_ids`。`rag_core` 会拒绝错误的 Claim 或来源角色关联，而不是把它降级成普通 gap。

## 6. 再观察合法的空范围

```bash
uv run python source/demos/rag_retrieval_lab/inspect_evidence_sufficiency.py \
  --variants empty_scope \
  --verbose
```

运行前预测：

```text
active sources = （无）
model calls = 0
两个 coverage requirement 都是 gap
observed decision = refusal
```

这组不需要模型猜测：范围内没有任何预期角色的已验证 Citation，不能形成强结论。输出仍应列出两个补充问题，因此 `refusal` 不是空结果，也不是 Provider 故障。

## 7. 读输出时先看边界，再看模型理由

每个 variant 至少输出：

```text
expected decision
observed decision
active sources
validation status
model calls

Requirement → Coverage → Citation claims → Reason
follow-up
```

先核对 active source 与唯一变量，再核对 `requirement_id → Citation claims` 的映射，最后才阅读模型 `reason`。如果先被一段流畅理由说服，很容易忽略它是否越过了来源角色或 Claim 边界。

`empty_scope` 的 `model calls = 0` 是预期优化：这里已能确定没有合格 Citation。其余拥有候选 Citation 的项目会合并进一次真实结构化调用，避免为每个覆盖要求重复请求。

## 8. 真实失败、输出契约失败与资料不足

| 表现 | 先检查的层次 | 验证方式 |
| --- | --- | --- |
| 空范围得到 `refusal` | 资料边界 | 对照 `active sources` 与 `model calls = 0`；这不是失败。 |
| 移除 `ERROR-UX` 后接口 Claim 也变为 gap | fixture 变量或关联校验 | 对照 active scope 与 `citation_claim_ids`。 |
| 模型把错误契约缺口标为 `covered` | Prompt 或模型语义判断 | 阅读该来源的完整范围，保留观察记录，不改用假结果。 |
| `validation status = structured_output_invalid` | Provider 输出结构 | 查看 parse 错误；此时没有 `EvidenceDecision`。 |
| `validation status = judgment_set_invalid` | requirement 身份、Claim 或来源角色关联 | 检查是否少回、重复、乱序或越界关联。 |
| 鉴权、额度、限流、超时或网络错误 | 真实依赖 | 检查 `.env`、Provider 配置与错误日志；进程应返回 `1`。 |

不要把最后两类失败映射为 `refusal`。`refusal` 是充分性链已经完成后的资料结论；失败是本轮不知道结论能支撑到哪里。

## 9. 从入口读到测试

建议按这条路径读代码：

```text
inspect_evidence_sufficiency.py
→ rag_core.decide_evidence_sufficiency
→ rag_core/evidence/sufficiency.py
→ evidence_sufficiency_v1.yaml
→ test_evidence_sufficiency.py
```

- demo 只读取固定 fixture、选择 active scope，并显示本次真实观察；
- 公共入口接收 Claim、上游 `VerifiedCitation`、覆盖要求和限定来源，不重新检索；
- `sufficiency.py` 负责候选边界、身份与来源角色校验、确定性聚合和 gap 渲染；
- Prompt 只承担语义覆盖判断；
- 测试使用 Fake Client 固定输出，证明身份、聚合与失败契约，不证明真实模型质量。

运行确定性测试：

```bash
uv run pytest source/packages/rag_core/tests/test_evidence_sufficiency.py -q
```

测试覆盖：全部缺证据时不调用模型并得到 `refusal`、部分覆盖得到 `partial` 与问题、错误 Claim 映射不形成拒答、结构化失败不形成拒答。

## 10. 修改一个变量再验证

只编辑 fixture 中 `missing_error_contract` 的 `active_source_ids`：把 `ERROR-UX` 加回去。不要修改 Claim、覆盖要求、引文、Prompt 或模型配置。

然后运行：

```bash
uv run python source/demos/rag_retrieval_lab/inspect_evidence_sufficiency.py \
  --variants missing_error_contract \
  --verbose
```

预期变化：错误展示的 gap 与 follow-up 消失，整体结果倾向从 `partial` 变为 `answerable`。

不应变化：接口规则的 Claim、`API-V2` 的来源角色、固定 Prompt 身份，以及“没有合格 Citation 时不调用模型”的空范围契约。

完成后恢复 fixture，或使用 Git diff 确认只改动了这个唯一变量。这个修改只能证明 scope 对当前覆盖判断的影响；它不证明新增资料本身一定真实、完整或适用于所有需求。
