# 引文真的支持这条结论吗

> [来源声明集合检查](016.trusted-generation.mechanism.md)已经确认模型写出的 `source_id` 属于本轮允许集合。现在继续追一条通过检查的声明：模型给出的引文真的来自这个来源吗？即使原话存在，它是否在当前版本、业务范围和适用条件下支持这条具体说法？
>
> 本文交付一条两段校验链：确定性程序先把逐字引文唯一定位回来源原文，结构化模型再判断完整语境与具体说法之间的关系。本文不判断整份回答的证据是否充分，不决定 Refusal 或补充问题；运行、日志、失败复现和修改任务见[配套实验](017.citation-support.lab.md)。

## 从候选来源声明继续

来源进入模型输出之前已经经过检索、Context 装配和成员检查。三个交付物不能混成一份笼统的“检索结果”：最终检索名单回答模型可能看到什么，Context 记录模型实际看到什么，成员检查确认模型声明的编号有没有越界。

![第 14–16 节依次交付最终名单、允许集合和候选来源声明](../assets/017.citation-support.incoming-objects.svg)

*图：第 17 节只接收已经通过成员检查的候选来源声明，继续核对引文位置和内容支持关系。*

这里必须守住一个边界：合法 `source_id` 只告诉应用应该去哪里核对，不能证明模型写出的那句话存在，更不能证明来源支持当前结论。

## 一个合法编号仍然引用了不存在的话

继续使用“订单详情页新增申请售后入口”的 Requirement。模型给出：

```text
具体说法：现行售后接口 v2 的所有请求都必须提供 source_channel
source_id：B.chunk_id
excerpt：售后接口允许省略 source_channel
```

本轮允许集合确实包含 `B.chunk_id`，所以编号成员检查通过。但 B 的真实内容是：

```text
售后接口 v2 必须提供 source_channel。
Flutter 客户端必须使用相同的入口可见性规则。
```

模型写出的“允许省略”不在原文中，含义还与原文相反。如果应用看到合法编号就直接生成链接，它会把一条编造的引文包装成可回查证据。

解决这个问题需要两段责任不同的校验：

![Citation 支持性先定位逐字引文，再判断完整语境能否支持具体说法](../assets/017.citation-support.support-validation.svg)

*图：找不到或不能唯一定位的引文停在确定性结果；只有唯一定位成功的项目才进入内容支持判断，且只有“支持”形成经过支持性校验的 Citation。*

第一段回答“这句话是否真的在指定来源里”；第二段回答“把它放回完整语境后，能否证明当前说法”。两段不能颠倒：引文本身不存在时，没有必要让另一个模型猜它可能想引用哪句话。

## 第一段：定位原话，不替模型改写

定位器拿到四项输入：稳定的 `claim_id`、要核对的具体说法、已经通过成员检查的 `source_id`，以及模型给出的逐字 `excerpt`。它先按 `source_id` 取得对应来源，再在原文中查找引文。

当前实现保留五种定位结果：

| 定位结果 | 确定知道什么 | 后续动作 |
| --- | --- | --- |
| `located` | 引文在对应来源中恰好出现一次 | 保存位置，进入支持判断 |
| `quote_not_found` | 有引文，但有限归一化后仍找不到 | 停止，不调用判断模型 |
| `ambiguous_quote` | 同一句在来源中出现多次 | 保留歧义，不擅自选第一次 |
| `missing_excerpt` | 模型没有给出可定位引文 | 停止，不把整段来源当作引文 |
| `source_not_allowed` | 来源不在本轮允许集合或没有对应原文 | 停止，不扩大证据范围 |

### 有限归一化只消除排版差异

DOCX、PDF 和 Markdown 解析后，同一句话可能因换行、连续空白或全角字符产生表面差异。例如：

```text
请求必须提供 source_channel。

请求
必须提供 source_channel。

请求必须提供 ｓｏｕｒｃｅ＿ｃｈａｎｎｅｌ。
```

因此定位前可以执行固定 Unicode 兼容归一化、折叠连续空白，并去除首尾空白。它们只处理排版，不改变文字关系。

定位器不能把“必须”换成“应当”，不能忽略版本号、数字或否定词，也不能使用向量相似度从同义句中挑一条替代原始引文。否则应用是在替模型修复证据，而不是检查模型声明。

### 找到以后必须保留原文位置

`located` 不能只返回一个 `true`。检查还要保留来源定位信息、Chunk 内的 `char_start` 与 `char_end`、模型原始引文和匹配次数。这样界面和后续处理才能准确回到本次校验使用的文字。

如果 Context 中装入的是压缩副本，调用方可以另外提供未压缩的权威来源内容。字符范围应指向权威原文，而不是为了生成而裁剪的副本。

到这里仍只证明“原话存在且位置唯一”，没有证明它支持结论。

## 第二段：读取完整语境，再判断支持关系

一条风险可能同时包含产品判断、外部事实和影响推断。支持性校验不能笼统地问“这份资料是否支持整条风险”，而要先抽出一个可以独立判断、需要外部证据支持的具体说法。本文把它称为 **Claim**。

当前例子的 Claim 是：

```text
现行售后接口 v2 的所有请求都必须提供 source_channel。
```

判断器同时读取 Claim、逐字引文、引文所在的完整来源内容，以及来源版本、范围等 Metadata。只给它孤立引文不够，因为决定含义的限制条件可能就在引文前后。

![同一句引文放回不同版本和业务范围后得到四种支持关系](../assets/017.citation-support.semantic-relations.svg)

*图：关键词和逐字引文完全相同，也可能因为版本、范围、条件和反向规则不同而变成支持、反驳、无关或无法判断。*

四种关系在自然语言中分别是：

- **支持**：当前规则在适用条件下直接证明 Claim。
- **反驳**：来源明确给出与 Claim 相反的当前规则。
- **无关**：文字存在，但属于另一个主题或业务范围。
- **无法判断**：来源相关，却缺少范围、条件或版本，暂时不能确定。

实现为了稳定记录，把它们写成 `supported`、`contradicted`、`unrelated` 和 `indeterminate`。后三种不能压成一个 `false`：反驳是有方向的证据，无关通常表示取错材料，无法判断则指出仍缺少条件。

`indeterminate` 也不能承载校验器自身失败。鉴权失败、超时、非法 JSON 或漏回一条 Claim，表示判断没有完成，而不是资料含义“无法判断”。

### 为什么不能只靠字符串或相似度

字符串包含只能证明文字出现；Embedding 相似度只能证明主题接近。它们都无法稳定理解否定、例外、全部与部分、现行与废弃、v1 与 v2，以及售后渠道和营销渠道这类同名字段。

因此当前主路径采用组合方式：确定性程序负责可重复的引文定位，结构化模型只负责读取已给材料并判断关系。模型不能补充外部知识，输出还必须经过固定 Schema 和身份集合检查。

这里的模型属于产品运行中的业务校验链，不是后续用于评价模型整体质量的 LLM-as-Judge。二者可能都使用模型做判断，但输入、责任和结果用途不同。

## 先定位全部声明，再批量判断

一次生成可能包含多条风险，每条风险又可能声明多个来源。如果每条 Citation 都单独调用一次模型，调用次数会随声明数量增长。当前机制先对全部声明做确定性定位，再把定位成功的项目按稳定顺序合并为一次结构化请求。

![多条来源声明先经过确定性定位，再合并为一次支持判断](../assets/017.citation-support.batch-judgment.svg)

*图：定位失败的项目不进入模型；定位成功的项目只调用一次模型，返回的 `claim_id` 集合和顺序必须与输入完全一致。*

批量只改变调用组织方式，不降低逐条校验要求。模型少回、多回、重复或调换一个 `claim_id`，整批结果都会成为 `judgment_set_invalid`；应用不能把缺失项目默认为支持。

当本轮没有任何项目唯一定位成功时，支持判断模型不会被调用，报告仍以确定性定位结果完成。只要有可判断项目，模型调用次数就是一次，而不是 Citation 数量。

报告同时保留输入、定位、跳过和四种关系的计数，以及 Prompt、配置、Structured Mode、模型身份、Token、成本、延迟和解析失败阶段。只有唯一定位且 verdict 为 `supported` 的检查才进入 `VerifiedCitation`；其他关系和失败仍作为诊断事实保留在 `CitationSupportCheck` 中。

## 三类失败不能互相伪装

| 失败层次 | 表现 | 必须怎样暴露 |
| --- | --- | --- |
| 引文定位未通过 | 引文缺失、找不到、位置不唯一或来源不允许 | 保留逐条定位结果，不调用判断模型 |
| 支持判断结果无效 | JSON、Schema、枚举或返回身份集合不符合契约 | 不产生任何 `VerifiedCitation`，记录失败阶段 |
| 真实依赖失败 | 鉴权、额度、限流、超时、能力不支持或 Provider 5xx | 继续向调用方抛出真实依赖错误 |

支持判断结果无效不能改写成 `indeterminate`，因为资料还没有得到有效判断。真实依赖失败也不能变成空 Citation 的成功报告，否则调用方无法区分“没有支持证据”和“校验根本没完成”。

## 当前实现怎样承载这条机制

本节仍然是固定 RAG Pipeline，没有 Agent、Tool Call 或动态补检索。

| 层次 | 当前责任 | 不负责什么 |
| --- | --- | --- |
| Provider / SDK | 发送结构化请求，返回响应、usage、延迟和错误 | 判断来源身份、原文位置和产品后果 |
| `llm_core` | Prompt、模型配置、Structured Output 和解析阶段 | 决定哪份资料可以支持哪条 Claim |
| `rag_core` | 接收允许集合与原文，定位引文，批量判断支持关系，形成报告 | 判断整份回答是否证据充分 |
| 产品领域层 | 把经过支持性校验的 Citation 绑定到具体 Finding | 改写模型声明或绕过证据规则 |

风险生成和支持判断使用两份独立的 Prompt 与 Schema。生成模型负责提出 Claim 和引用声明，校验模型负责判断给定材料之间的关系；两步可以独立观察和失败，不能让生成模型在同一次输出中给自己的引用打分。

校验器只接受调用方明确交付的允许集合和可回查原文，不自己重新检索或扩大证据范围。因此同一机制以后可以接收运行级证据登记簿形成的允许集合，而不用改变“先定位、再判断”的语义。

## 支持成立仍不等于证据充分

假设一次评审包含三条 Claim：第一条有一条 `supported` Citation，第二条没有任何外部资料，第三条只有一条 `indeterminate` Citation。本节可以准确报告每条候选引用与对应 Claim 的关系，却不能把整份评审直接判成“可以回答”或“应该拒答”。

支持性回答的是：

> 一条来源与一条具体说法之间是什么关系？

后续证据充分性机制回答的是：

> 已经成立的支持关系加在一起，是否足以支撑这次回答？缺口又应该怎样转成 Refusal 或补充问题？

本节向后交付全部支持性检查、已经得到支持的 Citation，以及未支持、无法判断和执行失败的诊断。边界标记为 `quote_location_then_semantic_support_not_sufficiency`，明确提醒调用方不能把局部支持关系改写成整份结论已经充分。

## 学完后的自检

从模型输出中任选一条已经通过来源成员检查的 Citation，只追踪它：

1. 写出它要支持的具体 Claim，不要笼统使用整条风险。
2. 按 `source_id` 找到本轮允许来源的权威原文。
3. 判断 `excerpt` 能否在有限归一化后唯一定位。
4. 记录原文位置和字符范围，不按语义自动修复引文。
5. 阅读引文前后的版本、范围、否定和适用条件。
6. 判断它是支持、反驳、无关还是无法判断，并说明理由。
7. 最后说明为什么这个结果仍不能推出整份回答证据充分。

如果能够完成这条追踪，并且不会把编号合法、文字存在、内容支持和证据充分混成一次“引用正确”，就掌握了 Citation 支持性校验。
