## 这一段课程要回答什么

第 7–16 节已经交付固定 RAG 核心链，终点是"模型声明的来源属于本轮允许集合"。第 17–24 节把它变成可交付产品：

```text
Citation 成员资格（已完成，第 16 节）
→ Citation 支持性
→ 证据充分性 / Refusal / 补充问题
→ 不确定性表达
→ 身份
→ 产品 RBAC
→ 知识资料 API 与生命周期
→ Review API、状态机与 SSE
→ Web 工作台联调
```

三层可信边界必须严格保持，任何一节都不许越界：

| 节 | 回答 |
| --- | --- |
| 16 | 模型声称的来源是否属于本轮允许集合？ |
| 17 | 来源片段是否支持该声明？ |
| 18 | 所有已支持的声明是否足以支撑这份报告？ |

## 两条上传流

产品有两条上传流，语义完全不同，任何一节都不能把它们混写：

```text
评审者上传 PRD / 粘贴文本
→ ReviewRequest.requirement_text
→ 固定 RAG
→ SSE 增量（生成中、未校验）
→ ReviewReport / Refusal / 真实失败

管理员上传知识资料
→ 解析、清洗、Chunk、Embedding、诊断
→ staged
→ 管理员发布
→ 新 dataset_version
→ 之后才成为 Retriever 候选
```

两条硬约束：

- PRD 是被评审对象，不进入 Retriever 候选池，不能成为 Citation Candidate。
- 上传本身不改变检索候选池；只有发布动作产生新的 `dataset_version`。

## 已确定的决定

起草时直接采用，不重新讨论。

1. **22 与 23 按生命周期切分**：22 归知识资料流，23 归评审流。不按"一节写契约形状、一节写状态语义"切分——SSE 事件是状态迁移的投影，形状与语义分家会让写契约的那节前向引用另一节的状态名，且承载两条独立生命周期，违反一节一个核心问题。
2. **ReviewRun 终态只有三个**：`completed / failed / cancelled`。证据充分性是业务结论，作为 `completed` 上的 `evidence_decision` 字段承载，不提为终态。失败原因作为 `failure_reason` 枚举，不扩成更多状态。
3. **知识资料在暂存时完成切分与向量化**，发布是一次廉价的版本翻转。这样发布前诊断就能看到 chunk 数、定位质量和 embedding 失败，发布本身原子，不需要队列（SPEC 明确第一阶段不引入 Redis）。
4. **第 17 节做两段校验**：确定性引文定位在前，模型支持性判断在后。只做前者会让 17 退化成第 16 节的加强版，失去独立核心问题。
5. **第 24 节新建文件**，位于 `course/project/stage-1-rag-application/`，与 `rag-review-assistant.md` 并列。理由是学习路径的状态标记按编号对应文件；24 可写而 29 等待前置，共用一个文件无法标状态。
6. **认证使用 Cookie Session，不用 Bearer Token。** 原生 `EventSource` 无法设置请求头，Bearer 方案会迫使 token 进 query string（进访问日志）或放弃 `EventSource` 自行解析流。单一同源 Web 工作台、无移动端，Bearer 的好处一个都用不上。这条决定属于第 20 节，并向第 23 节的传输实现传导，正文中要说明这层传导关系。
7. **前端选型**（第 24 节联调使用，22/23 只写契约不写前端）：

   | 关注点 | 选择 | 理由 |
   | --- | --- | --- |
   | 服务端状态 | TanStack Query | 本应用状态几乎全是服务端状态 |
   | 客户端状态 | 页面级 `useReducer`，不建全局 store | SSE 流是页面级的；跨路由续跑是产品决定而非前端决定，出现后再引入 Zustand |
   | 路由 | React Router | 够用；TanStack Router 的 `beforeLoad` 更贴合路由级守卫，但不值得为它换栈 |
   | API 类型 | 从 FastAPI OpenAPI 生成 | 让 22/23 的契约被强制而非被描述，漂移在类型检查阶段暴露 |
   | 组件库 | 无样式可访问类（Radix / shadcn） | 证据、引文、逐条支持状态、部分回答都无现成组件；重样式库会挡路，且需控制到 ARIA 层 |
   | 表单与上传 | react-hook-form + zod | schema 镜像后端错误契约，两种上传在类型层面分开 |

## 跨节共享契约

只在指定的一节定义，其余节引用，不重复解释。

### ReviewRun 状态机（第 23 节定义）

```text
submitted → retrieving → generating_unverified → validating
                                                    ↓
                              completed | failed | cancelled
```

- `completed` 携带 `evidence_decision`：可回答 / 部分回答 / 拒答。
- `failed` 携带 `failure_reason`：鉴权失败 / 限流 / 超时 / 能力不支持 / 结构化校验失败 / 内部失败。
- `validating` 内部依次执行第 16 节成员资格、第 17 节支持性、第 18 节充分性三层校验，结果进诊断字段。**状态机不镜像机制链**——后续增加校验层不改状态机。
- 检索零候选是"完成且拒答"，不是 `failed`。
- 取消只在 `retrieving` 与 `generating_unverified` 期间可请求；进入 `validating` 后按完成处理。
- SSE 连接断开是传输层事件，不改变任何业务状态。

### 知识资料生命周期（第 22 节定义）

```text
uploaded → parsing → parse_failed
                   → staged → published → superseded
```

- `parsing` 失败必须落到 `parse_failed` 并暴露明确错误，不能停在 `parsing`。
- 同一 `document_id` 的新版本发布后，旧版本进入 `superseded`。
- 切分与向量化在进入 `staged` 前完成。
- 一次发布动作产生一个 `dataset_version`，覆盖该次发布的文档集合；`dataset_version` 是快照身份，文档是它的成员。

### dataset_version 与运行的绑定（第 22 节定义规则，第 23 节定义绑定时机）

ReviewRun 在进入 `retrieving` 时钉住当时生效的 `dataset_version`，之后全部检索与校验都在该版本内进行，报告中带上它。

不做这条绑定的后果：管理员发布与评审者提交并发时，中途发布会改变候选池，Citation 无法复现，冻结的 acceptance Golden Set 失去意义。

`course/mechanisms/retriever-contract.md` 中 `dataset_version` 目前只是实验运行身份；第 22 节要说明它在产品中升级为 Metadata Filter 的一部分，参与"两路检索前应用过滤"这一步。

### SSE 事件契约（第 23 节定义）

- 事件必须区分"未校验分支的增量"与"最终已校验结果"，后者是替换语义而非合并语义。
- 事件带单调递增序号，允许消费端幂等丢弃乱序或重复事件。第一阶段不做断线重连游标（第 67 节的责任），但序号本身成本极低。
- 客户端把未校验草稿与已校验报告放在两个独立字段：生成期只写前者；`validating` 成功时写后者并清空前者；失败时清空前者并写失败。**撤回等于丢弃一个分支，不存在反向补偿逻辑**，也就不可能出现未校验内容残留在界面上。

## 逐节起草基准

每节固定：类型、核心问题、学习者已有输入、交付、非目标。实验篇的单变量在此登记，起草时直接沿用。

### 17 Citation 支持性校验

- **类型**：机制篇 + 实验篇
- **核心问题**：Citation ID 合法之后，来源中的那段内容是否真的支持对应风险？
- **已有输入**：第 16 节交付的结构化风险与成员资格检查结果。
- **交付**：`VerifiedCitation`——声明、证据片段、原文定位、支持档位、理由。
- **两段校验**：
  1. 确定性定位。模型在声明 `source_id` 的同时必须给出逐字引文；应用把引文拿回对应 chunk 原文做归一化后精确匹配，成功才产生 locator。失败直接判定，不进入第二段。这一段零成本挡住编造引文，并顺带产出原文定位。
  2. 模型判断。引文确实存在时，判断它是否支持该声明。这一步无法用程序替代。
- **支持档位必须含"无法判定"**，且该档在报告中可见。校验器自身失败不得默认算作支持——这是"不静默降级"在本节的具体形态。
- **它是业务校验器，不是评估 Judge。** 固定 Prompt 版本与 Schema，结果进业务结果。LLM-as-Judge 的人工校准在第 101 节、第二阶段，本节正文要有一句显式区分。
- **成本**：一次 run 的所有声明合并为一次调用，Token 与成本进诊断。
- **对第 16 节的扩展**：本节把生成 Schema 从"声明 source_id"升级为"声明 source_id + 逐字引文"。由本节承担这次扩展并解释为什么现在才加（第 16 节时还没有支持性概念，加了也无人消费），同时在 `course/mechanisms/trusted-generation.md` 补一句向后指引。
- **实验单变量**：冻结上游，只替换证据片段。四个 fixture——真支持 / 引文真实但与声明无关 / 引文与声明矛盾 / 引文根本不存在。最后一个由第一段拦下，前三个走到第二段，顺带让学习者看清两段各自能证明什么。
- **非目标**：不判断整份报告的充分性；不做 Refusal 决策；不设计界面。
- **代码落点**：`source/packages/rag_core/`

### 18 证据充分性、Refusal 与补充问题

- **类型**：机制篇 + 实验篇
- **核心问题**：若若干 Citation 都成立，是否足以支撑当前结论？缺什么？
- **已有输入**：第 17 节交付的 `VerifiedCitation` 集合及其支持档位。
- **交付**：`EvidenceDecision`——可回答 / 部分回答 / 拒答，以及结构化 gap。
- **补充问题是 gap 的输出形式，不是独立生成链。** 先有结构化 gap（缺哪类事实、哪个来源角色本应覆盖它、影响哪几条风险），问题是 gap 的渲染。本节若长出第二条生成流水线就是切分失败，应停下重新划界。
- **实验单变量**：冻结一切，只从 `knowledge_scope` 移除一份关键文档，观察决策从"可回答"滑向"证据不足"。
- **非目标**：不定义运行状态；不设计界面；不做补充答案的回填闭环（第一阶段用户回答后重新提交一次评审即可）。
- **代码落点**：`source/packages/rag_core/`

### 19 AI Native 界面与不确定性表达

- **类型**：概念篇
- **核心问题**：用户如何区分生成内容、已验证结论、证据不足和真实系统失败？
- **交付**：UI 表达原则与结果层级。本节同时是第 23 节状态机必须满足的需求来源。
- **核心原则：可信状态是逐条的，不是整份报告的。** 三层表达——报告顶部一句话说明本次评审能支撑到什么程度；每条风险自带支持状态；每个补充问题挂到对应 gap 与受影响的风险项。
- **部分回答的设计要求**：partial 的本质是"有些结论现在就能用，有些还差一个具体答案"，界面必须同时回答这两件事。只显示一条"证据不足，请谨慎参考"的警告条不合格——它把判断责任推回给用户。
- **不确定性不得只靠颜色和图标承载，必须有文字。** 既是可访问性，也因为后续 bad case 讨论依赖截图与运行记录。
- **非目标**：不写具体组件、不定义运行状态名、不建设通用 AI 工作台。
- **可验收判据（交给第 24 节执行）**：给一个 partial 的 run，用户在不打开诊断区的前提下，能说出哪几条风险可直接采纳、回答哪个问题能把剩下的补齐。

### 20 用户身份与认证

- **类型**：机制篇；验证并入第 22 节实验
- **核心问题**：登录、凭证校验、会话签发、失效和登出如何形成后端可依赖的身份事实？
- **交付**：后端可依赖的 principal，而不是前端自报角色。
- **使用 Cookie Session**，理由见"已确定的决定"第 6 条。
- **正文要讲清一层传导**：认证方式的选择会实质约束 API 与传输实现——原生 `EventSource` 无法设置请求头，因此第 20 节的选择直接决定第 23 节的 SSE 能否用标准浏览器 API。这是"身份机制不是孤立的"的一个真实例子，比抽象讲 token 生命周期更有说服力。
- **非目标**：不做注册审批、找回密码、多因子、OAuth、第二阶段 Tool 权限。
- **代码落点**：`source/apps/review_assistant/`

### 21 产品 RBAC 与 Tool 权限的区别

- **类型**：机制篇；验证并入第 22 节实验
- **核心问题**：普通评审者和管理员分别能看什么、做什么？
- **交付**：路由级与动作级两层授权决定。
- **必须显式对照第 35 节**：本节回答"界面上谁能点什么"，第 35 节回答"模型能执行什么"。两者概念独立，不能相互替代或合并实现。
- **非目标**：不做审批工作流、不做超过两个角色的权限矩阵、不做多租户。
- **代码落点**：`source/apps/review_assistant/`

### 22 知识资料 API 与资料生命周期

- **类型**：机制篇 + 实验篇
- **核心问题**：资料怎样从上传变成可检索候选？
- **交付**：知识资料 API 的请求、响应、错误形状；资料生命周期状态；`dataset_version` 的产生规则。
- **本节第一次引入 FastAPI**：这条流确定性、无流式、无模型调用，认知负担最小，适合建立请求/响应/错误分层与依赖注入。它也符合真实数据依赖顺序——没有发布过 `dataset_version`，评审根本检索不到东西。
- **解析诊断的归属**：诊断对象的形状是 `rag_core` 从第 8 节起就有的输出，本节只负责存储与暴露，不重新定义。
- **实验**：合并承担第 20、21 节的验证——真实登录取得会话，两个角色分别调用评审端点与发布端点，观察 403 同时出现在路由层与动作层。授权缺陷只在真实请求里现形，但为它单开两个薄实验不划算。
- **非目标**：不写评审流的 API；不写 SSE；不写前端。
- **代码落点**：`source/apps/review_assistant/`

### 23 Review API、ReviewRun 状态机与 SSE 事件契约

- **类型**：机制篇 + 实验篇
- **核心问题**：一次评审此刻处于什么状态，客户端据此显示什么？
- **交付**：Review API 契约、ReviewRun 状态机、SSE 事件契约、增量撤回语义。错误形状复用第 22 节已建立的分层。
- **含未校验增量的撤回语义**：它是状态迁移在客户端的投影，属于状态语义而非 UI 实现细节，因此归本节而不归第 19 或 24 节。
- **实验单变量**：同一请求，分别制造正常完成、证据不足、结构化校验失败和用户取消，观察四种情况下的事件序列与终态差异。
- **非目标**：不做心跳、断线重连游标、Tool 事件、多步骤运行轨迹（全部属于第 64–67 节）；不写前端实现。
- **代码落点**：`source/apps/review_assistant/`

### 24 固定 RAG 工作台集成检查点

- **类型**：项目篇，新建文件于 `course/project/stage-1-rag-application/`
- **核心问题**：怎样把评审与知识管理这两条流程接入同一 Web 工作台？
- **交付**：最小真实前后端联调与验收证据。
- **必须显式声明的非目标**：不做 Golden Set、不做四路对照、不设质量门槛、不做需求变更题——全部属于第 29 节。本节只验证两条流能真实跑通。
- **引用纪律**：只引用 `SPEC.md` 中与联调相关的几条（角色边界、上传暂存发布、增量流式与最终校验），质量门槛部分一个字不碰，直接指向第 29 节。
- **至少包含的验收项**：
  - 管理员上传 → 查看解析诊断 → 暂存 → 发布 → 产生新 `dataset_version`，且发布前候选池不变。
  - 评审者提交（粘贴文本与上传文件两种入口）→ 增量流式 → 最终校验替换 → 已验证报告。
  - 校验失败时未校验增量被显式撤回，界面无残留。
  - 普通评审者看不到也调不到知识管理动作。
  - 第 19 节的 partial 判据：不打开诊断区即可说出哪些风险可采纳、回答哪个问题能补齐剩下的。
