# Reliability、错误分类与可见降级

> 机制篇：解释模型调用失败怎样被分类、有限重试、显式降级并形成可诊断结果。
>
> 课程位置见[标准学习路径](../learning-path.md)。前置是统一模型调用与结构化输出边界；真实调用、稳定失败复现、日志和读码见[配套实验](../labs/reliability-and-errors.md)。

## 为什么一次失败不能统一重试

“模型调用失败”只是表象。缺少密钥、权限不足、限流、网络抖动、超时、能力不支持和 Schema 校验失败有不同根因。统一重试会带来三种危险：

- 对不可恢复错误反复请求，放大延迟和成本；
- fallback 成功后隐藏真实失败，使质量变化不可追踪；
- 把结构化或证据错误当成暂时性网络问题。

可靠性不是“永不失败”，而是让失败可分类、可控制、可观察，并让用户知道系统最后采用了什么路径。

## 可靠调用的控制链

```text
调用意图
  → 单次尝试
  → 结构化错误分类
  → 判断是否可重试
  → 有限退避与再次尝试
  → 判断是否允许降级
  → 返回成功结果或最终失败报告
```

这条链必须由应用控制。模型供应商可以提供错误码，重试库可以执行等待，但“是否值得再试”“是否允许换模型”“换模型后是否仍满足业务要求”仍是产品策略。

## 先按恢复可能性分类

| 错误类别 | 常见表现 | 默认动作 | 原因 |
| --- | --- | --- | --- |
| 配置或鉴权 | 缺少 Key、401、403 | 不自动重试 | 重复请求不会修复配置 |
| 能力不匹配 | 模型不支持结构化模式或角色用错 | 不自动重试 | 需要换配置或策略 |
| 限流 | 429 | 有限退避 | 可能随时间恢复 |
| 暂时性服务错误 | 部分 5xx | 有限退避 | 远端可能短暂异常 |
| 网络错误 | 连接重置、临时 DNS 问题 | 谨慎重试 | 可能是短暂传输故障 |
| 超时 | 在预算内未完成 | 视剩余预算决定 | 重试可能再次超时 |
| JSON / Schema 失败 | 已取得内容但无法进入业务 | 按失败类型决定 | 不一定是网络问题 |
| 业务证据不足 | 没有足够资料形成结论 | 不重试同一调用 | 需要补证据或追问 |

“可重试”不是“必须重试”。即使错误可能恢复，也要同时考虑请求是否幂等、剩余时间和成本预算，以及用户是否已经取消。

## 重试为什么必须有限

一次可靠性策略至少要有：

- 最大尝试次数；
- 总时间预算；
- 每次尝试的超时；
- 退避与随机抖动；
- 可重试错误白名单；
- 取消传播；
- 每次尝试的独立记录。

退避减少大量客户端同时重试造成的拥塞，随机抖动避免它们在同一时刻再次请求。硬上限保证系统最终会结束，而不是把“暂时失败”变成无限等待。

超时也不能只设置一个全局数字。单次尝试超时、整条任务预算和用户界面的等待预期属于不同边界。某次调用还有重试资格，不代表整个评审任务仍有足够预算。

## 降级必须是显式产品决策

降级可能是换备用模型、降低结构化约束强度、缩短输出或返回部分结果。它不是“把错误吃掉”。每种降级都可能改变质量、能力、成本和结果形状。

一次可接受的降级需要说明：

1. 什么错误允许触发；
2. 从哪种能力降到哪种能力；
3. 哪些业务不变量必须继续满足；
4. 结果怎样标记实际路径；
5. 用户是否需要知道；
6. 评估时怎样与主路径区分。

例如结构化生成模型不可用时，退回普通 JSON Mode 仍必须经过同一应用 Schema；不能因为 fallback 返回了文本就把它当成有效风险列表。

## 一次结果要同时报告“发生了什么”

最终结果不应只包含内容或异常字符串。可靠调用报告至少需要：

- 最终状态；
- 尝试次数和每次尝试的错误类别；
- 实际模型与配置身份；
- 是否发生 fallback；
- 总耗时与可获得的用量；
- 最终失败阶段；
- 是否由取消、预算或硬上限停止。

这使 UI 能区分“正在重试”“已使用备用模型”“输出校验失败”和“系统不可用”，也使评估能够判断质量变化是否来自降级路径。

## Structured Output 失败怎样进入可靠性

结构化失败发生在已经取得模型内容之后，但它仍是调用结果的一部分。需要继续区分：

- JSON 因偶发围栏或截断失败；
- Schema 因固定枚举或字段漂移失败；
- 供应商在生成约束阶段拒绝请求；
- 契约通过但内容缺少证据。

前两类有时可以在严格预算内重试，但必须记录原始失败；固定重复的 Schema 错误更应修 Prompt 或契约。最后一类不是重试问题，应回到 RAG、Citation 或用户补充信息。

## 副作用改变重试边界

当前模型调用主要是读取和生成，重复执行通常不会直接修改外部世界，但仍会增加成本并产生不同输出。进入 Tool 与 Agent 后，调用可能写文件、发消息或修改业务状态，自动重试会更危险。

因此可靠性机制从一开始就要区分：

- 纯读取或可安全重复的操作；
- 需要幂等键的写入；
- 必须人工确认且不能自动重放的副作用。

这条边界会在 Tool 权限与副作用课程中加厚，但重试层不能假设所有动作天然幂等。

## 五类常见错误设计

### 无限重试

它把供应商故障转化为无限成本和无限等待，并阻止系统形成明确结束状态。

### 对鉴权失败重试

密钥或权限没有变化，重复请求没有恢复可能，只会制造噪声。

### fallback 不留痕

用户得到结果，却不知道模型和能力已经变化；后续质量回归也无法解释差异。

### 解析失败返回空列表

“没有风险”与“系统没能解析风险”是完全不同的业务事实，不能共用结果。

### 用 fake 掩盖真实失败

Mock 可以稳定复现错误分支，但不能在主路径上替代真实模型。缺 Key、限流或超时必须清晰暴露。

## 如何验证可靠性策略

真实服务调用可以证明当前鉴权、网络和供应商链路的真实行为，却不容易稳定触发所有错误。确定性失败复现可以证明分类、退避、fallback 和报告逻辑，却不能证明真实服务可用或真实质量合格。

两类证据需要并列：

| 证据 | 可以证明 | 不能证明 |
| --- | --- | --- |
| 真实调用 | 当前服务与配置真实工作或真实失败 | 所有错误分支都已覆盖 |
| 稳定失败复现 | 控制逻辑对已知错误的行为可重复 | 生产服务质量和可用性 |

配套实验先运行真实主路径，再稳定复现可重试和不可重试失败，观察尝试次数、等待、fallback 和最终报告。命令、日志和读码路径见[实验篇](../labs/reliability-and-errors.md)。

## 掌握标准

完成本节后，应能：

1. 根据恢复可能性区分鉴权、限流、网络、超时、能力和解析失败。
2. 解释最大次数、总预算、退避、抖动和取消各自解决什么问题。
3. 判断一次 fallback 是否仍满足业务契约。
4. 设计不会把失败伪装成空结果的调用报告。
5. 说明真实调用与稳定失败复现各自能证明什么。
6. 识别重试在未来 Tool 副作用场景中的幂等风险。

本节交付的是可观察、可停止的可靠调用边界，不是“永不失败”的承诺。完成实验后回到[标准学习路径](../learning-path.md)。
