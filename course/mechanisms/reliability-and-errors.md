# Reliability、错误分类与可见降级

> 机制篇：解释模型调用失败怎样被分类、有限重试、显式降级并形成可诊断结果。
>
> 课程位置见[标准学习路径](../learning-path.md)。前置是统一模型调用与结构化输出边界；真实调用、稳定失败复现、日志和读码见[配套实验](../labs/reliability-and-errors.md)。

## 为什么一次失败不能统一重试

“模型调用失败”只是表象。缺少密钥、权限不足、限流、网络抖动、超时、能力不支持和 Schema 校验失败有不同根因。统一重试会带来三种危险：

- 对不可恢复错误反复请求，放大延迟和成本；
- fallback 成功后隐藏真实失败，使质量变化不可追踪；
- 把结构化或证据错误当成暂时性网络问题。

可靠性不是“永不失败”，而是让失败可分类、可控制、可观察，并让用户知道系统最后采用了什么路径。

先看一次真实的结构化评审可能怎样推进：

```text
主模型请求超时
→ 判断 timeout 是否允许重试
→ 第二次尝试仍超时
→ 判断当前任务是否允许 fallback（切换到预先批准的备用路径）
→ 备用模型返回文本
→ Structured Output 校验
→ 结果可用，但明确标记为 degraded
```

这里任何一步都不能由“自动重试一切”替代。鉴权失败重复请求不会恢复，Schema 稳定漂移也不会因为多请求几次自动修复；fallback 即使成功，也改变了模型身份和潜在质量。

本节建立的是同步单次调用的最小可靠性闭环，不是完整生产平台。队列、熔断器、跨进程恢复和长期 Trace 都可能在真实需求出现后加入，但错误分类、有限尝试、显式降级和最终报告是它们共同依赖的基础。

## 可靠调用的控制链

```text
调用意图
  → 单次尝试
  → 结构化错误分类
  → 判断是否可重试
  → 有限退避与再次尝试
  → 判断是否允许降级
  → 返回成功结果或最终失败报告
```

这条链必须由应用控制。模型供应商可以提供错误码，重试库可以执行等待，但“是否值得再试”“是否允许换模型”“换模型后是否仍满足业务要求”仍是产品策略。

这条控制链需要四类不同对象，它们不能合并成一个“retry 配置”：

| 对象 | 决定什么 |
| --- | --- |
| 错误分类 | 失败属于哪种性质，是否可能恢复 |
| Retry Policy | 同一条能力是否再次尝试、最多几次 |
| Degradation Policy | 主路径失败后是否允许切换能力 |
| Attempt Report | 实际尝试了什么、为何停止、最终用了什么 |

Retry Policy 只判断同一路径是否再试；Degradation Policy 判断是否接受另一条路径。把两者混在一起，会让“再次调用主模型”和“切换到能力不同的备用模型”在记录中不可区分。

## 先按恢复可能性分类

| 错误类别 | 常见表现 | 默认动作 | 原因 |
| --- | --- | --- | --- |
| 配置或鉴权 | 缺少 Key、401、403 | 不自动重试 | 重复请求不会修复配置 |
| 能力不匹配 | 模型不支持结构化模式或角色用错 | 不自动重试 | 需要换配置或策略 |
| 限流 | 429 | 有限退避 | 可能随时间恢复 |
| 暂时性服务错误 | 部分 5xx | 有限退避 | 远端可能短暂异常 |
| 网络错误 | 连接重置、临时 DNS 问题 | 谨慎重试 | 可能是短暂传输故障 |
| 超时 | 在预算内未完成 | 视剩余预算决定 | 重试可能再次超时 |
| JSON / Schema 失败 | 已取得内容但无法进入业务 | 按失败类型决定 | 不一定是网络问题 |
| 业务证据不足 | 没有足够资料形成结论 | 不重试同一调用 | 需要补证据或追问 |

“可重试”不是“必须重试”。即使错误可能恢复，也要同时考虑请求是否幂等、剩余时间和成本预算，以及用户是否已经取消。

### 为什么错误名称要统一

不同供应商可能用不同异常类和状态字段表达超时、限流或能力不支持。业务层如果直接判断供应商异常名，同一种恢复策略会散落到多个入口。

Provider 应先把远端失败翻译成应用统一错误，但统一名称仍不能抹掉必要事实。错误报告还应保留配置身份、发生阶段和安全的原始原因，才能在供应商映射错误时继续排查。

### Schema 失败为什么不等于 Provider 失败

模型请求可能已经成功返回，但结果无法通过应用 Schema。对结构化任务而言，这次业务调用仍然失败，只是失败阶段晚于网络请求。

这一区分会影响策略：远端 5xx 可能值得有限重试；固定字段或枚举漂移更可能需要修改 Prompt 或 Schema；证据不足则应该补检索或追问，而不是重新生成同一输入。

## 重试为什么必须有限

一次可靠性策略至少要有：

- 最大尝试次数；
- 总时间预算；
- 每次尝试的超时；
- 退避与随机抖动；
- 可重试错误白名单；
- 取消传播；
- 每次尝试的独立记录。

退避减少大量客户端同时重试造成的拥塞，随机抖动避免它们在同一时刻再次请求。硬上限保证系统最终会结束，而不是把“暂时失败”变成无限等待。

超时也不能只设置一个全局数字。单次尝试超时、整条任务预算和用户界面的等待预期属于不同边界。某次调用还有重试资格，不代表整个评审任务仍有足够预算。

## 重试机制怎样从弱到强演进

### 直接调用

实现最简单，但失败时通常只抛出异常。用户和开发者都不知道它是暂时性超时、错误密钥还是无效结构。

### 捕获所有异常并重试

它可能恢复一次网络抖动，却会同时重复鉴权、参数和能力错误。系统看起来“更努力”，实际只是延迟更长、日志更乱。

### 分类后有限重试

只有明确可能恢复的错误再次尝试，不可恢复错误快速失败。这解决偶发故障，却还没有回答主模型持续不可用时怎么办。

### 显式 fallback

允许的错误可以切换到备用路径，但成功结果必须保存降级事实。此时系统能继续服务，却新增了质量和能力变化。

### 完整 Attempt Report

每次尝试、配置、错误、耗时、降级和停止原因都进入报告。只有到这一步，后续 Harness、成本统计和质量评估才能解释一次结果究竟来自哪条执行路径。

```text
直接调用
→ 无差别重试
→ 错误分类与有限重试
→ 显式 fallback
→ 可比较的尝试报告
```

## 降级必须是显式产品决策

降级可能是换备用模型、降低结构化约束强度、缩短输出或返回部分结果。它不是“把错误吃掉”。每种降级都可能改变质量、能力、成本和结果形状。

一次可接受的降级需要说明：

1. 什么错误允许触发；
2. 从哪种能力降到哪种能力；
3. 哪些业务不变量必须继续满足；
4. 结果怎样标记实际路径；
5. 用户是否需要知道；
6. 评估时怎样与主路径区分。

例如结构化生成模型不可用时，退回普通 JSON Mode 仍必须经过同一应用 Schema；不能因为 fallback 返回了文本就把它当成有效风险列表。

还要注意“换模型”和“降低格式约束”是两种不同降级。前者改变推理能力、成本和行为，后者改变输出稳定性。一次运行可能同时发生两者，报告必须分别表达，不能只用一个 `degraded=true` 隐去细节。

## 一次结果要同时报告“发生了什么”

最终结果不应只包含内容或异常字符串。可靠调用报告至少需要：

- 最终状态；
- 尝试次数和每次尝试的错误类别；
- 实际模型与配置身份；
- 是否发生 fallback；
- 总耗时与可获得的用量；
- 最终失败阶段；
- 是否由取消、预算或硬上限停止。

这使 UI 能区分“正在重试”“已使用备用模型”“输出校验失败”和“系统不可用”，也使评估能够判断质量变化是否来自降级路径。

Attempt Report 不只是调试日志。它是业务结果的运行上下文：同样一份风险列表，来自主模型一次成功，还是两次超时后由备用模型生成，代表不同的可信度和成本事实。

## Structured Output 失败怎样进入可靠性

结构化失败发生在已经取得模型内容之后，但它仍是调用结果的一部分。需要继续区分：

- JSON 因偶发围栏或截断失败；
- Schema 因固定枚举或字段漂移失败；
- 供应商在生成约束阶段拒绝请求；
- 契约通过但内容缺少证据。

前两类有时可以在严格预算内重试，但必须记录原始失败；固定重复的 Schema 错误更应修 Prompt 或契约。最后一类不是重试问题，应回到 RAG、Citation 或用户补充信息。

如果降级路径没有继续使用同一份 Context 和 Citation Candidate，还可能生成无法追踪的来源。可靠性层不能只验证“有文本”，还要保证降级没有绕过原有业务契约。

## 副作用改变重试边界

当前模型调用主要是读取和生成，重复执行通常不会直接修改外部世界，但仍会增加成本并产生不同输出。进入 Tool 与 Agent 后，调用可能写文件、发消息或修改业务状态，自动重试会更危险。

因此可靠性机制从一开始就要区分：

- 纯读取或可安全重复的操作；
- 需要幂等键的写入；
- 必须人工确认且不能自动重放的副作用。

这条边界会在 Tool 权限与副作用课程中加厚，但重试层不能假设所有动作天然幂等。

模型生成本身虽然通常没有外部写入副作用，也不是零代价的纯函数：重复调用会产生费用、等待和不同文本。进入 Agent 后，Tool Call 还可能带来真实写入，因此当前建立的取消、预算和 attempt 身份会直接成为后续执行治理的前置。

## 五类常见错误设计

### 无限重试

它把供应商故障转化为无限成本和无限等待，并阻止系统形成明确结束状态。

### 对鉴权失败重试

密钥或权限没有变化，重复请求没有恢复可能，只会制造噪声。

### fallback 不留痕

用户得到结果，却不知道模型和能力已经变化；后续质量回归也无法解释差异。

### 解析失败返回空列表

“没有风险”与“系统没能解析风险”是完全不同的业务事实，不能共用结果。

### 用 fake 掩盖真实失败

Mock 可以稳定复现错误分支，但不能在主路径上替代真实模型。缺 Key、限流或超时必须清晰暴露。

### 降级破坏证据边界

备用路径若使用了不同 Prompt、丢失当前 Context，或忽略 Citation Candidate，可能返回结构合法但来源不可追踪的风险。降级策略必须明确哪些输入和校验不允许变化。

### 只记录最终错误

最终错误相同，不代表过程相同。一次立即鉴权失败和三次超时后的最终失败，对配置、成本和用户体验有完全不同的含义；只保留最后一条异常会丢失这些事实。

## 如何验证可靠性策略

真实服务调用可以证明当前鉴权、网络和供应商链路的真实行为，却不容易稳定触发所有错误。确定性失败复现可以证明分类、退避、fallback 和报告逻辑，却不能证明真实服务可用或真实质量合格。

两类证据需要并列：

| 证据 | 可以证明 | 不能证明 |
| --- | --- | --- |
| 真实调用 | 当前服务与配置真实工作或真实失败 | 所有错误分支都已覆盖 |
| 稳定失败复现 | 控制逻辑对已知错误的行为可重复 | 生产服务质量和可用性 |

配套实验先运行真实主路径，再稳定复现可重试和不可重试失败，观察尝试次数、等待、fallback 和最终报告。命令、日志和读码路径见[实验篇](../labs/reliability-and-errors.md)。

## 常见误区与当前边界

| 误区 | 正确判断 |
| --- | --- |
| 加上 retry 就等于可靠 | retry 只处理可能恢复的失败 |
| HTTP 成功就是业务成功 | 结构化和业务校验仍可能失败 |
| fallback 有答案就可以隐藏降级 | 模型和能力变化必须进入结果身份 |
| 错误越多重试次数越应该增加 | 次数受总预算、成本和用户取消控制 |
| Mock case 通过说明真实服务可靠 | Mock 只证明确定性控制逻辑 |
| 可靠调用应顺便完成队列、熔断和 Trace | 当前只建立单次调用的最小控制与报告 |

## 掌握标准

完成本节后，应能：

1. 根据恢复可能性区分鉴权、限流、网络、超时、能力和解析失败。
2. 解释最大次数、总预算、退避、抖动和取消各自解决什么问题。
3. 判断一次 fallback 是否仍满足业务契约。
4. 设计不会把失败伪装成空结果的调用报告。
5. 说明真实调用与稳定失败复现各自能证明什么。
6. 识别重试在未来 Tool 副作用场景中的幂等风险。

本节交付的是可观察、可停止的可靠调用边界，不是“永不失败”的承诺。完成实验后回到[标准学习路径](../learning-path.md)。
