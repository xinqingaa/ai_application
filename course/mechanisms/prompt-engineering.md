# 面向应用的 Prompt Engineering

> 机制篇：把 Prompt 从临时文字变成可解释、可版本化、可受控比较的任务协议。
>
> 课程位置见[标准学习路径](../learning-path.md)。前置是稳定的模型调用边界；模板、运行、观察和修改见[配套实验](../labs/prompt-engineering.md)。

## 为什么“写一句更好的提示词”不够

临时聊天只要求当前回答看起来合理，产品里的 Prompt 还要被复用、修改、比较和追踪。若任务、材料和输出要求散落在代码字符串里，一次改动可能同时改变多个变量，失败也无法归因。

需求评审助手会逐步承担风险识别、补充问题和报告综合。每类任务都需要稳定回答：

- 模型这一轮扮演什么角色；
- 只处理哪些材料；
- 目标是什么；
- 必须遵守和不得越过什么；
- 输出将被谁消费；
- 证据不足时怎样处理。

因此 Prompt 的核心不是“咒语”，而是一份模型任务协议。

## 任务协议由哪些部分组成

可以用六个视角检查 Prompt，但不要求每份模板机械地写成六个标题。

| 组成 | 回答的问题 | 缺失后的典型表现 |
| --- | --- | --- |
| 角色 | 从什么职责和视角工作 | 风险评审变成泛化产品建议 |
| 任务 | 本轮只完成什么原子目标 | 摘要、评审和建议混在一起 |
| 材料 | 哪些内容属于本轮事实输入 | 用常识补出材料中没有的接口 |
| 约束 | 必须做什么、禁止做什么 | 强答、编造或遗漏关键边界 |
| 示例 | 合格输出的风格和粒度 | 类别和表达粒度反复漂移 |
| 输出描述 | 后续希望怎样消费结果 | 结构和字段不稳定 |

拆分的价值在于可诊断。角色错、材料缺、约束冲突、示例污染和输出结构漂移属于不同问题，不能都用“再加一句 Prompt”处理。

## Prompt、Context 与 Schema 的分工

三者会一起进入模型任务，但责任不同：

| 对象 | 主要责任 | 不能保证 |
| --- | --- | --- |
| Prompt | 描述任务、材料边界、行为约束和输出意图 | 资料真的存在、字段一定合法 |
| Context | 提供本轮可见的事实和证据 | 模型一定正确使用证据 |
| Schema | 定义应用接受的字段、类型和枚举 | 结论事实正确或引用充分 |

在 Prompt 中写“只依据公司规范”不会自动给模型公司规范。证据由 RAG 或其他可信来源提供，Prompt 只规定怎样使用证据；应用还要校验输出和 Citation。

这也是为什么固定 Evidence 可以用于 Prompt 实验，却不能冒充已经建成知识库：它只隔离“任务协议怎样影响输出”这一变量。

## 从临时文字到可维护协议

Prompt 工程通常经历以下变化：

```text
临时任务文字
  → 任务文字与业务材料分离
  → 显式变量契约
  → 稳定任务身份与版本
  → 固定输入上的受控对比
```

稳定身份回答“这是什么任务”，版本回答“当前采用哪组任务规则”。两者必须随运行记录保存。否则团队说“上一版更稳”时，无法还原当时的任务文本、输入、模型和参数。

模板采用什么文件格式是实现选择；真正的机制要求是：任务真源可以版本化，变量来源可检查，调用方通过稳定身份取得确定版本，缺少关键变量时显式失败。

## 变量契约为什么重要

Prompt 模板中的变量不是随意占位符，而是任务输入接口。需求评审场景常见四类输入：

| 输入 | 责任 |
| --- | --- |
| 需求文本 | 用户本轮希望评审的对象 |
| 证据块 | 可引用的内部规则或检索候选 |
| 评审维度 | 本轮需要覆盖的稳定检查范围 |
| 已知摘要 | 前序步骤保留下来的受控信息 |

每个变量至少要有来源、必填性、空值语义和长度边界。缺少证据不应被悄悄渲染成一个看似完整的 Prompt；否则模型强答后，问题会被错误归因成模型幻觉。

变量渲染完成后，任务协议和本轮数据共同形成消息。模板负责稳定规则，变量负责变化事实，两者不能反过来：业务规则不应藏进临时数据，用户内容也不能被当成更高优先级指令。

## Few-shot 何时有用

Few-shot 适合解释抽象文字难以定义的输出边界，例如风险类别、表述粒度或合格引用形式。它不适合承载频繁变化的业务事实。

一个示例是否值得加入，可以检查：

1. 当前失败是否来自“合格结果长什么样”不清楚；
2. 仅靠文字规则是否仍难以对齐；
3. 示例中的内容是否稳定，不会让模型照搬旧接口或旧状态机；
4. 增加的上下文成本是否值得。

示例越具体，污染风险越大；示例越多，成本和噪声越高。历史评审记录更适合作为 RAG 资料或评估样例，而不是无选择地塞进 Prompt。

## 坏 Prompt 怎样暴露协议缺口

考虑下面的要求：

```text
你是一个专业的需求评审助手，请认真、全面地分析需求并输出风险。
```

它的问题不在于文字太短，而在于不可检查：“专业”是哪种视角，“全面”覆盖哪些维度，哪些材料可以作为事实，缺少信息时是否允许推测，输出给人看还是给程序处理，都没有定义。

更稳定的协议应明确：从研发视角工作；只基于本轮 PRD 与证据；识别研发风险；不得编造接口、状态、权限和埋点；证据不足时提出缺口；按风险类别、等级、理由和依据组织。

这仍不是最终 Schema，但失败已经更容易归因。若材料缺失，应修 Context；若字段漂移，应进入 Structured Output；若任务效果在多样例上不稳定，应进入 Harness 和评估，而不是无限加长 Prompt。

## 怎样进行可信的版本对照

Prompt 对比必须固定输入样例、模型配置、采样参数、证据和输出 Schema，只改变一个协议因素，例如：

- 增加明确的证据不足行为；
- 调整一个约束；
- 加入或移除一个示例；
- 修改输出描述。

观察也要针对具体失败，而不是只问“更喜欢哪版”：

| 观察 | 对应问题 |
| --- | --- |
| 是否编造材料外事实 | 材料边界和约束是否有效 |
| 是否遗漏约定维度 | 任务范围是否明确 |
| 是否稳定说明证据不足 | 拒答或追问边界是否明确 |
| 输出结构是否更一致 | 输出描述是否清楚 |
| token 和延迟怎样变化 | 新规则和示例的代价 |

单次漂亮输出不能证明版本更好。当前实验建立最小受控比较，后续 Harness 才在固定数据集上形成更可靠的回归证据。

## Prompt 失败时的定位顺序

1. **任务是否单一**：是否把摘要、风险、建议和报告混成一轮。
2. **材料是否存在**：模型是否真的看到了 PRD 和证据。
3. **边界是否一致**：是否同时要求“尽量简短”和“覆盖所有维度”。
4. **输出是否可检查**：下游究竟需要文本段落还是稳定字段。
5. **示例是否污染**：是否照搬了示例中的过期规则。
6. **实验变量是否固定**：是否在换 Prompt 的同时换了模型、样例或参数。

这个顺序避免把所有失败都归结为“模型不稳定”。很多波动其实来自任务接口不稳定。

## 产品策略必须显式进入版本

需求评审助手可以偏审慎：证据不足就追问；也可以偏启发式：允许提出潜在风险，但必须标记依据不足。这是产品决策，不是模型自动决定的性格。

两种策略不能悄悄混在同一版本。改变风险容忍度、拒答倾向或输出受众时，应形成可见版本，并用固定样例重新比较质量和代价。

## Prompt 不能替代什么

Prompt 不能完成：

- 知识检索与资料更新；
- Schema 强校验；
- Citation 存在性和支持性验证；
- Tool 权限、参数校验和副作用控制；
- 统计化质量评估；
- 会话状态和长期记忆管理。

如果缺少的是事实、类型、权限或评估证据，继续堆提示文字只会让责任更混乱。

## 用实验验证什么

配套实验固定模型、样例、证据和采样参数，只切换 Prompt 版本，比较约束遵循、遗漏、无依据扩写、结构稳定性和成本。模板位置、运行命令、日志、读码和修改任务全部放在[实验篇](../labs/prompt-engineering.md)。

## 掌握标准

完成本节后，应能：

1. 把一段临时 Prompt 拆成任务、材料、约束和输出责任。
2. 解释 Prompt、Context 和 Schema 的边界。
3. 为变量说明来源、空值语义和信任级别。
4. 判断 Few-shot 是在定义边界还是在污染任务。
5. 设计一次只改变一个因素的 Prompt 对照。
6. 根据失败类型判断应修改 Prompt、证据、Schema 还是评估方法。

本节交付的是可维护的任务协议，不是检索、结构校验或质量保证。完成实验后回到[标准学习路径](../learning-path.md)。
