# 面向应用的 Prompt Engineering

> 机制篇：把 Prompt 从临时文字变成可解释、可版本化、可受控比较的任务协议。
>
> 课程位置见[标准学习路径](../learning-path.md)。前置是稳定的模型调用边界；模板、运行、观察和修改见[配套实验](../labs/prompt-engineering.md)。

## 为什么“写一句更好的提示词”不够

临时聊天只要求当前回答看起来合理，产品里的 Prompt 还要被复用、修改、比较和追踪。若任务、材料和输出要求散落在代码字符串里，一次改动可能同时改变多个变量，失败也无法归因。

需求评审助手会逐步承担风险识别、补充问题和报告综合。每类任务都需要稳定回答：

- 模型这一轮扮演什么角色；
- 只处理哪些材料；
- 目标是什么；
- 必须遵守和不得越过什么；
- 输出将被谁消费；
- 证据不足时怎样处理。

因此 Prompt 的核心不是“咒语”，而是一份模型任务协议。

先比较同一份售后需求的两种要求：

```text
要求 A：帮我评审这份需求。

要求 B：只依据 Requirement 和 Evidence，
从状态、接口、多端一致性和失败分支识别研发风险；
证据不足时提出待确认问题，不得补充材料中不存在的接口。
```

第二种不只是“写得更详细”。它开始定义任务范围、材料边界、禁止行为和证据不足时的处理方式。这些内容一旦影响产品结果，就必须能够命名、版本化和比较，而不能只存在于某个开发者临时修改的字符串中。

本节提供的是当前项目的一套最小工程方法，不是行业唯一模板。需要区分三层：

| 层次 | 稳定内容 |
| --- | --- |
| 通用原则 | 任务边界、变量来源、版本和对照必须可追踪 |
| 当前工程实践 | 使用可版本化模板和稳定任务身份组织 Prompt |
| 项目取舍 | 先围绕风险评审任务，用固定 Evidence 建立受控对照 |

换到客服、合同审查或测试生成场景，段落和变量会变化，但“任务可解释、变化可比较、失败可归因”仍然成立。

## 任务协议由哪些部分组成

可以用六个视角检查 Prompt，但不要求每份模板机械地写成六个标题。

| 组成 | 回答的问题 | 缺失后的典型表现 |
| --- | --- | --- |
| 角色 | 从什么职责和视角工作 | 风险评审变成泛化产品建议 |
| 任务 | 本轮只完成什么原子目标 | 摘要、评审和建议混在一起 |
| 材料 | 哪些内容属于本轮事实输入 | 用常识补出材料中没有的接口 |
| 约束 | 必须做什么、禁止做什么 | 强答、编造或遗漏关键边界 |
| 示例 | 合格输出的风格和粒度 | 类别和表达粒度反复漂移 |
| 输出描述 | 后续希望怎样消费结果 | 结构和字段不稳定 |

拆分的价值在于可诊断。角色错、材料缺、约束冲突、示例污染和输出结构漂移属于不同问题，不能都用“再加一句 Prompt”处理。

### 角色不是人格装饰

“你是一个专业助手”几乎没有定义可验证行为。有效角色应限制判断视角和责任，例如从研发实现角度发现接口、状态和多端风险，而不是替产品经理重新设计需求。

角色也不能授予模型应用权限。即使 Prompt 写着“你可以修改文件”，真正的文件写入仍必须经过 Tool Runtime、权限和确认。

### 任务要能在一轮内判断是否完成

“分析需求并给出所有建议”包含摘要、风险发现、方案设计和验收规划等多个目标。模型可能每次选择不同重点，结果难以比较。原子任务则能明确判断输出是否完成了本轮职责。

任务不一定很短，但必须有清晰完成条件。风险识别可以要求覆盖哪些维度；补充问题生成则应只把证据缺口转成问题，不能顺便重新生成整份报告。

### 材料边界决定模型可以依据什么

Prompt 必须区分被评审需求、可引用证据、历史辅助信息和用户当前问题。它们都可能出现在 Context 中，却不具有相同证据资格。

模型“看见”一段内容只表示这段内容进入了上下文，不表示它是现行规则，也不表示可以成为 Citation。材料角色如果没有明确，模型很容易把历史案例或示例当成当前事实。

### 约束应该对应具体失败

“认真”“全面”“高质量”无法验证。有效约束应指向已知失败，例如不得编造接口、证据不足时不得形成强结论、来源编号只能来自候选集合。

约束不是越多越好。互相冲突的要求会制造新的随机性，例如同时要求“只输出高置信风险”和“至少输出十条”。新增约束前应先说明它要防止哪类 bad case。

### 示例定义边界，不提供现行业务事实

Few-shot 适合展示风险项应该有多细、枚举如何表达、合格理由怎样绑定依据。它不适合偷偷携带会变化的接口版本和业务规则。

### 输出描述只表达意图

Prompt 可以告诉模型期望哪些字段或段落，却不能强制类型和枚举合法。输出描述为 Structured Output 铺路，但最终接受边界仍由 Schema 和业务校验负责。

## Prompt、Context 与 Schema 的分工

三者会一起进入模型任务，但责任不同：

| 对象 | 主要责任 | 不能保证 |
| --- | --- | --- |
| Prompt | 描述任务、材料边界、行为约束和输出意图 | 资料真的存在、字段一定合法 |
| Context | 提供本轮可见的事实和证据 | 模型一定正确使用证据 |
| Schema | 定义应用接受的字段、类型和枚举 | 结论事实正确或引用充分 |

在 Prompt 中写“只依据公司规范”不会自动给模型公司规范。证据由 RAG 或其他可信来源提供，Prompt 只规定怎样使用证据；应用还要校验输出和 Citation。

这也是为什么固定 Evidence 可以用于 Prompt 实验，却不能冒充已经建成知识库：它只隔离“任务协议怎样影响输出”这一变量。

可以把三者类比为填写表单：Prompt 说明为什么填、依据什么填和怎样填写；Context 提供本轮能够参考的材料；Schema 定义表格有哪些字段以及什么值可被系统接受。说明写得再严格，也不会自动生成缺失材料，更不会让非法字段变合法。

## 从临时文字到可维护协议

Prompt 工程通常经历以下变化：

```text
临时任务文字
  → 任务文字与业务材料分离
  → 显式变量契约
  → 稳定任务身份与版本
  → 固定输入上的受控对比
```

稳定身份回答“这是什么任务”，版本回答“当前采用哪组任务规则”。两者必须随运行记录保存。否则团队说“上一版更稳”时，无法还原当时的任务文本、输入、模型和参数。

从临时文字走到可维护协议，可以分成五个阶段：

1. **任务文字写在调用处**：能运行，但任务变化与代码变化混在一起。
2. **业务材料通过变量注入**：规则和数据开始分离，但任务仍没有稳定身份。
3. **模板独立保存**：变化可以被审查，却还难以表达线上究竟用了哪一版。
4. **任务身份和版本分离**：调用方引用稳定任务，运行记录保存具体版本。
5. **固定输入进行版本对照**：Prompt 修改第一次成为可验证实验，而不是凭印象覆盖旧文字。

这里真正重要的不是模板采用 YAML、数据库还是远端平台，而是任务真源唯一、身份稳定、历史版本可回放。存储形式只是实现选择。

模板采用什么文件格式是实现选择；真正的机制要求是：任务真源可以版本化，变量来源可检查，调用方通过稳定身份取得确定版本，缺少关键变量时显式失败。

## 变量契约为什么重要

Prompt 模板中的变量不是随意占位符，而是任务输入接口。需求评审场景常见四类输入：

| 输入 | 责任 |
| --- | --- |
| 需求文本 | 用户本轮希望评审的对象 |
| 证据块 | 可引用的内部规则或检索候选 |
| 评审维度 | 本轮需要覆盖的稳定检查范围 |
| 已知摘要 | 前序步骤保留下来的受控信息 |

每个变量至少要有来源、必填性、空值语义和长度边界。缺少证据不应被悄悄渲染成一个看似完整的 Prompt；否则模型强答后，问题会被错误归因成模型幻觉。

“变量缺失”和“变量明确为空”也不是一回事。前者表示调用方没有履行输入契约，应在模型调用前失败；后者可能是合法业务状态，例如本轮确实没有检索到证据，此时 Prompt 应触发拒答或追问行为。

变量渲染完成后，任务协议和本轮数据共同形成消息。模板负责稳定规则，变量负责变化事实，两者不能反过来：业务规则不应藏进临时数据，用户内容也不能被当成更高优先级指令。

同一个任务版本还应使用相同的变量语义。若某次 `evidence` 表示现行规则，另一次却混入历史评审摘要，即使变量名和 Prompt 版本都没变，实验身份也已经漂移。

## Few-shot 何时有用

Few-shot 是在输入中提供少量示例，让模型从示例理解合格结果的边界。它适合解释抽象文字难以定义的风险类别、表述粒度或引用形式，不适合承载频繁变化的业务事实。

一个示例是否值得加入，可以检查：

1. 当前失败是否来自“合格结果长什么样”不清楚；
2. 仅靠文字规则是否仍难以对齐；
3. 示例中的内容是否稳定，不会让模型照搬旧接口或旧状态机；
4. 增加的上下文成本是否值得。

示例越具体，污染风险越大；示例越多，成本和噪声越高。历史评审记录更适合作为 RAG 资料或评估样例，而不是无选择地塞进 Prompt。

例如示例中写着“客户端必须继续使用旧版字段”，而当前需求已经迁移到新接口。模型可能反复输出旧字段风险，即使当前材料从未提到它。这不是模型记忆出了问题，而是示例在任务上下文中拥有过强暗示。

## 坏 Prompt 怎样暴露协议缺口

考虑下面的要求：

```text
你是一个专业的需求评审助手，请认真、全面地分析需求并输出风险。
```

它的问题不在于文字太短，而在于不可检查：“专业”是哪种视角，“全面”覆盖哪些维度，哪些材料可以作为事实，缺少信息时是否允许推测，输出给人看还是给程序处理，都没有定义。

更稳定的协议应明确：从研发视角工作；只基于本轮 PRD 与证据；识别研发风险；不得编造接口、状态、权限和埋点；证据不足时提出缺口；按风险类别、等级、理由和依据组织。

这仍不是最终 Schema，但失败已经更容易归因。若材料缺失，应修 Context；若字段漂移，应进入 Structured Output；若任务效果在多样例上不稳定，应进入 Harness 和评估，而不是无限加长 Prompt。

一个实用判断是：每增加一段文字，都应该能回答“它在防哪种失败，如何验证它有效”。无法回答时，这段文字很可能只是让 Prompt 看起来更专业，并没有建立新的任务边界。

## 怎样进行可信的版本对照

Prompt 对比必须固定输入样例、模型配置、采样参数、证据和输出 Schema，只改变一个协议因素。这就是本节所说的单变量对照，例如：

- 增加明确的证据不足行为；
- 调整一个约束；
- 加入或移除一个示例；
- 修改输出描述。

观察也要针对具体失败，而不是只问“更喜欢哪版”：

| 观察 | 对应问题 |
| --- | --- |
| 是否编造材料外事实 | 材料边界和约束是否有效 |
| 是否遗漏约定维度 | 任务范围是否明确 |
| 是否稳定说明证据不足 | 拒答或追问边界是否明确 |
| 输出结构是否更一致 | 输出描述是否清楚 |
| token 和延迟怎样变化 | 新规则和示例的代价 |

单次漂亮输出不能证明版本更好。当前实验建立最小受控比较，后续 Harness 才在固定数据集上形成更可靠的回归证据。

还要区分探索和验收。探索阶段可以观察某个版本似乎减少了编造；要把它升级为默认版本，则需要在固定样例上比较风险覆盖、证据使用、结构稳定性、token 和延迟，并保留旧版本结果。

## Prompt 失败时的定位顺序

1. **任务是否单一**：是否把摘要、风险、建议和报告混成一轮。
2. **材料是否存在**：模型是否真的看到了 PRD 和证据。
3. **边界是否一致**：是否同时要求“尽量简短”和“覆盖所有维度”。
4. **输出是否可检查**：下游究竟需要文本段落还是稳定字段。
5. **示例是否污染**：是否照搬了示例中的过期规则。
6. **实验变量是否固定**：是否在换 Prompt 的同时换了模型、样例或参数。

这个顺序避免把所有失败都归结为“模型不稳定”。很多波动其实来自任务接口不稳定。

## 产品策略必须显式进入版本

需求评审助手可以偏审慎：证据不足就追问；也可以偏启发式：允许提出潜在风险，但必须标记依据不足。这是产品决策，不是模型自动决定的性格。

两种策略不能悄悄混在同一版本。改变风险容忍度、拒答倾向或输出受众时，应形成可见版本，并用固定样例重新比较质量和代价。

例如同一份 PRD 没有说明接口失败兜底：审慎策略会要求只提出待确认问题；启发式策略可以输出“潜在风险”，但必须标记依据不足。两种策略都可能合理，真正的问题是产品没有明确选择，却希望模型自己保持一致。

## 怎样形成 Prompt 的学习所有权

能够让 AI 生成一份模板，不等于已经掌握它。学习者至少应能解释：

- 角色限制了哪个判断视角；
- 每条约束对应哪个已知失败；
- 变量来自哪里，空值意味着什么；
- 示例是否可能过期或污染；
- 输出描述是给人阅读，还是为 Schema 铺路；
- 修改一处后应该用哪类固定样例验证。

如果这些问题无法回答，Prompt 当前即使效果不错，也仍是不可维护的偶然结果。

## Prompt 不能替代什么

Prompt 不能完成：

- 知识检索与资料更新；
- Schema 强校验；
- Citation 存在性和支持性验证；
- Tool 权限、参数校验和副作用控制；
- 统计化质量评估；
- 会话状态和长期记忆管理。

如果缺少的是事实、类型、权限或评估证据，继续堆提示文字只会让责任更混乱。

常见失败可以这样归因：

| 表现 | 更可能的问题 | 不应先做什么 |
| --- | --- | --- |
| 输出空泛、编造系统 | 材料边界或约束不足 | 先增加复杂 Schema |
| 同一任务时长时短 | 任务混杂或约束冲突 | 继续堆互相矛盾的要求 |
| 反复照搬旧规则 | Few-shot 污染 | 把旧规则再写一遍强调 |
| 看起来像 JSON 但程序接不住 | 缺少结构化契约 | 只增加“请严格输出” |
| 新版本似乎更好但无法复现 | 对照变量没有固定 | 直接覆盖旧版本 |

## 用实验验证什么

配套实验固定模型、样例、证据和采样参数，只切换 Prompt 版本，比较约束遵循、遗漏、无依据扩写、结构稳定性和成本。模板位置、运行命令、日志、读码和修改任务全部放在[实验篇](../labs/prompt-engineering.md)。

## 掌握标准

完成本节后，应能：

1. 把一段临时 Prompt 拆成任务、材料、约束和输出责任。
2. 解释 Prompt、Context 和 Schema 的边界。
3. 为变量说明来源、空值语义和信任级别。
4. 判断 Few-shot 是在定义边界还是在污染任务。
5. 设计一次只改变一个因素的 Prompt 对照。
6. 根据失败类型判断应修改 Prompt、证据、Schema 还是评估方法。

本节交付的是可维护的任务协议，不是检索、结构校验或质量保证。完成实验后回到[标准学习路径](../learning-path.md)。
