# Course Writing

编写或重写 `course/**/*.md` 时执行本 Skill。

规则真源是 [docs/learning-guide.md](../../docs/learning-guide.md)。本 Skill 只提供写作流程和条件化自检，不建立第二套模板。

## 写前

1. 阅读 `docs/strategy.md`，确认当前项目阶段和长期边界。
2. 阅读 `docs/learning-guide.md` §1–§9，确认学习路径、文档类型和代码关系。
3. 新增知识、技术或功能时，先按其中“知识与功能的分级准入”判断进入项目篇、机制篇、概念篇还是未来认知；不要因实现困难降低产品必需能力的级别。
4. 判断当前文档属于概念篇、机制篇还是项目篇；不能同时承担三个主体。
5. 阅读 `course/knowledge-map.md` 和当前项目篇（存在时），确认它为什么需要、优先级和前置知识。
6. 阅读被引用的真实代码、package README、demo README 或产品 README。
7. 若机制已有真实实现，先找出公共入口、核心调用链、关键不变量和实验入口，决定正文需要解释哪些关键代码。
8. 用一句话写出本文核心问题、目标读者和明确非目标。
9. 先设计解释顺序，再决定标题；不要先套固定章节。

涉及 Agent、Tool、Workflow 或 Multi-Agent 时，另读 `docs/learning-guide.md`
“Agent、Workflow 与 Multi-Agent 工程规则”，不要自行弱化其中的控制、状态、恢复、评估和安全约束。

若 `course/knowledge-map.md` 或新目录尚未落地，以用户当前目标和 `docs/` 真源为准，不自行创建占位结构。

## 选择文档类型

### 概念篇

当主要任务是回答“是什么、为什么需要、与相近概念有何区别、边界在哪里”时，写概念篇。

至少讲清：

- 真实问题和一句话定义。
- 输入、处理和输出。
- 最小心智模型或数据流。
- 与相近概念的区别。
- 一个反例或常见误区。
- 能解决与不能解决什么。
- 在需求评审助手中的位置和当前优先级。

概念篇通常不新增代码。不要用 package 文件树、运行参数和框架 API 主导阅读。

### 机制篇

当主要任务是回答“为什么有效、内部如何变化、失败时如何定位”时，写机制篇。

至少讲清：

- 简单方案的问题。
- 输入输出如何变化。
- 内部数据流、关键约束和不变量。
- 从简单到工程方案的递进。
- 可观察的最小实验。
- 一个来自真实输入、真实依赖或正常策略取舍的 bad case / 边界现象及排查顺序。
- 不要求独立失败章节，不为满足写作清单凭空制造异常输入、损坏实现或无业务意义的报错演示。
- 框架封装了什么、没有解决什么。
- 对应 package、demo 或外部服务边界。

已有真实实现时，还要让正文能够独立建立公共入口、核心调用链、关键数据变化和失败层与代码的对应；不能只链接 README。完整运行参数和源码阅读顺序仍由 demo / package README 承担。

仅在需要新观察维度或通用实现时修改代码。优先复用已有 package 和 demo。

### 项目篇

当主要任务是定义 V0–V6 某个版本的业务契约、综合实现和验收时，写项目篇。学习者可以在版本开始时先读取其中的业务场景、输入输出、Definition of Ready 和非目标，为后续实验取得固定契约；完整实现和验收仍位于必要概念、机制和小实验之后。项目篇不作为脱离标准学习路径的零基础阅读入口。

至少讲清：

- 业务目标、已有能力、新增能力和非目标。
- 输入、输出和业务契约。
- 进入项目前应具备的概念和机制，并链接回 `course/learning-path.md` 的标准路线。
- 需要学习者作出的设计选择。
- `source/packages/` 与 `review_assistant/` 的真实入口。
- 运行时应观察什么。
- 至少一个真实 bad case / 自然边界题和一个需求变更题。
- 数据流、状态流和异常流。
- 版本验收标准。

项目篇不复制产品安装、API 和部署说明；链接到 `review_assistant/README.md`。产品 README 也不复制项目篇的课程原理。

## 组织正文

根据核心问题自由组织标题。可以采用场景、数据流、对比、递进、实验、失败分析或决策树，但不要机械复制统一目录。

始终遵守：

- 先用自然语言和小例子建立主线，再引入正式对象、字段和框架。
- 表格用于精确比较，不代替机制解释。
- 代码片段只在能帮助理解时使用，来自真实文件并标注路径。
- 不规定统一篇幅、代码块数量或自检题数量；厚度由问题复杂度决定。
- 工程方案要区分通用原则、当前实践、项目取舍和明确非目标。
- 未实现内容明确写成边界，不能用设计草图冒充真实能力。
- 相关链接以当前阅读需要为准，不按“同课上下节”机械连接。
- 正文不自行维护“下一篇”；只说明必要前置、本文交付和在标准学习路径中的位置，读完后返回 `course/learning-path.md`。

## 代码、实验与 README

### 决定是否修改代码

按顺序判断：

1. 这是纯概念建立吗？若是，通常不改代码。
2. 已有代码或实验能否支撑机制观察？若能，直接复用。
3. 已有 demo 增加小配置能否完成对照？若能，不新建目录。
4. 是否出现新的通用能力？若是，扩展唯一 package。
5. 是否进入产品版本？若是，在 `review_assistant/` 组合能力。

不要为文档数量、类型或编号创建平行 package、demo 或 app。

### README 分工

- package README：模块职责、代码阅读顺序、调用链和扩展边界。
- demo README：实验变量、运行命令、输出解读和常见失败。
- product README：安装、配置、启动、测试、API 和部署。
- course 文档：概念、机制、项目判断和学习验收。

课程正文引用这些 README，不复制完整操作手册。

## 真实调用

- LLM、RAG、Agent 和 Eval 主路径调用真实模型或真实外部服务。
- 缺少 key、限流、超时和供应商异常应清晰暴露。
- 不在真实调用失败后静默返回 fake 或 mock。
- Mock 只用于单元测试、离线排查、稳定失败复现或明确对照。
- 使用 Mock 时，标明验证对象、局限和真实运行路径。

## 写后自检

### 所有类型

- [ ] 文档类型单一且核心问题明确。
- [ ] 开头让读者知道为什么读、读完得到什么、本文不做什么。
- [ ] 新概念先有自然语言或小例子，再出现对象名和框架。
- [ ] 没有用表格、代码块、文件树或命令替代解释。
- [ ] 通用原则、工程实践、项目取舍和非目标没有混为标准答案。
- [ ] 与当前 `docs/`、代码和 README 一致。
- [ ] 没有写迁移过程、实时进度或未实现的成功结论。

### 概念篇

- [ ] 能解释定义、输入输出、相近概念、反例和边界。
- [ ] 说明了它在需求评审助手中的位置和优先级。
- [ ] 没有为了交付感强行新增代码。

### 机制篇

- [ ] 数据流、关键约束和递进关系可独立读懂。
- [ ] 有可观察实验或说明为什么当前只做认知。
- [ ] 真实 bad case 或自然边界包含表现、原因假设和验证路径，没有为了教学凭空制造异常。
- [ ] 框架出现前已经解释基础机制。
- [ ] 已有真实实现时，正文解释了公共入口、核心调用链、关键代码和至少一个不变量，而不只是给出链接。

### 项目篇

- [ ] 对应 V0–V6 的一个明确版本范围。
- [ ] 有业务契约、设计选择、真实 bad case / 自然边界题、需求变更和验收。
- [ ] 指向真实 package 和产品入口。
- [ ] 没有复制产品 README。
- [ ] 真实运行、评估和异常是验收的一部分。

## 禁止

- 强制套用“真实问题 → 原理 → 实现 → 框架 → 失败”的固定标题。
- 按旧课程编号、每课 00 或普通专题规则组织新文档。
- 在 `course/concepts/` 或 `course/mechanisms/` 下按 LLM、RAG、Agent 等能力域创建子目录；正文平铺，能力域只写入 `knowledge-map.md`。
- 将知识清单条目机械扩写成正文。
- 一篇文档同时做概念教材、源码导览和产品运行手册。
- 为每篇文档新建 demo 或 package 增量。
- 用 Mock 结果证明真实模型或项目质量。
- 将多 Agent、Schema、Prompt 或目录取舍包装成唯一标准答案。
- 主动创建 Git commit 或 tag，除非用户明确要求。
