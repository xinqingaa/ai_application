# Course Writing

用于编写、重写或审查 `course/**/*.md`。规则真源是 [docs/learning-guide.md](../../docs/learning-guide.md)；本 Skill 只保留写作流程和最小自检。

## 写前

1. 阅读 `docs/strategy.md`、`docs/learning-guide.md`、学习路径和知识地图中的相关部分。
2. 涉及产品职责时读取 `SPEC.md`、`PLAN.md` 和对应项目篇。
3. 判断文档属于概念、机制、实验还是项目；不能同时承担多个主体。
4. 用一句话确定核心问题、读者已有输入、本文交付和非目标。
5. 阅读配套正文、实验代码、README 与真实测试。
6. 先确定解释顺序，再决定标题，不套固定目录。

## 粒度闸门

一篇正文只回答一个核心问题。若出现两个独立生命周期、两种主要状态变化、两套实验变量或不同失败模型，优先拆分。

协议课程尤其要分开概念与责任边界、协议生命周期、真实接入实验、项目职责和验收。一节课可以同时链接机制篇和实验篇，不因文件数量增加课程序号。

## 概念篇

至少讲清真实问题与定义、最小心智模型、输入输出、相近概念、误区或反例、适用边界和项目位置。默认不讲实现代码、运行命令和项目任务。阶段完成后可以补充“学完后回看”，但不能变成全部机制的汇总。

## 机制篇

至少讲清当前问题和已有输入、一条主要数据流或状态流、一个关键约束、简单方案的不足和正常边界。

新术语第一次出现时先用自然语言解释。机制篇可以使用公式、状态图、业务样例和最小抽象数据形状；不系统讲源代码、SQL、Shell、文件树、公共类调用、完整日志字段、安装步骤或读码顺序。只有缺少该片段就无法解释机制时，才保留极少量关键语法并立即回到原理。配套实验只链接，不复制操作手册。

## 实验篇

正文位于 `course/labs/`，代码位于 `source/demos/` 或产品。至少讲清对应机制和观察问题、环境与真实依赖、入口与命令、运行前预测和唯一主要变量、输出与日志、失败区分、排查顺序、读码入口、修改题和验证命令。

实验篇不重复完整原理。Mock 必须标明验证对象和局限，主路径仍指向真实服务。

## 项目篇

项目篇引用 `SPEC.md`，不复制产品规格或产品 README。至少讲清阶段学习目标和检查点、已有能力、设计选择、真实代码入口、自然 bad case、需求变更、数据/状态/异常流、验收证据和非目标。

## 组织方式

- 从学习者当前遇到的问题开始。
- 术语沿数据流按需出现，不在开头堆完整架构。
- 表格只用于精确比较，不代替解释。
- 复用相邻课程的业务材料，避免换样例掩盖差异。
- 不写死“上一节、下一节”；说明知识输入、本文交付和复用方向。
- 通用原则、当前实践、项目取舍和非目标必须分开。
- 未实现内容明确写成边界，不冒充已经落地。

## 代码与文档

- 概念篇通常不改代码。
- 机制篇不因已有代码而转为源码讲解。
- 新观察维度进入已有或必要的新 demo。
- 新通用能力扩展唯一 package。
- 产品组合只进入 `source/apps/review_assistant/`。
- 不为每篇文档创建 package、demo 或 app。

## 最小自检

- [ ] 核心问题单一，读者输入和本文交付明确。
- [ ] 新概念首次出现时已经解释。
- [ ] 没有复制其他真源或记录迁移过程。
- [ ] 概念篇没有被实现主导。
- [ ] 机制篇没有源代码、命令、安装和源码导览。
- [ ] 实验篇有预测、单变量、日志阅读、排查和验证。
- [ ] 项目篇引用 SPEC，有检查点、需求变更和验收证据。
- [ ] 真实调用失败不会静默变成 Mock 成功。

## 禁止

- 建立第二套课程顺序或阶段内版本轴。
- 将知识地图条目机械扩写成正文。
- 让机制篇退化为源码导览。
- 让实验篇重复完整原理。
- 让项目篇复制 SPEC 或产品 README。
- 用 Mock 证明真实模型、检索或 Agent 质量。
- 未经用户要求创建 Git commit 或 tag。
