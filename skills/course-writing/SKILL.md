# Course Writing

用于编写、重写或审查 `course/**/*.md`。规则真源是 [docs/learning-guide.md](../../docs/learning-guide.md)；本 Skill 只维护执行流程、按需迁移检查和可操作自检。

## 写前

1. 阅读 `docs/strategy.md`、`docs/learning-guide.md`、学习路径和知识地图中的相关部分。
2. 涉及产品职责时读取 `SPEC.md`、`SDD.md`、`PLAN.md` 和对应项目篇。
3. 涉及已有实现时读取配套正文、实验代码、README 和真实测试。
4. 判断文档属于概念、机制、实验还是项目；不能同时承担多个主体。
5. 用一句话写下核心问题、学习者已有输入、本文交付和非目标。
6. 判断知识是学习主线、扩展还是未来认知，以及产品是必接、条件接入、受控实验还是不实现。
7. 先确定解释顺序和主要数据或状态流，再决定标题，不套固定目录。
8. 涉及 MCP、A2A、Agent Skills 等演进协议时，核对官方当前稳定规范，记录正文依据的规范修订和实验使用的 SDK 版本，区分稳定核心、可选扩展、实验能力与已弃用内容。
9. 涉及 Agent 框架时，先标明 Provider API、框架运行时、本地通用封装和产品领域组装分别负责什么，并判断当前内容是在解释框架能力与实现逻辑，还是在演示某个版本的 SDK 操作。
10. 编写尚未成文的连续课程前，确认产品输入、核心对象、完成条件、人工门、阶段交接和验收已经由上游真源锁定。若发现其中存在方向性缺口，先报告并回到 `SPEC.md`、`SDD.md`、`PLAN.md` 与学习路径处理；正文只能细化已确定的方向，不能临时定义另一条产品主线。
11. 课程规划中的编号只允许出现在 `course/learning-path.md`；高级 Agent 能力、协议和质量方法仍必须学习、实验和比较。固定教学 fixture 不等于产品启动前置；涉及产品入口时必须区分新 Project 的空 Brief / 空检索池冷启动与已有项目的证据沉淀。第二阶段 Agent 只在 editor 或 owner 已创建或选择的轻量 Requirement `draft` 上介入，不能把自然语言种子直接写成正式 Requirement。

## 学习者路线

优先使用下面的解释顺序：

```text
当前遇到的具体问题
→ 已有经验能建立的直觉
→ 数据或状态推进时需要的新术语
→ 主要机制和关键约束
→ 正常边界与失败边界
→ 在需求评审助手中的位置
→ 实验观察与修改验证
```

新术语第一次出现时先用自然语言解释。不要在开头罗列完整架构，也不要用尚未解释的术语互相定义。

## 粒度闸门

一篇正文只回答一个核心问题。若出现两个独立生命周期、两种主要状态变化、两套实验变量或不同失败模型，优先拆分。

协议课程尤其要分开：概念与责任边界、能力模型、协议生命周期、真实接入实验、项目职责和验收。工具课程还要区分“是否应当使用”与“运行时怎样执行”。一节课可以链接机制篇和实验篇，不因文件数量增加课程序号。

学习路径中的每个编号必须有当前问题和学习交付，不能只写标题、状态或实验链接。知识地图中的每个节点必须有核心问题与边界说明。

标题保持简洁，优先使用学习者已经接触过的术语，表达核心对象、关系或边界；标题下方的介绍再补充当前问题、学习交付和非目标。不要为了覆盖所有子步骤把标题写成说明句，也不要在术语尚未解释前用本地 package、类名或目录名命名课程。

## 概念篇

至少讲清：

- 学习者当前为什么需要这个概念。
- 用自然语言表达的定义和最小心智模型。
- 输入、输出或主要参与者。
- 与相近概念的区别。
- 一个误区或反例。
- 适用和不适用边界。
- 在产品中的位置，但不展开项目实施。
- 涉及框架时，说明 Provider、框架运行时、本地通用封装和产品领域组装的层次与选型边界。

默认不讲实现代码、运行命令、SDK 版本和项目任务。阶段完成后可以补充“学完后回看”，但不能变成全部机制的汇总。

## 机制篇

至少讲清：

- 当前问题和已有输入。
- 一条主要数据流、状态流、证据流或异常流。
- 新对象为什么在此时出现。
- 一个关键约束或不变量。
- 简单方案为什么不足。
- 正常边界和失败边界。
- 本文向后续能力交付什么。
- 当前能力由原生实现、成熟框架还是二者组合承载。
- 使用框架时，框架怎样实现当前能力，应用怎样配置、约束和组合它。

框架是机制的主要实现手段时，正文直接讲解框架的公开能力、核心抽象、运行流程和扩展位置，说明框架怎样完成当前能力、应用怎样提供配置与业务约束，以及二者如何组合。可以使用框架术语、公式、状态图、业务样例、接口形状、伪代码和少量关键代码；最小原生实现只在有助于看清框架隐藏责任时作为对照，不是机制篇的前提。

机制篇不承担安装、命令、完整可运行项目、完整日志、逐步调试、读码顺序或按版本罗列的 SDK 调用，也不逐行导览框架或本地源码。配套实验负责把机制运行、观察和验证出来，不复制完整原理。

## 实验篇

正文位于 `course/labs/`，代码位于 `source/demos/` 或产品。实验篇必须让学习者不依赖已删除的旧文档也能完成操作。

至少讲清：

1. 对应机制、观察问题和不能证明的内容。
2. 环境、真实依赖、凭证、数据和运行前检查。
3. 唯一主入口、精确命令、参数、默认值和退出状态。
4. 固定输入、运行前预测和唯一主要变量。
5. 正常输出、关键日志字段和读法。
6. 自然边界、真实依赖失败和确定性失败的区别。
7. 按“表现 → 可能层次 → 验证方式”组织的排查顺序。
8. demo → 公共入口 → 核心步骤 → 测试的读码路径，并说明各自责任。
9. 一个修改任务、预期变化、不应变化的契约和验证命令。
10. 使用框架或协议时固定 SDK、Provider 和协议版本，观察公开状态、事件、错误和 Trace，并说明升级差异。

Mock 必须标明验证对象和局限，主路径仍指向真实服务。框架课程先运行成熟实现；最小原生实现只做单变量对照，不能扩成第二套教学框架。存在稳定失败复现时，要明确它证明状态机或错误契约，不证明真实服务质量。

## 项目篇

项目篇引用 `SPEC.md` 与 `SDD.md`，不复制产品规格、详细设计或产品 README。至少讲清：

- 阶段学习目标和核心业务问题。
- 已有能力和 Definition of Ready。
- 数据、状态、工具、证据和异常怎样流动。
- 必须做出的设计选择。
- 真实代码入口和组合责任。
- 集成检查点及其验收证据。
- 框架运行时、本地通用层和领域组装的职责分界，以及新能力进入了正确层次。
- 自然 bad case、需求变更和回归。
- 明确不做的能力。

## 旧内容重构与迁移（按需）

新写课程、普通改写和质量审查跳过本节。只有移动、合并或删除已有内容时，删除原内容前必须完成：

1. 枚举准备删除的代码、命令、输出解读、调试、读码和验收内容。
2. 将每块内容标记为机制、实验、README、测试、SPEC / PLAN / 项目篇或废弃。
3. 先在目标位置形成可用内容，再删除原文。
4. 检查代码注释、README、学习路径和相邻课程是否仍引用旧位置。
5. 验证命令、参数、默认值、文件路径和测试入口与当前代码一致。
6. 删除临时迁移清单，不把迁移过程写入长期文档。

不能因为实验篇出现了“预测、日志、测试”等关键词就判断迁移完成。必须实际检查学习者能否准备、运行、观察、定位、修改和验证。

## 实验与验收纪律

- 先预测再运行，一次只改变一个主要变量。
- 复用稳定业务材料，不通过更换样例制造更好结果。
- 区分自然 bad case、真实依赖失败和确定性契约失败。
- 区分探索实验与验收实验。
- 支撑准入或验收时，预先冻结数据、版本、对照、指标、通过条件和预算。
- 运行后不删除失败样例、不回改阈值、不覆盖旧结果。
- 真实依赖失败可以成为失败记录，不能静默替换为 Mock 成功。

## 代码与文档

- 概念篇通常不改代码。
- 机制篇不因已有代码而转为源码讲解。
- 新观察维度进入已有或必要的新 demo。
- 新通用能力扩展唯一 package。
- 产品组合只进入 `source/apps/review_assistant/`。
- 不为每篇文档创建 package、demo 或 app。
- 不预建空实现、空 fixture 或占位运行入口。
- 第二阶段的 `agent_core` 随 Agent 框架接入建立，并在课程推进中扩展通用运行、治理和适配能力；实验可以直接调用框架观察公开行为。
- `agent_core` 组合和适配成熟框架，不重复实现框架运行时；领域 Prompt、Schema、证据、权限、记忆和角色属于产品 `agent/`。

README 分工：package README 维护职责和公共 API；demo README 维护入口、测试和实验链接；产品 README 维护安装、配置、运行、API 与排错；课程实验篇维护完整学习操作。

## 完成自检

- [ ] 核心问题单一，学习者输入、本文交付和非目标明确。
- [ ] 解释从具体问题开始，新概念首次出现时已经解释。
- [ ] 学习路径条目有问题与交付，知识地图节点有说明。
- [ ] 没有复制其他真源或记录迁移过程。
- [ ] 概念篇没有被实现或项目任务主导。
- [ ] 机制篇没有命令、安装、完整日志和系统性源码导览。
- [ ] 实验篇能从干净环境运行，并有预测、单变量、日志阅读、排查、读码、修改和验证。
- [ ] 项目篇引用 SPEC，有检查点、需求变更和验收证据。
- [ ] 学习主线与产品准入已经区分。
- [ ] 协议正文已核对官方规范，版本特性、扩展和已弃用内容没有冒充稳定核心。
- [ ] 框架、`agent_core` 与产品 Agent 的责任分层明确，机制与 SDK 用法没有混写。
- [ ] 依赖方向是“产品领域组装 → `agent_core` 契约与适配 → Agent 框架”，没有重复实现框架运行时或把领域策略放进通用 package。
- [ ] 真实调用失败不会静默变成 Mock 成功。
- [ ] 若本次移动、合并或删除旧内容，目标归属已经存在，链接、注释和测试路径有效。

## 禁止

- 建立第二套课程顺序或阶段内版本轴。
- 将知识地图条目机械扩写成正文。
- 让机制篇退化为源码导览。
- 让实验篇退化为命令清单或重复完整原理。
- 让项目篇复制 SPEC 或产品 README。
- 用 Mock 证明真实模型、检索或 Agent 质量。
- 用压缩行数代替职责归位和学习完整性。
- 把所有框架知识推迟到实验篇，或在机制篇逐行讲框架 API 和源码。
- 把 `agent_core` 建成与成熟框架竞争的自研框架，或把产品领域策略混入通用运行层。
- 未经用户要求创建 Git commit 或 tag。
